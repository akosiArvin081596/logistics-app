# Backend (`server.js`)
Single-file Node.js/Express server. Its size is not written down here because every figure that was went stale; measure it instead: `wc -l server.js` for the length, and `grep -cE '^\s*app\.(get|post|put|patch|delete)\(' server.js` for the route registrations (one per `app.<verb>(` call at the start of a line: it includes the SPA catch-all `app.get("*")`, counts each two-path array registration (`/api/driver/position`, `/api/loads/:loadId/draft-invoice`) once, and leaves out the two `app.all()` 405 method guards and every `app.use()` mount). Google Sheets is the primary database (Sheets API v4); SQLite for local data; Drive API for rate-con lookups and a best-effort rate-con mirror (uploaded files are stored locally under `uploads/`); Socket.IO for real-time. Body limit raised to 50mb for large payloads with embedded base64 photos/signatures.

**Static file serving**: Express serves `client/dist/` if it exists (production build), else `public/` (legacy vanilla HTML/JS). SPA catch-all `app.get("*")` serves `index.html` for client-side routing.

**Schema migrations**: On boot, server runs two types of migrations:
- `ALTER TABLE ... ADD COLUMN` for adding new columns. Checks for existing columns first.
- **Rename-recreate** for CHECK constraint changes: a test insert in try-catch; on failure, rename the table, create a new one with the updated constraint, migrate data, drop the old, and clear all sessions to force re-login.

## Notable libraries

**Notable libraries**:
- **pdfkit**: PDFs for applications, invoices, onboarding docs; converts base64 camera photos to one PDF for `POST /api/documents/upload` (`imageToPdf()`: JPEG only, checked against the document photo limits in `lib/image-size.js` before pdfkit embeds it).
- **pdf-lib**: alongside pdfkit for document manipulation (e.g., embedding signatures into onboarding PDFs).
- **tesseract.js**: OCR on **Receipt** image uploads only (`extractReceiptText()` at `POST /api/documents/upload`, `docType === "Receipt"` — never POD, BOL or Other; this line used to say "POD image uploads", which was never true). It runs **after** the response: `queueReceiptOcr()` reads one receipt at a time and fills `documents.ocr_text` by id, which `GET /api/documents/:loadId` serves to `DocumentList` later — nothing reads the text synchronously, so the upload no longer waits on OCR. A queued receipt holds its image in memory until its turn, so the queue is capped at **20 jobs and `RECEIPT_OCR_MAX_QUEUED_BYTES` (64 MB) of images**, and an image OCR would skip is refused **when it is queued**, not when its turn comes. Once hooked into expense receipts but unwired for low accuracy — that path now uses Gemini (see below). OCR failure never blocks the upload. **⚠️ The OCR engine never runs in the server process** — never `require("tesseract.js")` in `server.js`. Each job runs in its own short-lived child, `lib/tesseract-ocr-child.js` (`runReceiptOcrChild()`), started with an empty environment and **SIGKILLed** at the `RECEIPT_OCR_TIMEOUT_MS` (90 s) deadline, so any failure inside the engine ends that child, never the server. **⚠️ Its `'error'` listener is attached before anything else touches the child** — a child that cannot be started at all (no file descriptors left, say) comes back with no stdio streams and no IPC channel and reports on the next tick, and an unheard `'error'` would end the server; only a child with a `pid` is ever signalled. Images over **`RECEIPT_OCR_MAX_PIXELS` (25 MP)** are not OCR'd at all, and neither is one whose dimensions cannot be read: `imageSize()` in `lib/image-size.js` (formerly `receiptImageSize()` in `server.js`) reads them from the PNG/JPEG header without decoding (`receiptOcrSkipReason()`), and decoding cost grows with pixel count, not file size. The app downscales photos to ~1.6 MP, so only a non-app client hits the limit, and the receipt is still stored. The model comes from a **version-pinned** URL (`RECEIPT_OCR_LANG_PATH`) and is cached in **`RECEIPT_OCR_CACHE_DIR`** (`.cache/tesseract/`, gitignored). The child says `{ ready: true }` once its model has loaded; a model it cannot fetch or read is answered **at once** with `{ error }` rather than waiting out the deadline. A job that fails **before `ready`** — reported or a silent exit — deletes the cached copy (`clearReceiptOcrModel()`), so a damaged model is fetched again. One that fails later failed on its image, and the model is kept. A crash is logged by its first error line, not the last line of its output (the runtime's version banner). Pinned by `scripts/test-receipt-ocr-crash.js` and `scripts/test-upload-ocr-deferral.js`.
- **nodemailer**: emails for driver onboarding acceptance and investor outreach. Needs `GMAIL_USER` + `GMAIL_APP_PASSWORD`.
- **compression**: Gzip response compression middleware.
- **archiver**: Streams zip downloads directly to the response — currently the per-truck expense-receipts bundle (lazy `require`d inside the handler; error handler installed before `pipe()`).
- **express-rate-limit**: Per-endpoint limiters; see [Rate limiting](#rate-limiting) below.

**⚠️ `poiStopsCache` is the actual cost control, not `poiLimiter`.** Each `/api/poi/fuel-stops` cache miss fans out to 4–8 billed Places calls on the Enterprise + Atmosphere SKU (~$0.16–0.32). The cache is a Map + TTL + FIFO cap (15 min, aligned to `ROUTE_CACHE_TTL`; 200 entries) sitting **after** coordinate resolution and **after** the Driver ownership check, so a hit can never bypass authorization. Keyed on the **resolved coordinates rounded to 3 decimals**, never the query string — so two loads on one lane share a fan-out and re-geocoding moves the key automatically. `limit` is not part of the key and never refetches. **Empty results are deliberately NOT cached** (an empty array is ambiguous between "no truck stops here" and "Places was briefly down"). The limiter is only the backstop on a scripted client.

**Status progression & guards**: `PUT /api/driver/status` enforces one active job — a driver can't transition to "At Shipper" with another load already active (`at shipper|loading|in transit|at receiver`) → 409 Conflict. Every change is recorded in SQLite: `recordStatusChange()` writes a `load_status_history` row (old → new status, source, actor), and `logAudit()` an `update_status` line. Uses `batchUpdate` to atomically set both the status and date columns.

**Error handling**: Route handlers catch their own errors and answer a 500 JSON body; a final Express error handler catches the rest. `POST /api/location` is a 410 stub now — geofence errors are caught inside `tryGeofenceAdvance()` and again around each call in the Routemate poller and in `ingestLinxupPosition()`, so a geofence failure never fails ingestion.

## Endpoint reference

REST endpoints (grouped by domain):

**Sheets CRUD** (Google Sheets as database):
- `GET /api/tabs` — list all sheet tab names
- `GET /api/data?sheet=&page=&limit=` — read rows (paginated, max 200/page). **Super Admin only** (2026-09-26): it answers any tab, and its `duplicates` and `?search=` over every column, as stored. Its SPA callers are the Data Manager (`/data`) and New Job (`/jobs/new`), both Super Admin routes.
- `POST /api/data?sheet=` — append row (`{ values: [...] }`). **Super Admin only** (2026-09-26), like `GET`: it appends to any tab with `valueInputOption: "USER_ENTERED"`, which stores a value starting with `=` as a formula. Its SPA callers are New Job (`/jobs/new`) and the Data Manager (`/data`), both Super Admin routes.
- `PUT /api/data/:rowIndex?sheet=` — update row by 1-based index. For every caller but a Super Admin, the broker contact rules below apply. **Writes only the cells it changes** (2026-09-26): each cell whose value as it will be written differs from the row as read, one A1 range per cell, in one `values.batchUpdate` with `USER_ENTERED` (`sheetRowCellWrites()`). The row is read as the sheet displays it and the Active Loads editor and the Data Manager send every column back as displayed, so a whole-row write would rewrite cells nobody edited, a formula cell among them coming back as its displayed value. A save that changes nothing writes nothing, logs no audit line and answers `{ success: true, updatedCells: 0, unchanged: true }`. A row that cannot be read is 409 `ROW_READ_FAILED` on any tab. **An optional `baseline`** (the row as the caller's form opened it, an array the length of `values`): a cell sent equal to its baseline was not edited, so it is set to the row as read and not written, even when the sheet changed under a stale view (the Active Loads editor's can be ~60 s old: another user, n8n, or a formula's shown value). It is applied right after the row read (`restoreUntouchedCells()`), so the Owner ID check, the broker restore, the formula refusal, the period guard and the audit all judge the row as it will be written. The Active Loads editor sends one; the Data Manager and API callers send none, and a missing or malformed baseline is ignored. **With a baseline, a row that no longer holds the load the form opened is 409 `ROW_MOVED`** (2026-09-27). A row number is a position, so after a sort or a row deleted above it the editor's number can hold another load, and the restore sets the Load ID cell (never edited) to the row as read. So on Job Tracking, before the baseline is applied, `rowMovedRefusal()` compares the baseline's Load ID with the row as read using `normalizeLoadId()`, the key the `DUPLICATE_LOAD` check uses. A different load, or a Load ID blank on either side, is refused with nothing written: the body names `expectedLoadId` and `foundLoadId`, the refusal is audited as `update_sheet_row_blocked` `[ROW_MOVED]` with the form's edits, and the Job Tracking cache is dropped so a reloaded dashboard shows each load on its current row. Other tabs, a layout with no load-id column, and a save with no usable baseline are judged as before (without a baseline, the opened load's id reaches the `DUPLICATE_LOAD` check when that load is on another row). `scripts/test-row-save-cell-writes.js`.
- `DELETE /api/data/:rowIndex?sheet=` — delete row (shifts rows up, Super Admin only)

**Broker contact columns are withheld from every role but Super Admin** (owner, 2026-09-26). Every Job Tracking column matching `BROKER_WITHHELD_RE` (`resolveBrokerWithheldColumns()`; on production "Broker Contact Name", "Phone Number" and "Email") is served blank by `sanitizeBrokerColumns()`, whatever the cell's format, JSON contact cells included, from `GET /api/dashboard`, `GET /api/driver/:driverName` and `GET`/`PUT /api/load/:loadId`. For every caller but a Super Admin, `PUT /api/data/:rowIndex` and `PUT /api/load/:loadId`:
- keep every withheld column exactly as stored, whatever the request sent (`restoreWithheldBrokerCells()`), so the save never writes it; the response names none of them. An empty stored cell stays empty.
- refuse a CHANGED cell whose trimmed value starts with `=` with **400 `FORMULA_NOT_ALLOWED`**, `field` being the column's header exactly as the sheet holds it, before anything is written (`formulaCellRefusal()`). Both write with `valueInputOption: "USER_ENTERED"`, which stores such a value as a formula. A cell equal to its stored value is never refused, so a stored value that starts with `=` does not block an unrelated edit.

The same formula rule, `formulaCellRefusal()` with an empty stored row where the row is new, holds on the other routes that write a non-Super-Admin's text into a sheet: `POST /api/loads/from-ratecon` (every field it writes, before the load is claimed or a sheet is read, then every cell as written to its three tabs, before the first write) and `POST /api/dispatch` / `POST /api/dispatch/reassign` (the driver name, which is written as sent when it names no Driver account). The other sheet writers open to a non-Super-Admin write only constants, a status from `STATUS_OVERRIDE_ALLOWED` or server timestamps: `POST /api/driver/respond`, `PUT /api/driver/status`, `PUT /api/loads/:loadId/status-override`, the POD flag of `POST /api/documents/upload`, and the geofence advance.

`ActiveLoadsTab.vue` mirrors the regex and shows the withheld columns read-only. `scripts/test-broker-column-redaction.js` runs both PUTs and the `GET` and `POST /api/data` gates; `scripts/test-sheet-formula-doors.js` runs from-ratecon, dispatch and reassign.

- `/api/trucks` — CRUD for trucks (GET, POST, PUT, DELETE)
  - **Truck amounts are finite and in range.** `POST` and `PUT /api/trucks/:id` read the five fixed costs, `purchase_price`, `maintenance_fund_monthly`, `fuel_tank_gallons` and `avg_mpg` through one parser (`parseTruckAmount()`) and one table (`TRUCK_AMOUNT_FIELDS`): a finite number from 0 to 1,000,000 (`TRUCK_AMOUNT_MAX`), and a blank (`null`, `""`, whitespace) is 0, except that for the fuel pair a `null` snake_case key falls back to the camelCase key and, if that is not sent either, counts as not sent. Anything else refuses the whole request with **400 `INVALID_AMOUNT`** (`field` names the column) before the month-end lock is asked and before any write, so the lock and the write see the same parsed values. The driver's daily rate keeps its own rule. `scripts/test-truck-cost-amounts.js`.

It never reads them, so nothing in them can refuse the add. `fixed` still means "a fixed cost `truckMonthlyFixed()` reads"; the month-end lock and the cost audit key on it.

Anything else is the same **400 `INVALID_AMOUNT`** with `field: "admin_fee_pct"`, before the lock and any write. `PUT` checks it whenever it is sent. `POST` checks it only for a Super Admin or a Dispatcher; an Investor's add keeps 50 and is never refused over it.

It keys on a change, never on presence: the Trucks page sends only the fields that changed, but an older page or a direct API caller may still send the whole row. The line names each change and, when a fixed cost moved, the monthly fixed-cost total before and after. The fuel tank and MPG keep their own lines. Its field list is the `TRUCK_AMOUNT_FIELDS` rows carrying a `per` (`"/mo"`, `"/yr"`, or `""` for the purchase price), in table order, plus the admin fee; `scripts/test-truck-edit-audit-coverage.js` fails if any of the eight columns drops out of it.

A unit number that is not text, is blank, holds a character of the Unicode classes Cc, Cf, Zl or Zp (controls, text-direction and zero-width characters, U+2028 and U+2029), is longer than 50 characters once trimmed, or starts with =, +, - or @ (dispatch copies it into Job Tracking's Truck column, where those characters begin a formula) is refused with **400 `INVALID_UNIT_NUMBER`**, `field: "unitNumber"`, before any write, a non-string or a blank sent to the `PUT` included. (The `PUT` reads the truck first, so an unknown id is answered 404 whatever the unit number.) Every truck audit line and refusal (`create_truck`, the `update_truck_*` and `update_driver_pay` lines, `delete_truck`, `routemate_link` / `unlink` and their `*_blocked` rows) names the unit number through `auditText(…, 100)`, which drops the same characters (and turns newlines, tabs, U+2028 and U+2029 into a space) before its purge-marker scrub.
  - **`PUT /api/trucks/:id` awaits once, before its guards read the row.** The only await is the active-load check, which runs right after the input checks (a refused amount, date, unit number or photo never waits on it). The route then reads the truck again, and from that read to its last write nothing is awaited: the photo decision, the date cross-check, `changed`, the month-end lock, the case-insensitive unit-number check and the audit "before" values all read the row as re-read. The driver assignment and the `UPDATE` are written in one transaction, and a unit number another writer took anyway (the column's `UNIQUE` is case-sensitive; `isUnitNumberTaken()`) is the same 400 "Unit number already exists", with neither written. `POST` writes its `INSERT` and the driver assignment in one transaction too, so an assignment that fails leaves no truck behind for a retry to meet as "Unit number already exists", and it maps the `UNIQUE` the same way. **Driver pay settings are Super Admin only** (owner decision, 2026-09-24). Pay lives in `drivers_directory.pay_type` / `pay_percentage` / `pay_daily` and `trucks.driver_pay_daily` — the two inputs `resolveDailyRate()` reads. `POST`/`PUT /api/drivers-directory` and `PUT /api/trucks/:id` also admit a Dispatcher, and `POST /api/trucks` an Investor, for every other column, so the rule is per field:
- A request from anyone but a Super Admin that would **change** a pay value is refused whole: **403 `PAY_EDIT_ADMIN_ONLY`** with `fields` (the columns it would change) and a message naming each change. Nothing is written — on a truck save that also reassigns the driver, not the assignment either.
- **Change, not presence.** The Drivers Database form sends the whole row; the Trucks page sends only the fields that changed, but an older page or a direct API caller may still send the whole truck row. Either way, resending the stored value is not a change. The directory compares as the money math reads each column (`directoryPayStruct()`: `"300"`, `300.0` and a legacy `"Fixed"` are the stored value); a truck compares through the route's own `changed` diff. On a create the stored value is the default: fixed / 0 % / $0 (the truck's rate applies) for a directory row, $0 (the $250 fallback) for a truck.
- **A rename can be a pay change.** The pay paths find a driver's terms by the directory row's name, so the stored name of a row that carries terms of its own is part of those terms: `PUT /api/drivers-directory/:id` refuses anyone but a Super Admin any change to it — a respelling in case or spacing included — the same way (`fields: ["driver_name"]`), and a save that resends it (padded or not) writes it back exactly as stored. A row on the default terms prices a driver exactly as no row does, so it is renamed as before.
- **Out of scope, deliberately:** which truck a driver is assigned to. For a driver with no `pay_daily` of their own, a reassignment changes which truck rate applies, but assignment is dispatch's job and keeps its current gate.
- A sent directory daily rate is held to the truck routes' cap, 0–`DRIVER_PAY_DAILY_MAX`, for every role: **400 `INVALID_PAY`** otherwise (`"Infinity"` and `1e308` included). Both directory pay fields (`PayDaily`, `PayPercentage`) are read through `parsePlainDecimal()`, not `parseFloat`: a value that is not a plain decimal (`"12abc"`, `"0x10"`, whitespace only) is **400 `INVALID_PAY`** too, and nothing is written.
- The check runs before the route's month-end lock (reopening a month would not make the edit allowed) and before its first write. A save that passes it still never writes its own pay values unless it comes from a Super Admin. `PUT /api/drivers-directory/:id` writes the stored pay columns back exactly as they are, so a legacy `"Fixed"` is not rewritten as `"fixed"` (with an `update_driver_pay` line to match) under an account that may not change pay. `PUT /api/trucks/:id` asks the pay check about the row as first read — the rate the caller's form loaded — and can yield in its active-load check after it, so it writes `driver_pay_daily = driver_pay_daily` rather than the rate the save carried: a Super Admin's rate change that lands in that window is kept, and the save names no pay change of its own (no `update_driver_pay` line, and the month-end lock is not asked about the rate).
- Every refusal is audited as **`pay_edit_blocked`** (entity `driver` or `truck`; the detail names the attempted change and `[PAY_EDIT_ADMIN_ONLY]`) through `logAuditRefusal()`, so repeats from one account coalesce to a row a minute. It is not on `PURGEABLE_REFUSAL_ACTIONS`.
- The client shows pay read-only to everyone else (`canEditPay`, from `TrucksView` and `DriversDbView`). Their saves leave the rate out (`TruckTable`), send the $0 default (`AddTruckForm`), or send the terms blank, which the server reads as "not sent" (`DriverTable`, `AddDriverForm`). A 403 reaches the user through the views' existing error toast.
- Pinned by `scripts/test-pay-settings-admin-only.js`, which runs the four shipped handlers against an in-memory database (period locks and the active-load check stubbed) and catches a mutant of each check: removed, keyed on presence, role test inverted.

The same checks apply: `…/sign/:docKey` (400 `INVALID_FIELD` / `INVALID_VEHICLES`, 413 / 415 on the signature image), `…/vehicles` (`INVALID_VEHICLES`) and `…/banking` (`INVALID_FIELD`); the anonymous `POST /api/public/investor-preview-pdf/:docKey` checks its signature image and vehicles before it renders anything.

- `GET /api/driver/me/identity-file/:fileType` and `GET /api/driver/me/truck-photo` serve a stored file only as what its bytes are — a JPEG, PNG or WebP, plus a PDF for an identity file — under `X-Content-Type-Options: nosniff`, and answer 404 for anything else, a malformed value included; the media type stored with the file is never read (`storedFileForServing()`). An identity file that is a PDF is sent as a download, `Content-Disposition: attachment`, under the name the Driver Kit's `<a download>` already gives it: `CDL-Front.pdf`, `CDL-Back.pdf` or `Medical-Card.pdf`. A header filename overrides that attribute, so the two must match; the runner reads DriverKit.vue's labels and its naming rule, and fails when they differ. An image stays inline, because the Driver Kit shows it as a CSS background. An identity file is sent `Cache-Control: private, no-store`, so the browser does not keep it, and a truck photo `private, no-cache` with an `ETag` taken from the stored value (`storedFileETag()`, the quoted first 32 hex digits of its SHA-256), so the browser revalidates it with the server on every use and a request whose `If-None-Match` names that ETag is answered **304** with no body (`ifNoneMatchIncludes()`). A truck photo that `POST /api/trucks` (Super Admin, Dispatcher; an Investor's is ignored) or `PUT /api/trucks/:id` would store must be such an image, within `LIMITS.TRUCK_PHOTO` (16 MP, 2 MiB), or the request is refused before anything is written: **413 `IMAGE_TOO_LARGE`** / **415 `UNSUPPORTED_IMAGE_TYPE`**, `field: "photo"`. What is stored is its canonical form (`truckPhotoForStorage()`): the label the bytes earn and the base64 re-encoded, so the stored value is exactly what the route serves. The PUT checks and normalizes a photo only when it CHANGES: the Trucks page sends the photo only when it changed, but an older page or a direct API caller may still resend the stored photo on every save; a resend is written back as stored, and `""` or `null` clears it. `scripts/test-stored-file-serving.js`. `GET /api/driver/:driverName` says which of these files exist by the same rule, from the bytes: `truck.has_photo` is 1 when the truck-photo route would serve the stored photo, judged from the stored value's first 200 characters, which are not returned. It reads only those, so a legacy value whose `data:` header runs long enough to push the payload's first bytes past them reads as no photo although the route would serve it (a photo stored in canonical form never does). And `application.cdl_front_type` / `cdl_back_type` / `medical_card_type` are `"pdf"`, `"image"` or `null` as the identity-file route would serve each (`storedFileKind()`, which decodes only the first 64 base64 characters: `servedType()` needs 12 bytes).

**Investor payout ledger** (settlement layer over `/api/investor` earnings; table `investor_payouts`, one row per `(owner_id, period)`):
- `GET /api/investor/payouts?as_user_id=N` — one investor's ledger. `GET /api/payouts` — Super Admin fleet-wide console (`/payouts` view), summing every investor into `monthlyTotals` + `grandTotals`. Both run the **same** `reconcileInvestorPayouts()`, which idempotently UPSERTs a row per completed past month and refreshes `amount` **only while the row is still `owed`** — a settled row's figure is frozen.
- `POST /api/investor/payouts/:id/status` — Super Admin moves a payout **either direction**: forward `owed → processing → paid` (`owed → paid` allowed), or backward ("reopen") `paid → processing → owed` (`paid → owed` allowed). A reopen **requires `reason`** (400 without one), clears the stamps it undoes (leaving `paid` nulls `paid_at`/`paid_by`; going to `owed` also nulls `processed_at`/`processed_by`), and records `reopened_at`/`reopened_by`/`reopen_reason` on the row plus a `REOPENED …` line in `audit_trail`. Reopening is exempt from the "$0 is not settleable" guard, which still blocks forward moves. Same-status transitions 409. **Reopening to `owed` re-links the row to live earnings** so the next reconcile refreshes its amount; reopening to `processing` keeps it frozen.
- `PUT /api/investor/payouts/:id/adjust` — signed correction on **any** period including a settled one (late receipts). Capped at ±$10,000, can never invert a payout below $0. Effective payout = `amount + adjustment`; the reconcile only writes `amount`, so adjustments survive recomputes.
- UI (`client/src/views/PayoutsView.vue`): `owed` rows offer Mark Processing / Mark Paid, settled rows offer Reopen / Adjust. **"Mark Paid" is confirm-gated** — it is the only status asserting money actually moved, and an unguarded click once booked $8,703 as paid that was never sent. Reopened rows carry a `reopened` badge with the reason on hover.

**Month-end close** (`PERIOD_FINALIZE_ENABLED`, default off — ships dormant). Client ask: stop hand-adjusting a prior month every time a late receipt lands. A work month now runs `accruing` → `pending` (books open `settlement_grace_days`, default 7, past month end) → `finalized` (frozen; statement published). Table `period_locks` (one row per closed month, **fleet-wide** — one carrier, one month-end; a per-investor lock is incoherent because the super-admin branch of the monthly math sums all expenses with no owner scope). Presence of a `status='locked'` row *is* the lock; `'reopened'` keeps the row so the per-minute sweep can't re-lock what an admin just reopened. No new `investor_payouts.status` value, so **no CHECK rebuild and no forced re-login** — the phase is the pair `(status, locked(period))`.
- **Three legs, all required.** *Lock*: the reconcile's refresh guard becomes `status='owed' && !finalized_at && !isLocked(period)`, which freezes the figure against **all six** drift sources (sheet revenue, driver pay, `trucks.status='Active'` fixed costs, live-read split %, maint/compliance, trip expenses) — not just expenses. *Document*: `finalized_breakdown` JSON snapshot so the statement prints the composition as of close instead of a live recompute. *Posting rule*: `expenses.posted_period` — a receipt whose own month is already finalized books to the **current open month** (prior-period adjustment) while `date` keeps the true purchase date. Legs 1+2 without 3 lose the money; 3 without 1+2 leaks through five other doors.
- **`EXPENSE_PERIOD_EXPR`** (beside `EXPENSE_PNL_FILTER`) is the single source of truth for *which month* an expense counts in. The rule: **settlement basis uses it; operational basis keeps plain `date`.** Applied at 8 sites — incl. `getDeductibleExpensesByDriverMonth()`, whose `substr(date,1,7)` is invisible to a grep for `strftime('%Y-%m'` and drives percentage-driver pay at three call sites. Deliberately *not* applied to the weekly invoice week, fuel CPM, IFTA, or expense trend charts.
- **Scheduled sweep**, not a lazy read-path close (ported from the invoice-autogen batch): a lazy close freezes whatever value is present on the first page load after day 7, so a day-9 receipt lands inside a "final" number and two investors finalize at different values depending on who logged in first. `finalizePeriods()` takes every due lock first (pure clock math, cannot fail), then reconciles **once per investor** and stamps across all periods. Stamps `recomputedAmount`, **not** `amount` — `amount` only refreshes on a page GET, so freezing it would lose receipts that landed while nobody was looking.
- Guards, all inert when the flag is off: forward settle (409 `PERIOD_NOT_FINALIZED`, reopen exempt), adjust (closes a hole the UI was faking client-side; a finalized-but-unpaid row *is* adjustable), statement (**finalized OR paid** — monotone, so legacy paid months stay printable), and expense status flips (`PUT /api/expenses/:id/status` + `/bulk-status`, which could otherwise move three closed months while clearing a backlog; bulk skips locked rows and names the periods rather than failing wholesale).
- `POST /api/periods/:period/finalize` (close early) and `/reopen` (**requires `reason`**; re-links only `status='owed'` rows — a paid row keeps its snapshot because its statement already went out; returns the count of receipts redirected away, which reopening does **not** pull back). `GET /api/periods` is the close calendar.
- **`lib/payout-statement.js` is dual-mode.** Statements now publish at finalization, i.e. possibly before money moves, so the doc keys on `paidAt`: FINAL prints "Final Amount", the finalized/due dates, and "not a receipt"; PAID is unchanged. Shipping without this mails investors a PDF saying they were paid when they weren't.
- Rollout: deploy flag-off (ledger byte-identical), then enable — a baseline seed locks every period whose window already passed, so nothing is retroactively reopened and a month still inside its window closes naturally.

**Invoices**:
- `POST /api/invoices/generate` — weekly (Sat–Fri) invoice PDF from completed loads. Fixed-driver pay uses the completed-loads ∩ ELD-travel active-day basis (see [`driver-active-days.md`](driver-active-days.md)), clipped to the billing week, at the daily rate `resolveDailyRate()` picks (the driver's `pay_daily`, else the truck's `driver_pay_daily`, else a $250 legacy fallback); soft-deleted loads are filtered out. Owner-op/percentage drivers bill `(week revenue − fuel/maintenance) × pct` instead. The handler is the named `generateInvoiceHandler(req, res)` so the auto-gen batch (below) can invoke the **same** pay math in-process — one source of truth. **Which loads a week bills is `selectInvoiceWeekLoads()` / `invoiceWeekVerdict()`** (fixed 2026-09-23, locked by `scripts/test-invoice-week-selection.js`): a completed row belongs to the week of its **Status Update Date**, else its **Completion Date**; ⚠️ a row with **neither is billed in no week** — it used to be billed in *every* week, harmless to day-rate pay (the window clips to $0) but a load's full revenue, weekly, for a percentage driver — and is reported in the response's `warnings` (plus `undatedInWeek` when its pickup/drop-off falls in the billing week). The Drop-off Appointment is deliberately **not** a fallback (scheduled, hand-typed, often wrong). Loads are de-duplicated, and matched against `deleted_loads`, on `normalizeLoadId()` — `#X` and `X` are one load. A Job Tracking sheet with no completion-date column answers **500 `INVOICE_WEEK_DATE_UNRESOLVED`** (the batch reports it as an error) instead of billing every completed load ever.
- **One driver, one week, one number, one PDF** (2026-09-24, locked by `scripts/test-invoice-driver-name-matching.js`). Every driver comparison on the weekly path — the existing-invoice check, the number's sequence, the pay lookups, the expenses, the payee's account and directory row, the batch roster, `GET /api/invoices`, the driver app's list, restore's one-per-week check, the approve email and the payment report — goes through `normalizeDriverName()`, so one driver in two spellings (the account's, a directory row re-spelled by spacing, a typed one) is one driver. The pay structure and daily rate are the P&L's own: `getDriverPayStructures()[normalizeDriverName(name)]` and the **last** truck naming the driver (the `trucksByDriver` loop: last wins, `|| 250`). A new row stores `canonicalDriverName()` lowercased; stored rows keep their spelling. ⚠️ `idx_invoices_driver_week` folds case but **not spacing**, so the application holds the rule: generate answers **409 `INVOICE_EXISTS`** (a settled invoice for the week in any spelling) or **409 `INVOICE_WEEK_DUPLICATE`** (two live Drafts — a human picks), and `generateInvoiceNumber()` mints the first number of the driver's sequence that **no row** — any status, soft-deleted or manual, any driver — holds as a number or as a PDF name, case-insensitively (two drivers with the same initials share every other part of a number). The row, its PDF and the Draft it replaces are written together by `commitInvoiceWithPdf()` after the render: a temporary file, then one IMMEDIATE transaction that re-checks the number, the file name, the driver-week and the Draft (still a Draft, same adjustment), deletes the Draft, INSERTs and renames the file into place last. A refusal writes nothing — **409 `INVOICE_NUMBER_TAKEN`** / **409 `INVOICE_WEEK_CHANGED`**, both meaning "generate again" — and a failed render or INSERT leaves the Draft and every file as they were. A regenerated Draft keeps its number. `POST /api/invoices/manual` mints `INV-M-` numbers through the same allocator and writes through the same helper. The adjust route's re-render refuses a PDF file another row also names, and after its render re-checks the row (`assertInvoiceFileStillOwn()`) before replacing the file in one step: an invoice regenerated, re-adjusted or deleted meanwhile answers 409 with nothing written, and the rollback undoes only that request's own adjustment.
- **Auto-invoice batch** (`INVOICE_AUTOGEN_ENABLED`, default off): a per-minute `setInterval` fires once the current week's **Friday 7:00 PM America/Chicago** — after the 6:30 PM driver cutoff, the two are a pair (DST-aware via `Intl`, `mostRecentInvoiceFridayCT()`) — has passed, then loops every `drivers_directory` driver — one call per `normalizeDriverName()`, so two directory rows spelled apart are one driver — runs `generateInvoiceHandler` in-process (mock req/res, system actor), and **auto-submits** each fresh Draft → `Submitted` (drivers kept forgetting to submit; approval stays manual). Only a **409 `INVOICE_EXISTS`** counts the driver as billed; any other 409 is an error and leaves the driver unbilled. Idempotent per week via the `invoice_autogen_runs` marker (keyed on the billing Friday); a boot-time run covers a restart across the trigger; first-enable seeds a baseline so it never retroactively bills a pre-feature week. It pre-reads the sheet once and **aborts without a marker** if empty (never closes a payroll week on a transient Sheets glitch), cross-checks that every driver who worked got billed — `driversWithCompletedLoadsInWeek()` asks the handler's own `invoiceWeekVerdict()`, so "worked" and "billed" cannot drift (worked-but-unbilled → bounded throttled retry, then an ACTION-NEEDED alert) — escalates any completed load scheduled in the week that has **no completion date**, for drivers on the roster and off it (ACTION NEEDED, never retried: a retry cannot supply a date; one whose appointments are also blank or unreadable is reported once by the undated-load alert below), and sends **one** batch summary (dispatch notification + email to `GMAIL_USER`) instead of N per-invoice submit emails.
- **Undated-load alert** (2026-09-23; `INVOICE_UNDATED_ALERT_ENABLED` — a kill switch, default ON — and inert unless `INVOICE_AUTOGEN_ENABLED` is on). `listUndatedCompletedLoads()` finds every completed load with neither a Status Update Date nor a Completion Date — billed in no week — and the `invoice_undated_alerts` ledger (keyed on `normalizeLoadId()`) reports each one **once**: after each Friday batch, one digest (email + dispatch notification) of the loads that are new or re-opened, leaving out those the batch summary already named (`undatedInWeek`). A digest names at most 25 loads (a rolling 24 h cap, so 25 per weekly run); the rest wait for the next run. **History stays silent:** the first run records every completed load of the day with `seeded_at` (undated ones open, dated ones closed) and marks a baseline in `server_state` — production seeded 160 open and 155 dated rows on 2026-09-23 — and a seeded load never reports. A load that gains a date, is soft-deleted or stops being completed is resolved, and re-opens (keeping `first_seen`) if it comes back. ⚠️ **A sheet that shrank is not a sheet that got fixed:** a run that would resolve more than min(20, 25% of the open rows), never fewer than 5, resolves and reports nothing until the same shrink is still there 24 h later. Observe-only — it writes no invoice, payroll marker or retry, and the batch's result never depends on it; its last outcome is kept in `server_state`. `scripts/test-invoice-week-selection.js`.
- `GET /api/invoices`, `GET /api/invoices/:id/pdf` — list and download invoices. **Super Admin, or the owning Driver — nothing else** (tightened 2026-08-09, issue #228). ⚠️ That rule, and the matching one on `PUT :id/submit` and `POST /api/invoices/generate`, is enforced **inside the handler**, not in the mount — it depends on the row, which middleware cannot express. A `requireAuth`-only mount here is not a missing gate; audited and confirmed 2026-08-19. `generate` keeps its rule in the same place — **Super Admin, or a Driver for themselves; every other role is refused** (since 2026-09-23) — because a Draft carries the driver's address, phone and bank name; `scripts/test-invoice-week-selection.js` §4a executes the gate and carries the mutant.
- `PUT /api/invoices/:id/submit` — submit an invoice. Same rule: **Super Admin or the owning Driver.** The gate is `role !== "Super Admin" && !driverOwnsInvoice(...)` (issue #228; it replaced a check that looked only at `role === "Driver"`), which needs no role list because `driverOwnsInvoice()` refuses a blank session `driverName` and neither role carries one. This aligns the detail routes with `GET /api/invoices`, whose non-Super-Admin branch lists exactly the rows `driverOwnsInvoice()` grants (since 2026-09-24; it used to scope to `LOWER(driver) = <own name>`) and therefore hands both roles zero rows; the SPA `/invoices` view is `meta.roles: ['Super Admin']` and the driver app shows a driver only their own, so no surface loses anything. Production: **0 of 4** non-Driver accounts (1 Dispatcher, 3 Investors) carry a `driver_name`, so no account lost anything its UI offered. Investor scoping via `getInvestorDriverSet()` was considered and **rejected** — it needs live Carrier Database sheet rows to be complete, so an authorization decision resting on it fails **open** for the truck-linked subset and closed for the rest depending on whether a sheet read succeeded. **⚠️ `test-suite.js` exercises neither route** (it only calls `GET /api/invoices`), so a regression here is silent.

**`poiStopsCache` — the Places fan-out cache (the actual cost control).** This endpoint shipped with a cost asymmetry: `getRoute()` was cached 15 min (`ROUTE_CACHE_TTL`) but the *expensive* half was not, so the cheap Routes call was memoized while the 4–8 billed Places calls were re-issued on every request, including repeat polls of a load whose route hadn't moved. `poiStopsCache` (Map + TTL + FIFO cap, mirroring `trackResponseCache`, 15 min TTL aligned to `ROUTE_CACHE_TTL` so both halves expire together, 200 entries) sits **after** coordinate resolution and **after** the Driver ownership check, so a hit can never bypass authorization. Responses carry `cached: <bool>` as an ops/QA signal for whether the request billed Google.
- **Keyed on the resolved coordinates**, rounded to 3 decimals (~111 m) exactly like `routeCacheKey()` — *not* on the query string or the raw `loadId`. So `?loadId=%23123` and `?loadId=123` land on the same `load_coordinates` row → same coords → same entry; two loads on the same lane share one fan-out; dispatch's raw-coordinate form reuses a driver's cached lane; and re-geocoding a load moves its key automatically, so there is no stale route and no invalidation hook to maintain.
- **`limit` is not part of the key and never refetches.** The fill always requests `POI_FETCH_CAP` (25) and the handler slices on read. This is **billing-neutral**: `limit` only feeds `maxResultCount` per call, while the billed call count is the waypoint count — `clamp(ceil(routeMiles/75), 4, 8)` — which `limit` cannot influence. Consequence worth knowing: the returned set is now the *N genuinely cheapest* rather than the lib's internal top-N re-sorted, which matches the endpoint's stated cheapest-first contract. `cheapest` is stable across limits (the global cheapest sorts to index 0); `livePriceCount` describes the returned slice, so it stays consistent with `stops`.
- **Empty results are deliberately NOT cached.** `findFuelStopsAlongRoute()` degrades a failed waypoint to `[]` silently, so an empty array is ambiguous between "no truck stops on this lane" and "Places was briefly down" — caching the latter would pin a blip into a 15-minute outage for that lane.

## Socket.IO events

**Who may connect, how much a client may send, and the rooms** (2026-09-24). `scripts/test-socket-hardening.js`.
- **Origin.** A live-update handshake gets the HTTP guards' own judgement of origin, per request: an `Origin` that is present must be the app's own, by `originIsSelf()` (over `Host`, and `X-Forwarded-Host` under `trust proxy`) and then `originHostIsExact()`, which holds the port to it too; while the session cookie is Secure (production) it must also be HTTPS. A `DRIVER_MOBILE_ORIGINS` entry passes. Anything else, `Origin: null` included, is refused before any namespace sees the connection: **403** on long-polling, **400** on a WebSocket upgrade, message `CROSS_SITE_REFUSED`. No `Origin` passes (a same-origin long-polling GET sends none) unless `Sec-Fetch-Site` is present and not `same-origin`. JSONP long-polling (a `j` query parameter) is always refused. It is Engine.IO's `allowRequest`, `liveUpdateHandshakeAllowed()` beside `crossSiteGuard`, and refusals are logged once a minute with a running total. The Vite dev proxy passes: it keeps the browser's `Host` on `/socket.io`. ⚠️ The nginx location serving `/socket.io` must forward `Host` (or `X-Forwarded-Host`), or every browser handshake is refused; the log line names the Host it saw.
- **Size.** A client message is capped at **16 KB** (`SOCKET_MAX_MESSAGE_BYTES`, Engine.IO's `maxHttpBufferSize`, whose default is 1 MB). A WebSocket message over it closes that connection; a long-polling request body over it is answered 413, and the client drops the connection. Clients send only `register` and the tracker's `subscribe` / `unsubscribe`, a few hundred bytes at most; chat and uploads go over HTTP, and what the server sends is not limited.
- **Rooms.** Role rooms are the literals `dispatch` (Super Admin, Dispatcher) and `investor`. Identity rooms are `driver:<driver name>` (`driverRoom()`) and `user:<username>` (`userRoom()`), trimmed and lower-cased, and every join and emit names a person only through them, so no name can equal a role room or the other kind of identity. `register` joins the role's room and the caller's own identity rooms, from the session; the name it carries adds only the caller's own driver or user room, and a payload that is not a string counts as no name. Chat goes to `chatRooms(from, to)`: the dispatch room, which sees every message, plus each party's driver and user rooms (the desk's own name, "Dispatch", adds none), once per socket. No value in a request can name a role room or another kind's room.
- **Handler faults are contained.** Every socket event listener in both namespaces is wrapped in `socketHandler(event, fn)`: a synchronous throw (or a rejected promise from an async handler) is caught, logged once a minute per event, and dropped — the connection stays up and the process is never ended by one event. The public tracker also accepts a load id only when it is a string; any other `subscribe` / `unsubscribe` payload is ignored, the same as an id that fails `LOAD_ID_RE`.

**Socket.IO events** (server emits):
- `load-assigned` — to specific driver when dispatched
- `load-cancelled` — to driver when dispatch cancelled
- `load-accepted` / `load-declined` — to dispatch room on driver response
- `status-updated` — to dispatch room on load status change
- `dispatch-notification` — to dispatch room for all dispatch events. Its `type` names the event (`load-assigned`, `load-deleted`, `status-updated`, `eld-feed-silent`, …) — a soft delete is announced only this way, never as an event of its own. `metadata` JSON includes `loadId` for every load emitter (drives the NotificationsView click-routing under Key Conventions in the root `CLAUDE.md`); system alerts carry none.
- `new-message` — to `chatRooms(from, to)`: the dispatch room and each party's rooms, once per socket
- `pod-uploaded` — to dispatch room on document upload. Carries the document's `driveUrl`, except for a rate con (`isRateConDocType()`), which is Super Admin only while the room also holds Dispatchers
- `location-update` — to dispatch room and the driver's own room, on each ELD position (the Routemate poller and the Linxup webhook)
- `geofence-trigger` — to driver and dispatch room when geofence auto-triggers status
- `new-load` — to dispatch room when a load is ingested; emitted from **both** paths (n8n webhook and the drag-and-drop `from-ratecon` route), which is part of keeping the two in lockstep
- `fuel-low` — to the **driver's own room** (`driver:<name>`) on a low-fuel episode. Throttled per vehicle and latched so one episode is one alert, not one per ~15 s ping. Gated by `FUEL_LOW_ALERT_ENABLED`, which is a **kill switch — default ON**
- `tracker-update` — to the public-tracker namespace room `load:<activeLoadId>`, feeding the customer-facing tracker (emitted by the Routemate poller only — a known gap for Linxup-tracked loads, see [`linxup.md`](linxup.md))
- `reload` — to all 500ms after server start (live reload during dev; it fires in production too, and only the legacy `public/` pages listen)
- `<domain>:changed` — from `notifyChange(domain)` (`dashboard`, `invoices`, `users`, `expenses`, `applications`, `trucks`, `investors`, `drivers`, `trailers`, `investor-applications`), to the dispatch room; for `trucks`, `expenses`, `invoices` and `investor` also to the `investor` room, with `investor:changed`. `useSocketRefresh()` consumers reload on these.

Clients emit `register` with their name to join a socket room. The server refuses a socket whose handshake carried no session (closing its namespace only; see below), picks rooms from the session's role, honors the requested name only when it is the user's own, and joins a session that must change its password to no room at all.

**A live-update socket ends with its session** (2026-09-23). A socket reads its session once, at the handshake, and used to keep the rooms it earned after the session ended. Now each socket records `socket.data = { sid, userId }` at connection, and the helpers walk `io.of("/").sockets` instead of joining `sid:` / `user:` rooms (those would share the namespace with the name rooms `register` joins):
- `disconnectSessionSockets(sid)` runs before logout destroys a session and before login, setup, change-password and `refreshOwnSession()` (a self-edit of the caller's own role, driver name or password) regenerate one. `purgeUserSessions()` is the path for a role change, password reset or driver rename (`PUT /api/users/:id` and `PUT /api/admin/fix-driver-name`), a delete, and change-password. It first ends the user's sockets on every other session (`disconnectUserSockets()`).
- The connection handler refuses a socket whose session is no longer in the store (fails **closed**), and `sweepSessionlessSockets()` closes, once a minute, any socket whose session the store no longer returns — expiry, or a script that clears `sessions` — failing **open** when the store cannot be read, so a read error never drops the whole fleet.
- Every close is namespace-level `socket.disconnect()`, never `disconnect(true)`: the helpers and both refusals in the connection handler. One socket.io-client Manager carries every namespace a page opens on this origin, so a tab holding the live-update socket and the public tracker shares one transport. `disconnect(true)` closes that transport, and first sends every namespace on it a server disconnect, which socket.io-client never retries. (No tab holds both today: every in-app route to `/track/:loadId` is a full page load, since dispatchers copy the link and the investor view opens a new tab, and nothing mounted on `/track` calls `useSocket()`.) The helpers are synchronous and never throw — they run inside the auth routes. `scripts/test-session-sockets.js`.
- A handshake that carried **no session user at all** is refused the same way; that branch called `disconnect(true)` until 2026-09-24. The refusal holds without closing the transport: the session was read once, at the handshake, so a CONNECT sent again over the same transport is refused again. A client with nothing else on the transport closes it itself once its last socket is gone (socket.io-client's Manager does). One that keeps it open holds no more than an anonymous `/public-track` connection already can: socket.io's 45 s `connectTimeout` stops as soon as an existing namespace admits a CONNECT, which for `/` happens before the gate runs.

## Rate limiting

Moved here from `CLAUDE.md` (2026-08-25) — it was reference material. The *reasoning* (per-user keying, `poiStopsCache` as the real cost control, `requireRole`-before-limiter ordering) followed on 2026-09-23 and is right below; the numbers are in the table after it.

**Rate limiting** (express-rate-limit, all `standardHeaders: true`, naming convention `{feature}Limiter`). **The per-limiter table is below** — `grep -oE 'const [a-zA-Z]+Limiter = ' server.js` for the current list. What matters here is *why* they are shaped the way they are:

- **⚠️ `poiLimiter` and `fuelPlanLimiter` are keyed PER USER, not per IP** (`u:<id>`, `ip:<ip>` fallback). IP keying was actively backwards: a dispatch office behind one NAT shared a single bucket while every driver on cellular got a fresh one — throttling the cheap callers and not the expensive ones. Note per-user keying *raises* the aggregate ceiling, which is why the cache below, not the limiter, is the real cost control.
- **⚠️ Mount `requireRole` BEFORE the limiter** on anything expensive (`fuelEventsLimiter`, `fuelGallonsLimiter` do this), or an unauthenticated caller spends the budget on 403s.
- **The unit of work sets the cap, not the traffic.** `fuelEventsLimiter` is 20/15min (~140 ms of local CPU per call); `fuelGallonsLimiter` is 6 (up to 25 **billed Gemini vision** requests per call). Same shape, three orders of magnitude apart.

All use `standardHeaders: true` and the `{feature}Limiter` naming convention. Every limiter defined in `server.js` has a row below. How many there are is deliberately not written down: list them with `grep -oE 'const [a-zA-Z]+Limiter = ' server.js` (append `| wc -l` to count them) and add a row for any name the table lacks. The first eleven rows carry the reasoning for limits that were set deliberately; the rest follow in `server.js` order. A limiter keys on the client IP (the default) unless its row says **per user** (`u:<id>`, falling back to the IP for a caller with no session); a split max is by the caller's role.
