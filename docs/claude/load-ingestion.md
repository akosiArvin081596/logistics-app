# Load ingestion — two paths, one shape
A load reaches Job Tracking two ways. **They must stay in lockstep** — a load that arrived one way has to be indistinguishable from one that arrived the other.

1. **Rate-con email (original, unattended).** `info@logisx.com` receives the rate con → a Gmail filter **stars** it + applies the **`RATECONs`** label → n8n "Dispatch v2 (Fixed)" (`ydFgTSFpKTyyZbXW`, see `Dispatch-v2-fixed.json`) fires → Drive upload, Gemini parse, dedupe, then writes **three tabs**. Blind spot: if the email never arrives, or arrives from a sender the filter doesn't match, there is **zero signal** — no execution, no alert, no row. **Two fixes shipped 2026-08-05 after two loads were lost in one day:** (a) n8n's `Validate Load ID` was a **Filter** node — one output, so a bad extraction was discarded with *no alert* while the execution still reported `success`; it is now an **If** node whose false branch feeds `Send Failure Alert` (same for `Critical Fields Complete?`, which silently dropped a written-but-rateless row). `Row Already Has Payment?`'s dead branch is **intentional** — it stops an existing payment being overwritten. (b) the reconciliation below, which catches the failure modes that produce no signal at all.

**Extraction runs in the APP, not n8n** (wired 2026-08-06). n8n's own chain was `LlamaParse (PDF→markdown) → Information Extractor`, two lossy steps that flatten the tables rate-con data lives in. Measured on the same PDF: n8n returned **`Load Number: null, Broker: null, Rate: null`** (while LlamaParse's quality gate reported `isValid: true` and pulled the word *"Confirmation"* as the load id) — the app returned every field. That failure lost load `562787563`. The workflow now goes `Merge Attachment + Email → Prep PDF Base64 (Code) → Extract via LogisX (HTTP) → Normalize Load Fields`, calling `POST /api/n8n/extract-pdf-via-gemini`, which already returned `{output:{…}}` in the Information-Extractor shape so **no downstream expressions changed**. A Code-node error with no error branch kills the whole execution (seen live), so every failure path must terminate somewhere. Auth uses **`N8N_EXTRACT_SECRET`**, never `N8N_WEBHOOK_SECRET` — the latter also gates `POST /api/webhook/new-load`, and n8n node parameters are plaintext in the workflow JSON.

**LlamaParse retired 2026-08-08** (54 → 45 nodes, applied live). The old fallback chain is gone: `Prep PDF Base64` and `Extract via LogisX` now route `onError` → **`Build Failure Context`** → `Send Failure Alert`, so a failure **alerts** instead of silently degrading. ⚠️ `Prep Thread PDF Item` fed `LlamaParse Upload` on its **main** output, not an error branch — the thread-sourced-PDF path (trigger email has no attachment, an earlier message in the thread does) was a *primary consumer*, so retiring LlamaParse without rerouting it to `Prep PDF Base64` would have killed that path outright.

**⚠️ Every Code node that emits items MUST set `pairedItem`.** This is what lost load `563593554`. C.H. Robinson sends the same confirmation **twice ~25 s apart**, so both land in one Gmail poll; `Prep PDF Base64` pushed objects with no `pairedItem`, which n8n tolerates at exactly ONE item (it assumes everything pairs to item 0) and not at two. The trace then breaks and every downstream `$('Node').item` throws — the sheet write threw, *and* `Send Failure Alert` threw on `$('Email Input').item`, so there was no row and no alert. Deterministic on any multi-email poll, not intermittent. `Extract via LogisX` had already returned the load correctly; n8n discarded it on item plumbing. `Build Failure Context` now resolves alert context in plain JS with try/catch so the alert path can never throw.

**⚠️ The errorWorkflow backstop was also dead**: "Dispatch v2 Error Alert" lives in the **personal** project while the main workflow lives in the **team** project `LogisX Dispatch`, and `callerPolicy: workflowsFromSameOwner` refuses that (`SubworkflowOperationError: current permissions do not allow this`). Both alert paths were down simultaneously; only `reconcileRateCons()` caught the gap, ~1h40m later.

**`Get Distance Matrix` held a plaintext Google Maps key and is DELETED** (applied live 2026-08-09, 45 → 43 nodes). It was a node nothing connected into — zero inbound edges, so it could never fire — feeding `Calculate RPM + Details`, which had no other inbound edge and an empty output. Post-flight, read back from the server: 43 nodes, still `active`, `settings.binaryMode` still `separate`, zero dangling connections, zero references to either node, `staticData["node:Gmail Trigger"]` cursor byte-identical (so no email was reprocessed), and **zero `AIzaSy` / `llx-` occurrences anywhere in the GET body**. The app has done this work since the drag-and-drop path shipped: `calculateRatePerMile()` in `lib/ratecon-load.js`.

**Distance runs in the APP too, not n8n** (wired 2026-08-09, 43 → 41 nodes). The live path was `Addresses Ready?` → **`AI Agent`** (Gemini + `Structured Output Parser`, **no tools** — `ai_tool` appears nowhere in the workflow) → `Update Job Details (Distance)` → `Update Job Tracking (Distance)`. Its prompt said *"Calculate the driving distance between the two locations"*, so it answered **from model memory**. Measured against real Distance Matrix on all 62 distinct production lanes (PR #226): **median error 20.5 mi (7.5%), p90 16.9%, max 224 mi, 32% of lanes off >10%**, median rate-per-mile error **$0.24/mi** (worst $1.41). It was **noise, not bias** — 23 of 28 repeated lanes answered differently each time, one lane asked 29 times spanned **680–840 mi**, and 74% of its answers were multiples of ten against 19% of Google's. A bias calibrates out with a constant; noise does not. The branch is now `Addresses Ready?` → **`Distance via LogisX`** (HTTP) → the two sheet nodes, calling `POST /api/n8n/load-distance`, which runs the **same** `calculateRatePerMile()` against the **same** Distance Matrix response as `POST /api/loads/from-ratecon`. One implementation, so the two ingestion paths agree again. The `AI Agent`, `Google Gemini Chat Model1` and `Structured Output Parser` nodes are deleted.

- **⚠️ THE TRAP, and why "just fix the mapping" was the wrong move.** The guessed numbers reached **no `Distance` or `Rate Per Mile` column**. Job Details' column A header is blank, so `Update Job Details (Distance)`'s `mappingMode: autoMapInputData` mapped the item's single top-level key — `output` — onto a column literally named **`output`**, dumping the whole JSON blob there as a string. Verified: 163 rows, `Distance` populated in **12**, `output` in **151**, **disjoint, zero overlap** (a clean partition; the 12 are the app's own drag-and-drop rows, and 5 of those are the degenerate `0 Miles` fallback). So the dollar impact was **zero by accident** — and it looked exactly like a one-line mapping bug. **Repairing that mapping while the LLM was still the source would have connected 151 guessed distances to the live figure.** Remove the source first.
- **⚠️ THE RESPONSE SHAPE IS THE FIX — never give this endpoint an `{output:{…}}` envelope.** Its sibling `/api/n8n/extract-pdf-via-gemini` answers that way because the Information-Extractor node it replaced did. Doing the same here **re-creates the trap verbatim**. `POST /api/n8n/load-distance` therefore returns a **flat** body whose top-level keys are exactly the Job Details column names (`Distance`, `Rate Per Mile`, `Details`, `Payment`, plus `Load ID` for parity), with everything else namespaced under `_meta`, which matches no column and is dropped. `Update Job Details (Distance)` is consequently **byte-identical to before** — autoMapInputData + appendOrUpdate + `matchingColumns:["Load ID"]` is the exact configuration proven across those 151 rows, and the fix is the *shape of the item*, not the node.
- The cells are formatted **server-side** (`${miles} Miles`, `$${rate_per_mile}`) so both paths write identical strings. The n8n node's own never-reached mapping would have written `486Miles`, no space — a format that lives in one place cannot drift.
- **A Maps outage is not an error.** The endpoint answers **200** with `0 Miles` / `Distance unavailable` / `measured:false`, the same honest zeros `calculateRatePerMile()` gives `from-ratecon`, so ingestion never stalls on Google. `onError: continueErrorOutput` → `Build Failure Context` fires only on a real HTTP failure (auth, rate limit, 5xx) — which is **better than before**, since the `AI Agent` had no error branch and simply killed the execution (seen live, execution 2450).
- **⚠️ But a Maps outage must NOT zero `Payment`, and that was a real blocker caught in security review.** `calculateRatePerMile()` computed `payment` *below* its early return, so any Google failure returned `payment: 0` for a rate the caller had supplied perfectly well. Latent while only `from-ratecon` called it; **live** the moment this endpoint fed the same figure to `autoMapInputData`, because top-level `Payment` makes n8n write a money column it had **never written before** (the old `{output:{…}}` item touched only `output`). `payment` is now parsed **above** the distance check — it is `parseFloat(rate)` and has nothing to do with Google — which also fixes the same latent zeroing on the drag-and-drop path. Verified: rate `$1,000.00` + unresolvable addresses → `Payment: 1000`, `Distance: "0 Miles"`.
- **The limiter is keyed on a VALID secret** (`n8nDistanceAuthorized()`, shared with the handler so the two cannot disagree), hashed, with a per-IP fallback. Per-IP alone does not bind the one caller it exists to bind — n8n Cloud's egress is shared and rotates — while keying on the *presented* value would hand an attacker a fresh 60-call bucket per invented string. Verified: invented secrets stay in the IP bucket; the real caller keeps its own.
- **⚠️ The 500-char address cap is a security control, not a UX choice.** `cityStateZip()` is super-linear in input length; the state/ZIP gap is `[\s,]*` and **not** `\s*,?\s*` because two adjacent `\s*` separated by an optional token is ambiguous, which made it ~cubic — measured 9.4 **seconds** of blocked event loop at 5,000 chars before the fix, 19 ms after. Do not raise the cap or re-introduce the ambiguity without re-measuring.
- **⚠️ `Update Job Tracking (Distance)` overwrites the COMMODITY `Details` with the route. CLIENT FIXED; the n8n half is STAGED, not applied.** `JOB DETAILS ENTRY` writes the rate-con's commodity text to Job Tracking `Details`, then this node replaces it with `City, ST ZIP - City, ST ZIP`. Proven on execution 2457: `"Empty CHEP Pallets, 33,556.15 lbs, 540 Units, 53' Dry Van Trailer Required"` → `"Tulsa, OK, 74134 - Joplin, MO, 64803"`. **324 of 344 populated rows are route-shaped**; the original commodity is **unrecoverable** and is deliberately NOT backfilled (many sit in locked periods and the source is not in the sheet).
  - **`Details` should hold the COMMODITY.** The Gemini prompt defines it that way, `from-ratecon` writes it that way, and `ActiveLoadsTab` renders it as a **wide free-text field under Load Information** beside Trailer/Driver/Truck (`wide: /details|commodity/i` literally equates the two). A route there is the **third** copy of the lane on one screen — the modal already opens with a two-line PICKUP & DROP-OFF panel (`_pickupStreet` over `_pickupLocation`) and carries a separate ROUTE section — in the worst format of the three (no street, no split).
  - **⚠️ Dropping the `Details` mapping is NOT the entire fix, and dropping top-level `Details` from `POST /api/n8n/load-distance` is actively worse** — `Update Job Details (Distance)` auto-maps it onto the **Job Details** tab's own `Details` column (the route, where it is correct and where `from-ratecon` writes the same), so removing the key makes that node write `""` and blank the column. Both tabs have a `Details` column meaning opposite things; that collision is the bug.
  - **⚠️ The endpoint cannot fix this alone.** `$json.Details` means *the route* on the `Addresses Ready?` **true** branch (via the pass-through `autoMapInputData` node) and *the commodity* on the **false** branch, which never calls the endpoint. The one expression correct on both is **`{{ $('JOB DETAILS ENTRY').item.json['Details'] }}`** — the row that node just wrote, so the re-write is idempotent. Verified available: that node's output carries all 14 mapped columns, and this node already resolves `['Load ID']` the same way. Staged in `scripts/stage-n8n-details-fix.js` (dry-run default; needs `--apply --i-really-mean-production`).
  - **Client shipped FIRST, and the order matters**: `stores/dashboard.js` `assignDriver()` (feeds the driver's load-assigned notification), `driver/LoadCard.vue` and `driver/LoadDetail.vue` all read `Details` as a route. `assignDriver`'s origin/destination regexes (`/origin|pickup.*city/`) matched **nothing** against the real headers (`Pickup Info` / `Pickup Address`), so the `Details` split fired on *every* dispatch. All three now use `resolveLoadRoute()` / `formatLoadRoute()` in `client/src/lib/address.js`, which reads `_pickupLocation`/`_dropLocation` → the address columns → a `Details` route **only when `splitRoute()` says it is genuinely route-shaped**. Locked by `scripts/test-details-route-vs-commodity.js` (49 assertions, 6 mutants).
  - Its expression moved `$json.output.details` → `$json.Details`, which also stopped the false branch **blanking** the column (execution 2426 wrote `Details: ""`).
- **Job Tracking has no `Distance` or `Rate Per Mile` column at all** (26 columns, verified) — only Job Details does. So `Update Job Tracking (Distance)` never wrote a distance anywhere; the name is a leftover.

**⚠️ Never PATCH an n8n credential to "test" it.** `PATCH /credentials/:id` overwrites immediately; suppressing curl output does not prevent the write. Doing this to `kzlHx6lePVcSV9B8` (Gemini) twice on 2026-08-05/06 broke ingestion with `API_KEY_INVALID` and cost a misdiagnosis — the resulting downstream failures look like unrelated node errors ("Bad request - please check your parameters"). Read the error `description`, which carries the real Google message.

**Rate-con reconciliation** (`lib/ratecon-reconcile.js` + `reconcileRateCons()`): asks, from *outside* the pipeline, "did every rate-con email become a load?" — so it catches an execution that never starts, a Gmail filter that stops matching, an n8n outage, or a deactivated workflow, none of which alert. Runs every 6 h behind `RATECON_RECONCILE_ENABLED` (**enabled in prod**), plus `GET /api/admin/ratecon-reconcile` (Super Admin; `?dryRun=true` reports without alerting or consuming the once-per-load alert). Alerts **once per load id** via `ratecon_reconcile_alerts` and marks a row resolved when the load appears — repeating a gap daily is how the existing "needs a manual check" emails came to be ignored. Matches **6–12 digit** load numbers: an 8–10 bound silently skips every 7-digit Bison / Steam Logistics id. **⚠️ The sweep MUST stay read-only (`EXAMINE` + `BODY.PEEK`)** — n8n's Gmail Trigger selects on **unread + starred**, so a sweep that set `\Seen` would silently stop ingestion, i.e. cause the outage it detects. Adding header fields to the fetch is free; dropping `.PEEK` is not. Deliberately does *not* use `excludeDroppedLoads()`: a cancelled load still reached the sheet and is not an ingestion gap.
- **⚠️ The window is a HIGH-WATER MARK, not a fixed lookback** (PR #274, 2026-08-11). `RATECON_RECONCILE_DAYS` was a flat 14 days measured from *now*, so a gap that aged out was not merely harder to find, it was **structurally unreachable**, and a sweep outage silently discarded the days nobody swept. `resolveSweepWindow()` now reads everything since the last *successful* sweep — floor **14** days (never narrower than the old behaviour), ceiling `RATECON_RECONCILE_MAX_DAYS` **400**, plus a deep pass of `RATECON_RECONCILE_DEEP_DAYS` **365** every `RATECON_RECONCILE_DEEP_EVERY_HOURS` **168** (weekly). The mark advances **only on a real sweep and only after it succeeds**, so a failed sweep re-covers its own period and a read-only `?dryRun=true` admin GET can never narrow the next real one. This was not hypothetical: load **556354570** (C.H. Robinson, 16 Jun 2026) matched n8n's unread+starred trigger exactly, no execution ever consumed it, and it had already fallen out of the 14-day window before this module went live — **eight weeks undetected**.
- **⚠️ Expect the first deep sweep after deploy to report a BASELINE, not 63 fresh failures.** A first full-history sweep finds **63 gaps against 0** in the old window, so that pass is labelled and excerpted rather than mailed as an incident. The once-per-load-id contract still holds, so no load is ever named twice.
- **Extraction is STAGED: subject → PDF attachment filename → body**, each stage running only where the previous found nothing. Subject-only missed 12 of 687 inbound messages. The staging is the *safety*, not an optimisation — the 675 messages the subject already answers cannot acquire a new false positive, and it costs a body fetch on 1.6% of messages instead of all of them. Measured across all 745 messages the two new stages add **one** candidate and **refuse one phantom** (Trident names the real load in its subject while its attachment is an internal doc number). The body anchor is the word `LOAD` and nothing else — `reference` scored 0/4, `booking` 0/2, `bol` 0/1, `confirmation` 0/1 on real mail. Narrow either stage back independently via `RATECON_RECONCILE_SCAN_FILENAMES` / `RATECON_RECONCILE_SCAN_BODY`.
- **The read-only archive is consulted too.** **12 of the 74** "gaps" a wide sweep turns up are loads that shipped and were **archived**, not loads that were lost — so without the archive read a full-history sweep mostly reports its own blind spot.
- **⚠️ Reading bodies made the IMAP reader a parser of attacker-influenced text, and both consequences were real.** (a) It is now **literal-aware**: a forwarded rate con quotes `Subject:` lines and any body can forge `* N FETCH` or a tagged completion, so literals are *counted* rather than scanned, FETCH boundaries are anchored to a line start (BODYSTRUCTURE is inline protocol text, so an attachment name could otherwise forge one), and the literal sentinel is stripped from protocol text so a filename cannot forge it. (b) The first draft carried a **self-inflicted DoS** — three unbounded whitespace runs in the body anchor were cubic, and because HTML tag stripping turns markup into whitespace, an ordinary **7.2 KB** broker email blocked the event loop for **28 seconds**, on an unattended 6-hourly timer, in the single process that also serves the dashboard, the driver app and the Linxup GPS webhook. Quantifiers are bounded, input is whitespace-collapsed, and the tag strip is now a **linear scan with no regex at all** (which also closed a phantom-load path the bounded regex had introduced). A 200-message sweep of crafted bodies went **24–27 s → 64 ms**.
- Locked by `node scripts/test-ratecon-reconcile-window.js` (166 assertions, 82 fail against `origin/main`) and `node scripts/test-ratecon-reconcile-wiring.js` (70 assertions, extracted from `server.js` so a rename fails the run). Verified read-only against the production mailbox: 89/89 messages parsed, `\Seen`/`\Flagged` unchanged (unread 15 → 15, starred 89 → 89).
- **Only INBOUND mail is a signal** (2026-08-08). The label is not a rate-con inbox — measured on the live 14-day window, **20 of 68** messages under it were sent *by* `info@logisx.com`. That produced the module's first false positive: `2787514`, an outbound Bison invoice whose customer **PO** number was read as a missing load. `splitSelfSent()` drops messages whose parsed `From` addr-spec equals `GMAIL_USER`, and only then — an unset address or an unparseable header keeps the mail, because a detector that discards what it cannot read stops detecting. Compared on the **parsed address** and the **last** angle-addr: a substring test on the raw header matches every reply chain that quotes us, and taking the first `<…>` would let a forged display name (`"x <info@logisx.com>" <broker@acme.com>`) suppress a real broker's rate con.
- **⚠️ Do not "harden" this by sanity-checking the NUMBER instead.** The PO is 2,787,514; real load ids already in Job Tracking include Steam's 2,214,407 / 2,216,467 / 2,218,094 and MegaCorp's **2,651,585** — same digit count, same magnitude, and the newest real id is nearer the PO than the oldest real one is. There is no range to cut. Its subject, `Bison Transport Order# 2787514`, is also byte-shaped like a genuine Bison rate con, so no subject heuristic separates them either. Sender is the *only* discriminator. Narrowing `LOAD_NUM_RE` to chase this re-breaks the 7-digit ids the 6–12 bound was widened to catch, and learning a plausible range from the sheet's own ids goes blind exactly when a new broker's loads *all* fail to ingest — the case this module exists for.
- Closing a row records **why**: `ratecon_reconcile_alerts.resolution` is `'appeared'` (the load reached the sheet) or `'self_sent'` (it was never a load). The sweep retires a still-open row whose number, in the current window, came only from mail we sent — idempotent, scoped to `resolved_at IS NULL`, and it cannot resurrect because that mail no longer reaches `findMissingLoads`. Sheet presence wins over the sender filter. `GET /api/admin/ratecon-reconcile` reports `selfSentSkipped` and `retired`; `scanned` is now inbound-only.
**Unusable addresses — the other silent loss, and why the guard could not live in n8n** (2026-08-09). Measured on production: of the 151 loads the `AI Agent` node priced, **6 came back `distance: 0` → `$0.00/mi`**. Two distinct causes, and conflating them sends the fix to the wrong layer:
- **5 of 6 — the extraction produced no placeable address.** The clearest is **`550303758`** ($740, delivered 2026-04-19): its Job Tracking **`Drop-off Address` cell is empty to this day**, while `Drop-off Info` reads `SAMS CLUB 8244`. The model was handed a pickup and nothing else and answered `"Hawkins, TX, 75765 - N/A, N/A, N/A"`. Three more carry `"N/A, N/A, N/A - N/A, N/A, N/A"` with `Payment: 0` (extraction wholly empty) and one carries the model's prose, `"Missing Pickup and Drop-off addresses and Payment information. Cannot perform calculations."`
- **1 of 6 — nothing to do with addresses.** **`554102888`** ($3,700, delivered, truck `LogisX-#33`, **Owner ID 5**) had *both* addresses clean and complete and still returned `distance: 0`. That is the LLM-distance problem, not an ingestion one. (⚠️ It is easy to misattribute: joining Job Details' `output` back to Job Tracking on the `details` string alone is **ambiguous** — that lane matches 5 rows. The `Payment` inside the JSON disambiguates. `550448673` is a *different* load: $3,500, **Cancelled**, and it priced fine at 1050/1070/1050/1100 mi across four runs.)

**⚠️ The workflow structurally cannot catch this, so do not try to fix it there.** The order is `Validate Load ID` → **`JOB DETAILS ENTRY` (which writes the Job Tracking row)** → `Addresses Ready?` → `AI Agent`. The row is **created before any address is examined**; `Validate Load ID` checks the load number and `Critical Fields Complete?` checks the Rate, and *nothing between them looks at the two addresses*. `Addresses Ready?` only decides whether a load gets a **mileage** — never whether it gets **created**. A guard downstream of the write cannot stop a bad write.

The check therefore lives in **`POST /api/n8n/extract-pdf-via-gemini`**, the one place that sees the fields before any sheet does and the one we own:
- **Lockstep with the drag-and-drop route.** That route normalized Gemini's output and re-ran it once when a critical field came back blank; this one returned the raw first pass. The divergence is measurable — **37 `Pickup Address` and 34 `Drop-off Address` cells in production still carry the broker's raw line breaks**, because only the attended half ever ran `collapseAddress()`. The second pass is the half that matters: it is the only mechanism that recovers a drop-off address the first pass missed.
- **⚠️ The retry is BUDGETED here and unbudgeted there.** The caller is n8n's `Extract via LogisX` node with a hard **120 s** timeout (and `retryOnFail`), while `runRateConGemini`'s own worst case is ~93 s. An unbudgeted second pass could push a *thin-but-usable* extraction past the node timeout and turn it into **no load at all** — the trade backwards. A `Promise.race` caps the retry at the remaining budget (deadline 105 s, and a retry never *starts* with under 20 s left, so a starved retry is unreachable).
- **It never fails the request.** A load with one bad field beats no load, and a non-2xx here sends n8n down its error branch. The extraction still ships; it just also raises its voice, **once per load id** (`ratecon_extract_alerts`, same shape and same reasoning as `ratecon_reconcile_alerts`). `warnings` / `unusableFields` are returned as **siblings of `output`**, never inside it, so no n8n expression changes.
- **`addressLooksUsable()` is deliberately a low bar** — a ZIP or a bounded US state token — because the two errors cost differently: a false negative costs one email, a false positive re-creates the silence. Calibrated against **all 413** production Job Tracking rows: **5 flags, all true positives** (two `Awaiting Rate Con` sentinels, and one cell holding a raw JSON blob `{"Street":…,"State":"TX","Zip":"752331402"}` that no geocoder resolves), **0 false positives**. Do not make it stricter — no city list, no street-suffix rule.
- **Replayed against the 6:** catches **5**; `554102888` correctly stays quiet, because its addresses really were fine.
- **⚠️ `RATECON_EXTRACT_ALERT_ENABLED` defaults ON**, breaking the ships-dormant convention on purpose (same call as `PII_MASK_ENABLED`): it is a kill switch, not an enable switch.
- **⚠️ Two spend ceilings, because neither the dedupe key nor `pdfOcrLimiter` is one.** The retry fires on *content* — a rate con with no rate makes it fire every request — and the dedupe key is Gemini's reading of the caller's PDF, so an incrementing load number mints fresh keys. Given the n8n secret sits in plaintext in a node parameter, treat the caller as semi-trusted. So: the load id is validated against the same `/^[A-Za-z0-9\-_.#]{1,40}$/` whitelist the public tracker uses before it may become a key (junk collapses into one `unidentified:<UTC-day>` bucket — 500 crafted ids → 1 alert); `RATECON_EXTRACT_ALERT_MAX_PER_DAY` (25) caps alerts on a key nobody controls, because `sendEmail` is shared with onboarding/outreach/invoices and a flood here would silence *all* app mail; and `RATECON_RETRY_MAX_PER_WINDOW` (20/15 min) plus a 2-slot in-flight cap bound the extra Gemini calls and the doubled peak memory. Exceeding any of them is never an error — the first-pass fields still ship.
- **⚠️ `alerted_at` is stamped only on CONFIRMED delivery**, which is why `sendEmail()` now returns a boolean (it used to return `undefined` on every path and swallow failures; existing callers ignore it, so nothing else changes). Stamping before the send is the obvious shape and it is wrong: a transient Gmail 4xx or an unconfigured mailbox would mark the load "alerted" forever, and in this table an alert that never went out would look exactly like one that did. The in-app dispatch notification counts as delivery in its own right — it is the channel that still works with no `GMAIL_*` at all.

**The 6 loads were NOT corrected.** `2026-04` and `2026-05` are both **locked and finalized**, and 2026-05 sits inside payout id 14 (owner 5) already marked **paid**. Nothing needed restating anyway: `Distance` / `Rate Per Mile` are **display** figures — no money math reads them (`findPaymentColumn` deliberately refuses a `/rate|amount/` fallback precisely so "Rate Per Mile" can never be billed), and each load's `Payment` is intact.

2. **Drag-and-drop (added 2026-07-25, attended).** Dispatcher drops the rate-con PDF on the Job Board or the New Job form (scoped to the Job Board only — removed from Active Loads per client request, since a freshly-dropped load is Unassigned and lands on the Job Board anyway). `POST /api/loads/ratecon/extract` parses it and **returns without writing**; the dispatcher reviews/corrects; `POST /api/loads/from-ratecon` then replicates the n8n steps server-side. This exists because dispatchers regularly learn about a load from the driver while the app has nothing.

`POST /api/loads/from-ratecon` runs the n8n sequence in order: validate Load Number (400 if blank) → dedupe against Job Tracking (**409 `DUPLICATE_LOAD`**) → Distance Matrix + rate-per-mile → append **Job Tracking** → upsert **Payments Table** (key `" Job ID"`, leading space is real) → upsert **Job Details** → **archive the PDF** (below) → `load_coordinates` + `audit_trail` + `dispatch-notification`, then `jtCacheInvalidate()` so the load shows up before the 60s cache expires.

Gotchas worth knowing before you touch this:
- **Anchor every sheet write to column A explicitly.** `values.append` with a bare tab range lets Sheets auto-detect the table's anchor column from *existing* data; when a tab's leading column is empty in that data (**Job Details' column A is blank-named; Payments Table's early columns are sparse**) the appended row lands **shifted right into the wrong columns** — broker name into Payment Amount, distance into Rate Per Mile. The upserts therefore write via `values.update` at a computed `A{lastRow+1}`, never bare `append`. Job Tracking's own append is safe only because its column A ("Contract ID") is populated in existing rows. A synthetic-header unit test will *not* catch this — it only reproduces against the real sheet's layout.
- **The rate-con archive is what makes a dropped load invoiceable, and it is LOCAL, not Drive.** Invoice drafting finds a rate-con via `getRateConBytes()`, whose 3 sources are tried in order: (a) the Drive folder, (b) a `documents` row of type `RATECON`, (c) a base64 in the request body. Source (a) **cannot be written by this app**: the prod "Rate Confirmations" folder is a *My Drive* folder owned by `info@logisx.com` (`canAddChildren:false` for the service account, which also has zero storage quota) — n8n only writes there via OAuth delegation. So `from-ratecon` writes the PDF to `uploads/rate-cons/<loadId>.pdf` + a `documents(type=RATECON)` row (source **b**, the same local-first pattern PODs use), and only *mirrors* to Drive best-effort (silent on the expected service-account failure). Do not "fix" the archive by making Drive the primary — it will fail in prod.
- **`Contract ID` on Job Tracking stays blank.** n8n writes `Contract ID = Broker Name` on the *Payments Table* tab only. Verified against production: Job Tracking's `Contract ID` is blank for email-ingested loads and holds a numeric reference when set at all. Do **not** prefill it with the broker/agent name — that makes a dropped load diverge from an email one.
- **`Driver` is left blank** even when the rate-con names one. Dispatching from the dashboard is what emits the driver socket event and notification; writing the name directly would create a silently-assigned load.
- **Job Details has no matchable Load ID column** (its column A header is blank in prod *and* staging), so the upsert can't dedupe there — but a re-drop is already stopped by the Job Tracking 409 upstream, so the Job Details upsert only ever runs for a genuinely new load.
- **⚠️ That missing `Load ID` column is also why the Job Details tab is 93% junk today (2026-08-09, NOT yet cleaned — awaiting owner approval).** n8n's `Update Job Details (Distance)` uses `mappingMode: autoMapInputData` with `matchingColumns: ["Load ID"]`. With no such column the match can never hit, so every run **appends**; and auto-map writes the input item's keys into like-named columns, so the agent's `{output:{…}}` item lands entirely in the one column whose name it does match — a column literally called **`output`** (column **T**, the last one). Production Job Details is **163 rows: 151 `output`-only rows + 12 real drag-and-drop rows**, the two sets **disjoint**, and *no* row carries anything else. Facts that matter before anyone "tidies" this:
  - **Nothing reads `output`.** Zero references in `server.js`, `client/`, or `scripts/`; the only surface that renders it is the generic Data Manager, which renders whatever columns exist. `Distance` / `Rate Per Mile` on this tab are likewise **write-only** (`from-ratecon`) and read by nothing.
  - **Deleting the column shifts nothing** — `output` is the **last** column, and `upsertByKey` resolves everything by header *name* on a fresh read anyway.
  - **⚠️ But deleting it while the n8n node still runs makes things worse, not better:** with no matching column at all, auto-map appends an **empty row** per load, converting junk *cells* into junk *rows*. Any cleanup must land **after** the workflow stops writing `output`.
  - **The 12 real rows are interleaved** (rows 128, 141–142, 149–154, 159, 162, 164), 11 of them inside the junk block — so "delete the junk rows" is a non-contiguous, index-shifting operation, whereas clearing is a single `values.clear` on `T2:T`.
- **Every step after the Job Tracking append is best-effort** and degrades to a `warnings[]` entry rather than failing the request — the row already exists at that point, and there are no transactions.
- Steps 3-8 are ported into `lib/ratecon-load.js` as pure functions; `buildJobTrackingRow` mirrors `NewJobView.vue`'s mapping. One deliberate deviation from n8n: an unparseable rate coerces to `0` instead of writing the literal string `"NaN"` into the sheet.
