# Invoice drafting — all brokers (IMAP + rate-cons)
One-click "Draft Invoice Email" on any **delivered/completed** load, distinct from the generic `/api/invoices/generate` flow. Originally Bison-only; generalized to every broker 2026-07-25.
- `POST /api/loads/:loadId/draft-invoice` (alias `…/draft-bison-invoice`, kept for old callers) — requires delivered/completed **and** a POD, assembles the invoice + supporting docs, and writes a Gmail **draft** (never auto-sends) via `lib/imap-draft.js`. Pass `dryRun` to preview **without** burning an invoice number or creating a draft; the dryRun response echoes `brokerName`/`to`/`subject`/`orderNumber`/`total`/`totalSource` so QA can check routing without opening the PDF.
- **Recipient** — `isBisonLoad()` survives as a *branch*, not a gate: Bison → `QPinvoicesUSA@bisontransport.com`; **every other broker → `quickpay@megacorplogistics.com`**.
- **Broker identity** (`resolveInvoiceTo()` in `lib/broker-invoice.js`): the sheet has **no brokerage-company column** — `Broker Contact Name` and `Contract ID` both hold the booking *agent* ("Danna Garcia"), which must not head an "Invoice To" block. Resolution order: `BROKER_DOMAIN_NAMES` map on the broker email domain (subdomain-aware) → humanized domain (`acmefreight.com` → "Acme Freight") → `Broker Contact Name` → `""`. Add new brokers to that map.
- **Order number** falls back to the **load ID** when the rate-con has none (normal for non-Bison). ⚠️ **On a BISON load that fallback is now a hard stop, not a default** — Bison AP matches payment on *their* Order #, so an invoice carrying ours looks valid and reconciles against nothing. When `isBison && !rcFields.orderNumber` the route answers **422 `INVOICE_REFS_REQUIRED`** unless the dispatcher supplies both `orderNumber` and `poNumber`; `?dryRun=1` instead returns 200 with `needsOrderNumber`/`needsPoNumber` so the review modal has a form to type into (same relaxation, and same reason, as `needsTotal`). An explicitly EMPTY `poNumber` satisfies it — omitted means nobody looked, empty means somebody decided. **The guard sits ABOVE `nextInvoiceNumber()`**: below it, every refusal would burn an invoice number. The dryRun also reports `orderNumberSource` (`ratecon` | `override` | `load-id-fallback`) and `rateconSource`, because a silent load-ID substitution with no UI signal is exactly what shipped a wrong Bison invoice on 2026-08-18. **Total** falls back to the sheet's `"  Payment  "` column (note the real surrounding spaces; matched on `h.trim()`, exact-`payment` only — deliberately no `rate|amount` fallback so "Rate Per Mile" can never be billed). If neither source yields a positive number → **422 `INVOICE_TOTAL_UNKNOWN`**; never draft a `$0.00` invoice.
- **Invoice numbering**: per-calendar-day counter in the `bison_invoice_seq` SQLite table (`nextInvoiceNumber()` / `peekInvoiceSeqStmt`) — table name kept deliberately (renaming needs a migration for zero gain; it now serves all brokers). Only a real (non-dryRun) draft increments it.
- **Rate-con attachment** (`getRateConBytes()`, **4** sources in order): (a) the n8n Drive folder BY FILE NAME — every *email-ingested* rate-con lands here (n8n uploads via OAuth), matched on a filename *containing* the load ID, needs `drive.readonly`; (b) a `documents(type=RATECON)` row — where **drag-and-drop** loads live (see "Load ingestion"), since the service account can't write to that My Drive folder; (c) a base64 in the request body; (d) the Drive folder **BY CONTENT**, only when (a)–(c) all came up empty.
  - **⚠️ (a) rests on an assumption that is not a rule, and (d) exists because it broke.** The Drive file name is the raw email SUBJECT, so (a) only works when our Load ID happens to appear in it. Measured 2026-08-19 against the live folder (697 files) and sheet (421 rows): **50 loads have no file-name match, 3 of them Bison.** Load 30080873 is filed as `"Subject: Bison Transport Order #7101850"` — Bison's order number reached the subject, ours did not — so the invoice went to Bison AP with our load id in place of Order #7101850 and no PO # at all, while the document sat in the folder containing both numbers.
  - **(d) reads the documents instead of trusting their names**, then REMEMBERS the answer as a `documents` row (`drive_file_id` set, `drive_url` empty — the shape `fetchDocumentBytes()` already resolves), so (b) serves every later draft for free. **Only on a real approve — `?dryRun=1` never persists**, or a dispatcher who previews, sees the wrong document and cancels has already written the link. Rules live in `lib/ratecon-drive-index.js`. **⚠️ It is deliberately biased toward finding nothing: these bytes get attached to a Gmail draft addressed to the broker, so a false positive mails another customer's rate to a third party.**
  - **⚠️ THE TWO RULES THAT MAKE (d) SAFE, both of which a review round proved were needed:**
    1. **The whole-token gate must survive the extractor it is paired with.** `harvestPdfStrings()` space-joins PDF text literals, and kerning routinely splits a number across them — `[(Order # )-2(30080873)-140(1)] TJ` is the number **300808731** but extracts as `"Order #  30080873 1"`. A plain boundary test then reports a hit for load 30080873 on a document that never mentioned it. Real files in this corpus already extract with runs like `"2216467 0"`, `"54406 1"`. `textHasToken()` therefore also refuses a match with a digit across a whitespace gap on either side. The real document survives because Bison prints ours as `LEG #: 30080873 PO #:` — flanked by letters.
    2. **"Independent" is not "load-specific".** The broker's email domain and our trailer identify the BROKER and the EQUIPMENT — every Bison rate-con contains `bisontransport.com`, and a trailer runs 20 loads a month. Counting either as corroboration collapses the bar to the id gate alone. Only the sheet's Payment total and the pickup/dropoff **cities** count, and **`MIN_CORROBORATIONS` = 2** because any one of them can coincide. Domain/trailer contribute to `score` only. Fewer than 2 → `unconfirmed`, surfaced to a human, **never attached**.
  - **⚠️ A content-matched rate-con may never choose the recipient.** `documentsEmail` becomes the Gmail `To:` for every non-Bison broker, so a wrong match would mail this invoice — and that customer's rate — to an address lifted off *their* paperwork. `source === 'drive-content'` candidates are excluded from both the primary and the alternate-recipient recovery loop. Rows already in `documents` are trusted: one exists only because a human approved a draft with that file attached and visible in the modal.
  - **Cost, and why it is bounded three ways**: a ±21-day window around the load's own dates, a 40-file cap, and `documents` caching so it never runs twice for one load. Downloads are **batched (`RATECON_CONTENT_CONCURRENCY`, default 6) and stop early** once a batch adds no new match — a sequential scan measured **137 s**, against a client that gives up at 60 s. Misses are held in a 15-minute negative cache (`rateconScanMisses`) because the dispatcher who hit this pressed Draft Invoice **four times in a row**.
  - **⚠️ (b) needs BOTH keys and a rank.** Job Tracking holds `513987502` and `#513987502`, and this query used to pass the raw URL param while (a) stripped the `#` — the two halves disagreed about the load's name. It also lists `'BOL'`, and ordering by `uploaded_at` alone meant a POD-day BOL scan **outranked the real rate-con** and got mailed to the broker as one. Rate-cons rank first, and the read is `.all()`, not fetch-one.
  - **`ratecon_load_aliases`** records what (d) proved: the numbers in a matched file's NAME are aliases for that load. `reconcileRateCons()` unions them into its known-ids set — without it that sweep reports `missing loads: 7101850` for a load that was delivered and invoiced. Same class of exclusion as the archive check, for the same reason. **⚠️ "Only corroborated matches reach this table" does NOT make every alias safe** — corroboration proves file↔*load*, not that each number in that file's *subject* identifies it. A subject also carries zips, dates and the broker's other refs, and an alias suppresses a real ingestion alert **permanently**. Floor is therefore **7 digits with `YYYYMMDD` excluded** (`MIN_ALIAS_LEN`), not the module's general 5 — a US ZIP is exactly 5 — and rows carry `drive_file_id` provenance so a bad one can be found.
  - **`from-ratecon`'s Drive mirror now keeps the id it asks for.** It requested `fields:"id,name"` and discarded the id, leaving `drive_file_id = ''` — and `fetchDocumentBytes()` falls back to Drive *only* via that column, so a RATECON row whose local file went missing silently stopped attaching. `uploads/` is not in the nightly backup, so that is routine, not hypothetical.
  - **Backfill**: `POST /api/admin/ratecon-index` (Super Admin, `rateconIndexLimiter` 4/15min, one run at a time) applies the same matcher in bulk. **Report-only unless BOTH `{"apply":true}` in the body AND `RATECON_INDEX_APPLY_ENABLED=true`** — it ships dormant like every other consequential writer, and the opt-in is in the body because `?apply=true` is a bookmarkable URL that writes up to 200 broker-facing links. Returns the reasons behind every proposed link, and reports `truncated`/`remaining` rather than letting a deadline look like completion.
  - **One definition of "does this file name carry our load id"** — `rcIndex.filenameCarriesLoadId()`. There were three and they disagreed: for a punctuated id the Drive lookup (which strips punctuation from the id but not the name) says no while whole-token matching says yes, so the backfill was skipping exactly the loads the lookup cannot find.
- **Field extraction**: `RATECON_PDF_SYSTEM_PROMPT` (Gemini) is broker-agnostic; `broker-invoice.js` holds a deterministic PDF text scan as a *free* pre-pass. That scan only recognizes Bison's "Billing Information" block, so it is **all-or-nothing on its `Order #` anchor** — with no anchor the whole result is discarded rather than letting stray label matches leak into `mergeGeminiFields`. This is load-bearing: before that gate, `\bTrailer` matched prose on Navisphere/CHR PDFs (`"are"`, `"Required"`, `"s53"`), and because the scan wins over Gemini in the merge, that garbage tripped the trailer-mismatch **409 and blocked every non-Bison invoice**. The route also only compares trailers when the extracted value contains a digit. **Net effect: Gemini is the primary path for all non-Bison brokers**, not an edge case.
- Alphanumeric refs (`SHP2607-A3BJ112`) are preserved by `cleanRef`; only Bison's numeric Order/Move go through `cleanNumericRef`.
- **⚠️ `RATECON_PDF_SYSTEM_PROMPT` says `"PO Number" … Digits only`, which contradicts `cleanRef` — and that contradiction is TEXTUAL ONLY. Do not "fix" it.** Measured 2026-08-19 against `gemini-3.5-flash`: a synthetic rate-con printing `PO #: SHP2607-A3BJ112` returns it **intact under the existing prompt**, twice. The model ignores the instruction when the document is unambiguous, so nothing is being truncated today and the downstream preservation is not dead code.
  - Relaxing the line to "copy it exactly" **was tried and reverted**. Across 9 real rate-cons × 2 runs per prompt, the only reproducible behavioural change was one C.H. Robinson load whose PO went `null` → `0019225255` — a number that *is* in the document but sits beside `Appointment#:` in a scrambled table, so it is as likely to be an appointment number mislabelled as a PO. An ambiguous new value on a money-adjacent field is a reason not to ship, not a win.
  - **⚠️ THE REAL FINDING IS THE NOISE FLOOR: this extractor is ~6-7% nondeterministic per field, prompt unchanged.** Two identical-prompt runs disagreed on **15 of 216** field comparisons; a second pair disagreed on 12. The unstable classes are consistent — `Details`, `Drop-off Address`, `Broker Phone`, `P/U Reference Number`, both appointment times, `Documents Email` casing — and one run flipped a street number (`1230` → `1273 W Danby Rd`). So **a before/after diff of this prompt is meaningless without a measured noise floor**, and any future prompt edit must run each prompt at least twice and compare the disagreement RATE, not the raw diff. It also means Job Tracking holds extracted fields that would not reproduce exactly if re-extracted. Literal `"None"` and `"$0.00"` normalize to `""`. Many `scripts/patch-bison-*.js` / `diag-bison-ratecon.js` helpers exist for one-off fixes to this pipeline.
