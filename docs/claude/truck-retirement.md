# Retiring a truck — `trucks.retired_at`, the mirror of `in_service_date`
`in_service_date` gave a truck a **first** billed month; nothing gave it a **last**, so a truck that left the fleet kept accruing insurance/ELD/payment/HVUT/IRP into every open month forever. The obvious workaround — flipping `status` to Inactive — is refused by `truckEditLockBlockers()` check (1), and correctly so: `status` has no time dimension, so it removes the truck from **every** month including the finalized ones it was legitimately billed in. There was therefore no correct way to remove a truck from the fleet at all. Named as a known gap in PR #210 and deliberately skipped in PR #216; built here.

- **⚠️ INCLUSIVE, and that is what makes the feature usable.** The retirement month IS billed, in full, no proration — a truck in service 2026-04-15 is billed all of April, so a truck retired 2026-07-27 is billed all of July. The interval a human reads off the two date fields is `[in_service_date, retired_at]`, both ends inclusive. Under the *exclusive* reading (`retired_at` = first unbilled month), retiring a truck at the end of the month that just closed would REMOVE that month's costs from a finalized period and be refused — i.e. the feature would be unusable for the exact case it exists for. **A truck retired mid-month bills that whole month.**
- **⚠️ THE CLIENT HAS NOT SIGNED OFF ON THE PRORATION QUESTION.** The convention above is derived from `in_service_date`'s own behaviour and is internally consistent, but "is the retirement month billed in full?" is an accounting decision, and insurance genuinely can be cancelled mid-month with a refund. The two answers differ by one month × up to **$3,105.83** on a single truck. Confirm before anyone retires a truck in anger.
- **One predicate, five gates.** `truckChargedInMonth(t, monthKey)` is the single both-bounds-inclusive test; `truckChargeUntilMonth()` is the upper-bound companion to `truckChargeFromMonth()`. All four money month-gates **and** `truckFixedCostLockedMonths()` (the guard) call it, so the guard cannot disagree with the math it protects. That is the whole point — PR #216 correctly identified "a mirrored upper bound, *or the guard disagrees with the math it protects*" as the hard part, and the answer was to stop mirroring and share.
- **Two shapes, not one.** Clamping the month gate does nothing to a multiplication, so the **all-time totals** need their own end bound: `truckBilledMonthCount(t, now)` replaced four hand-rolled copies of `(now − start) + 1`. A fifth site, `truckMonthsInPeriod()` in `GET /api/investor/report`, re-derives the start with **day** granularity and is invisible to a grep for `truckChargeFromMonth(` — it is clamped separately. **This is why `retired_at` is a DATE, not a bare month**: that site clamps against a caller-supplied date range, and a month-only column would force an invented "last day of the month" there.
- **⚠️ `""` MEANS UNBOUNDED AT BOTH ENDS.** `truckChargeFromMonth()` returns `""` for "no usable in-service date" and the money math reads it as **charge every month**; `truckChargeUntilMonth()` returns `""` for "not retired" and the math reads it as **charge forever**. A guard reading either `""` the other way waves through precisely the truck with the most exposure — the inversion corrected in PR #205 and again in PR #216. The upper-bound version is strictly more dangerous because `""` is the **default value of every existing row**, so misreading it would report zero exposure for the entire fleet.
- **⚠️ Every fixed-cost `SELECT` list must carry `retired_at`.** Eight of them name columns explicitly; an absent column makes `truckChargeUntilMonth()` return `""` and the bound silently never fires. Asserted textually by the harness.
- **⚠️ `truckChargeUntilMonth()` range-checks the month and `truckChargeFromMonth()` does not — deliberately.** `'2026-13-01'` passes a bare shape test and slices to `'2026-13'`, which every real 2026 month sorts *below*, so a truck "retired" that way would bill all of 2026 and then silently stop in 2027. The FROM half is left alone because it has a `created_at` **fallback**, so tightening it would change which months an existing malformed row bills — a live behaviour change on rows that already have money against them.
- **Setting `retired_at` is itself retroactive**, so it gets guard check **(4b)**, a clone of the `in_service_date` check: the months at risk are the **symmetric difference** of billed-before and billed-after, so backdating into a finalized month is 409 `PERIOD_FINALIZED` (naming the field, the months and the dollars) while retiring effective the current or a future month is 200. Clearing the date (un-retiring) *adds* months back and is caught by the same difference with no extra branch. 400 `RETIRED_BEFORE_IN_SERVICE` guards the cross-field case — an empty interval would make the truck behave like one that never existed.
- **`POST /api/trucks` deliberately does NOT accept it** (a truck is not created retired), which removes a whole gate from `truckCreateLockBlockers`.
- **Scope: `retired_at` is a BILLING bound, not a soft delete.** This is exactly why PR #210's objection to `trucks.deleted_at` ("nine-plus query sites, and missing one means a deleted truck keeps billing") does not apply: a retired truck stays visible everywhere — trucks list, `truckCount`, `getInvestorDriverSet`, driver-pay rate maps — and only its **fixed-cost accrual** stops. Deliberately **not** changed: the ten `status != 'Active'` `NOT IN` subqueries that scope maintenance/compliance fees (those rows are **dated**, so they stop naturally; excluding them would retroactively remove real costs from closed months — the exact harm this feature prevents), and `/api/financials`' per-truck month count for a truck **with loads**, which is bounded by its own load span already.
- **Fixed at the same time**: `perTruckData`'s `avgMonthlyGross`/`avgMonthlyExpenses` divided by `truckMonths` whose floor is **0** — a live `Math.round(x/0)` → `Infinity` → `null` in JSON. Reachable before (a forward-dated truck) but ordinary once a truck can retire.
- **Measured on production, read-only, 2026-08-09.** 6 trucks, all Active, 15 locked periods (2025-05…2026-07); only 2026-08 open; two payouts already **PAID**. Fixed costs currently billed into locked months: `LogisX-#33` **$12,173.32**, `LogisX-#2372` **$7,487.32**, `LogisX-#302` **$6,080.00**, the other three $0. Fleet rate **$9,540.99/mo**. `LogisX-#302` last pinged 2026-07-27 — the live retirement candidate, and under the inclusive rule `retired_at = 2026-07-27` is **allowed** (July stays billed) while `2026-06-30` is refused.
- Verified: **129/129** unit assertions against source **extracted** from `server.js` (`node scripts/test-truck-retirement.js`) — including a deliberately independent oracle, since testing the predicate against itself proves nothing — plus **61/61** end-to-end HTTP on a scratch DB. Migration is additive, idempotent (`ALTER` in try/catch) and reversible (`UPDATE trucks SET retired_at = ''` restores every figure exactly).
