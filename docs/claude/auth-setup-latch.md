# `POST /api/auth/setup` — the unauthenticated admin minter
Creates the first Super Admin with no session and no role check. Its only gate was `SELECT COUNT(*) FROM users == 0`, i.e. the contents of one table — so anything emptying `users` republished an open admin minter. **`scripts/reset-super-admin-password.js` does exist** (committed 2026-08-12 from the VPS, where it had been untracked since 2026-04-13 — earlier revisions of this file asserted the opposite, twice, and were wrong). **It does not change the picture here**: it resets the password of an *existing* `super_admin` row and refuses when that row is absent, so a genuine **zero-Super-Admin** state still means `SETUP_RECOVERY_TOKEN` or hand-editing `app.db` on the VPS. The recovery script covers "I forgot the password"; this route and its latch cover "there is no admin left."
- Now `setupLimiter` (5/15 min), audit-logged (`setup_super_admin`), and the count-check + INSERT run in **one synchronous transaction** — `await bcrypt.hash` sits between them and yields, so two concurrent requests could both pass the check and both insert.
- **The latch:** `usersEverExisted()` refuses setup when `users` is empty but the DB still carries a live system's data — a row in any of `LIVE_SYSTEM_EVIDENCE_TABLES` (`audit_trail`, `expenses`, `trucks`, `investor_payouts`, `documents`), all of which need an authenticated writer. Fails **closed** on an unreadable `users` table. A genuinely fresh install has none of them and setup works unchanged.
- **⚠️ NEVER latch on `sqlite_sequence`.** `users.id` is AUTOINCREMENT so its high-water mark looks like the perfect durable signal (413 vs 12 live rows in production) — but the CHECK-constraint probe at the top of `server.js` inserts and deletes a `__test_sa__` row on **every boot**, so the sequence climbs once per restart on an empty database. The first draft of this feature used it and refused first-time setup on a fresh install. `invoices` and `investor_applications` carry the same kind of probe.
- **What it deliberately does not cover:** a *missing* `app.db`. No content test can — the file is new and empty, which is indistinguishable from a fresh install because it is one. Mitigated by the limiter, the audit row, and backups; the structural fix is that the API can no longer reach a zero-admin state.
- **`SETUP_RECOVERY_TOKEN`** is the owner's way back: with the latch armed, setup proceeds only for a caller presenting it (via `X-Setup-Token`, `Authorization: Bearer`, or `setupToken` in the body). Unset — the normal state — the latch is simply closed. An unset token plus an empty presented token is refused *explicitly*, because `safeEqual("", "")` is true. **A token under 24 chars is treated as UNSET** (with a boot warning): it is the only control between the network and an admin, and `safeEqual` compares length first, so a short one is both guessable and length-leaking. Every refusal is `logAudit`ed (`setup_refused`) — a distributed guess would otherwise be invisible in `audit_trail`, the one place anyone looks afterwards.
- `GET /api/auth/setup-check` still returns **only** `{needsSetup}` — unchanged shape — but it now means "setup would actually succeed". **⚠️ Do not add a `locked` flag.** The route is unauthenticated and unlimited, so that flag is a free, pollable oracle for "this instance has lost its accounts but still holds data" — exactly the state in which `SETUP_RECOVERY_TOKEN` is the only remaining control. A latched system renders the ordinary login page. Rate-limiting this GET is not the alternative: the SPA calls it on every boot.
- **Session revocation is part of the guard, not a nicety.** `requireRole()` reads `req.session.user.role` and never re-reads the DB, and the cookie lasts 24 h — so before `purgeUserSessions()`, demoting or *deleting* a Super Admin left them holding a working admin cookie, and they could simply `PUT /api/users/:self {"role":"Super Admin"}` back or mint a new admin. `LAST_SUPER_ADMIN` never fires, because they are transacting as a valid Super Admin. `PUT` purges on a role change or password reset (sparing the caller's own sid), `DELETE` purges unconditionally. This also makes "reset their password" a real incident response again.
