# Tests — the standalone runners and the HTTP suite

**Tests & linting:** No Jest/Mocha/Vitest/ESLint configured — but there IS a pipeline now: `npm run ci` locally, and `.github/workflows/ci.yml` on every PR (see [`ci-deploy.md`](ci-deploy.md)). Integration harness at `test-suite.js` — numbered HTTP tests against a running server. **Do not pin that count here.** It has now drifted twice (the figure read `136` while the file held ~147 `test()` call sites plus ~42 `skip()`, measured 2026-08-26); `test()` and `skip()` both push to `results[]`, so the suite's own printed `results.length` is the only true count and a number written in this file is stale the next time a test is added. Prepare fixtures first, or nearly everything fails at the login on test 2.

**⚠️ The suite WRITES — point the server at a copy, never the live sheet.** Test 46 logs an expense, so this is not a read-only harness. Production's `.env` sets **no `SPREADSHEET_ID` at all**, so `server.js` falls through to its hardcoded production default (`1ey1n0AA…`) — meaning *any* server started without an explicit override (this suite's, a helper script's, a stray `npm start`) writes to the live Dispatch Management sheet. **And never identify a sheet by its title:** the VPS `logisx-staging` process uses a sheet *titled* **"logisx-production"**. Its ID is not production — the title is a leftover from how the copy was made — but read in a hurry it says the opposite of the truth. Check the ID, never the name. The safe local copy, used in the command below, is `156Y5-OUUEZspiY7dRsJZ57iyKWLJAjdVP8a4yw0PMN0` ("Dispatch Management (LOCAL)"). Same class of accident on the port: the suite defaults to **3000, which is production on the VPS** — pass `TEST_PORT` (and the server's `PORT`) to run anywhere else.

```bash
./scripts/refresh-local.sh                             # optional: a fresh sanitized copy; every password on it is random
node scripts/prepare-test-fixtures.js --yes-local-db   # LOCAL db only: sets its test password on one account per role
# separate terminal — the override IS the safety; without it the server uses the PRODUCTION sheet
SPREADSHEET_ID=156Y5-OUUEZspiY7dRsJZ57iyKWLJAjdVP8a4yw0PMN0 npm start
TEST_ADMIN_USER='<super admin username>' TEST_INVESTOR_USER='<investor username>' \
  TEST_DISPATCHER_USER='<dispatcher username>' TEST_DISPATCHER_PASS='Password123!' node test-suite.js
```
The three usernames are the accounts `prepare-test-fixtures.js` picked; it prints this last command with them filled in. `Password123!` is the local test password **that script sets on a local database** — and `test-suite.js`'s own default for the admin and investor logins — so it exists only where the script has written it. A refreshed copy accepts no known password at all: `refresh-env.js` gives every account its own random secret, so on a fresh copy nothing signs in until `prepare-test-fixtures.js` has run.

**The other half of the test story: the standalone runners `npm run test:unit` drives.** These are plain `node scripts/test-<thing>.js` — **no server, no fixtures, no sheet override, no rate-limit window** — and each exits 1 on failure. They are the only tests you can run on a whim, and several are explicitly load-bearing elsewhere in these docs: `test-db-export-guard.js` (lifts `requireRole` into a bare `new Function`, which is why the CSRF check must stay self-contained), `test-csrf-write-header.js` (pins the two duplicated guard copies identical), `test-invoice-owner-guard.js` (the only authorization coverage on the invoice pdf/submit routes), `scripts/check-ratecon-address-parsing.js` (16 verbatim production addresses locking `cityStateZip()`), plus `test-truck-retirement.js`, `test-investor-expense-scoping.js`, `test-period-lock-queue.js`, `test-payout-carry-freeze.js`, `test-google-timeout-retry.js` (locks the Google API retry-on-timeout behaviour a googleapis major would silently break), `test-eld-feed-staleness.js` (the ELD feed-silence sweep — the alarm on the estimated-pay-basis fallback) and the rest of the money-math set. Added 2026-09-23 and load-bearing the same way: `test-password-change-enforced.js` (the forced-change gate, copied into both guards and pinned identical), `test-login-session-rotation.js`, `test-load-ownership-guard.js` (the three-valued `loadBelongsToDriver()`), `test-jt-cache-isolation.js` (fails if a route writes to the shared Job Tracking cache), `test-image-limits.js` with `test-image-limits-regression.js` (every image guard ahead of its decode), `test-public-form-input.js`, `test-expense-load-window.js`, and `test-deploy-scripts.js`, `test-deploy-record.js` and `test-deploy-live.js` + `test-drift-gate.js` (the deploy lock, exact-SHA deploys, the verified-deploy record, the live commit and the rollback target, the pm2 restart proof, the deploy action's steps and the drift gate, run against the real scripts), `test-session-sockets.js` + `test-socket-session-client.mjs` (a socket ends with its session; the client's reconnect ladder), `test-sanitize-before-transfer.js` + `test-refresh-sign-in.js` (a refreshed copy accepts no known password; `REFRESH_OPERATOR_PASSWORD` reaches one Super Admin and nothing but `refresh-env.js`; `prepare-test-fixtures.js` refuses a deployed database by any name), `test-routemate-vehicle-sync.js` (the list-outage handling) and `test-invoice-week-selection.js`, which also covers the undated-load ledger. Added 2026-09-24: `test-invoice-driver-name-matching.js` (one driver in two spellings is one weekly invoice; numbering never reuses a number; a PDF is only ever replaced by its own regeneration; the invoice's pay lookups against the P&L's own code; a mutant per money guard). **Run the ones covering what you touched before reaching for `test-suite.js`** — they are seconds, not a 15-minute window. ⚠️ **`ls scripts/test-*.js` under-reports.** The runner takes every `scripts/` file matching `^(test|check)-.*\.(js|mjs)$`, so it also picks up the `scripts/test-*.mjs` client-logic runners and `scripts/check-ratecon-address-parsing.js` — which is the load-bearing one named two sentences up. `node scripts/run-unit-tests.js` prints the authoritative list.

**The suite cannot be run twice inside 15 minutes** — it exhausts its own rate limiters (`exportLimiter` is 20/15min), so a second back-to-back run returns 429 across the export and statement tests and looks like a regression. Wait for the window, or compare against a run from the same cold start. Covers auth, role gating, debug-endpoint auth, webhook secret, chat file validation, canceled-load exclusion. Exits 1 on any failure. When editing `server.js`, run `node --check server.js` before committing (one file — a syntax error anywhere breaks the whole app).

## Browser end-to-end harness (`scripts/e2e/`)

A Playwright (`playwright-core`) harness that drives the real UI in Chrome for Testing, headed so a person can watch or headless, and writes a verdict and a screenshot per step. In this repo "test" means this: a real browser run through the UI, locally **and** on staging. The full reference is [`scripts/e2e/README.md`](../../scripts/e2e/README.md).

- **It is NOT part of `npm run ci`.** It is its own npm package: the root `npm install`, CI and the deploy never install it, and `run-unit-tests.js` only runs the top-level `scripts/{test,check}-*` files. Install it with `npm --prefix scripts/e2e ci`. The browser is the Chrome for Testing that the app's `puppeteer` already downloaded (`CHROME_PATH` overrides).
- **Local recipe** (Node 22.23.2; in a worktree, prefix each command with `fnm exec --using=22.23.2`):
  1. `setup-db.cjs <work dir>/qa.db` takes a read-only `.backup()` of the main checkout's `app.db` and sets four logins on the copy.
  2. `verify-creds.cjs` checks those logins against the copy.
  3. `prep-worktree.sh` links the main checkout's installs, `.env` and key, and builds `client/dist`.
  4. `boot-server.sh <worktree> <port> <db>` starts the server on the copy.
  5. `BASE_URL=http://127.0.0.1:<port> PHASE=after DB_PATH=<db> node scripts/e2e/e2e.mjs` runs the harness.
  6. `stop-server.sh <port>` stops that server.
- **Staging:** `BASE_URL=https://staging-app.logisx.com` plus `CREDS_FILE=<staging logins>`, and no `DB_PATH`. The planted steps SKIP. ⚠️ A full run creates, edits and deletes `QA-TEST-*` trucks there; `ONLY=signout` only signs in and out.
- **Safety rails:**
  - It refuses `app.logisx.com`.
  - The server binds 127.0.0.1 and refuses ports 3000/5173 and busy ports. It runs with every integration and default-ON alert forced off and every outbound credential blanked. It refuses a `SPREADSHEET_ID` that is unset, empty or production's, and it is stopped by its recorded PID, never `pkill`.
  - ⚠️ **The DB copies are unsanitized production data.** They, the logins, the screenshots, the results and the logs live in the work dir: `E2E_WORK_DIR`, default `$TMPDIR/logisx-e2e`, created 0700, and refused inside a checkout.
  - Identity documents are masked in saved screenshots.
- **The login limiter** allows 20 sign-ins per 15 minutes per server process. A full run uses 11, so restart the server between full runs.
