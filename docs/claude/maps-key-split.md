# Maps key split — one key cannot be restricted, two can
`GET /api/config/maps-key` publishes a Maps key to every visitor. That is by design (the SPA needs one), so the **only** thing standing between that key and an arbitrary bill is a Google Cloud console restriction. Audited 2026-08-08: there was **none** — no application restriction and no API allowlist, verified empirically (Geocoding returned `OK` from an off-VPS IP with no `Referer`; Places New `searchNearby` returned results with a bogus `Referer`; the legacy Directions API — which this app never calls — also returned `OK`, proving no API allowlist; every denial seen was the project-level *"This API is not activated on your API project"*, never the key-level *"This API key is not authorized to use this service or API"*). Prod and staging share the identical key.
- **⚠️ The two restriction types are mutually exclusive, which is why one key can never be locked down.** A referrer-restricted key is refused outright by the legacy web services (`API keys with referer restrictions cannot be used with this API`) and, having no `Referer` to match, by Routes/Places (New) too — so it breaks **every server call**. An IP-restricted key cannot drive the Maps JavaScript API at all — so it breaks **every map**. Anyone "just adding a referrer restriction" to the shared key takes the dashboard, tracking, geocoding and rate-per-mile down at once.
- **The split**: `GOOGLE_MAPS_API_KEY` = server key (IP-restricted to the VPS; Geocoding + Distance Matrix + Routes + Places (New)). `GOOGLE_MAPS_BROWSER_KEY` = browser key (referrer-restricted; Maps JavaScript + Places). Only the browser key is ever served by the endpoint. Unset → falls back to the server key, i.e. deploying the split changes nothing until a second key exists.
- **This moves the expensive SKU off the public key.** `places:searchNearby` with `fuelOptions` (~$0.16–0.32 per fan-out) is called **only** from `lib/poi-fuel-stops.js`, server-side — so it belongs on the IP-restricted key and becomes unreachable from the published one.
- **⚠️ A referrer restriction is anti-scraper, not anti-attacker.** `Referer` is client-supplied and forgeable with one curl flag. It stops the realistic abuse (a harvested key embedded in someone else's *real website*); it does not stop a determined caller. The actual spend ceiling is the **API allowlist plus per-API quota caps and a budget alert** in the console — set those, not just the referrer.
- **⚠️⚠️ The VPS talks to Google over IPv6, so an IPv4-only allowlist breaks everything.** `76.13.22.110` is the address the box is *reached* on; it is not the address it *leaves* from. `maps.googleapis.com` resolves AAAA-first and the box prefers v6, so both curl and the Node runtime egress from **`2a02:4780:59:f4fb::1`** (proven: `curl -w '%{local_ip}'` and `socket.localAddress`/`remoteFamily` both report the v6 address against `2001:4860:…`). An IP allowlist containing only the IPv4 address would silently 403 **every** Geocoding / Distance Matrix / Routes / Places call in production. Allowlist **both** — and re-check after any VPS network change, because this is invisible until it breaks.
- **n8n was the third caller. It no longer calls Maps at all** (applied live 2026-08-09). The node was **`Get Distance Matrix`**, whose only consumer was `Calculate RPM + Details`; both are deleted, live and in `Dispatch-v2-fixed.json` (45 → 43 nodes). It was the **only** node in the workflow referencing `maps.googleapis.com`, so **the server key can now be IP-restricted to the VPS without breaking email-ingested rate-per-mile**: the app computes it in `POST /api/loads/from-ratecon` via `calculateRatePerMile()` (`lib/ratecon-load.js`), and n8n already calls back into the app for extraction.
  - ⚠️ **Earlier revisions of this file named the node "Google Maps Distance" and said it read `{{ $env.GOOGLE_MAPS_API_KEY }}`. Both were wrong** — no node by that name ever existed, and the key was a **literal string** in the node's `key` query parameter, not `$env`. The `$env` story mattered because it implied the node was already broken (n8n Cloud blocks `$env` by default) and therefore harmless; in fact it held a live, working, plaintext key. Do not reason about an n8n node from this file alone — read the live workflow over the API.
  - ⚠️ **That key must still be rotated — but not for the reason first written here.** A prior revision of this bullet claimed the literal "survives in version history" because `GET /workflows/:id` returns an `activeVersion` snapshot plus `workflowPublishHistory`. **That was measured and is false:** the PUT republishes, so `activeVersion` was refreshed to the 43-node state and the whole GET body now contains **zero** `AIzaSy` occurrences (it had two before: one in `.nodes`, one in `.activeVersion.nodes`). What could *not* be verified is n8n Cloud's internal workflow history — `GET /workflows/:id/versions` and `/workflow-history/workflow/:id` both **404** on the public API, so "no copy reachable via the API" is not "no copy exists," and execution data from past runs is a separate store entirely. **Rotate it anyway:** a key that sat in plaintext in a third-party SaaS is exposed regardless of who can still read it back, and **deletion is not revocation**.
  - The pair was already dead code: `Get Distance Matrix` had **zero inbound edges** so it could never fire, and `Calculate RPM + Details` had no other inbound edge and an empty output. Its `parseFloat` of an unparseable rate also yielded `NaN`, which is why `calculateRatePerMile()` deliberately coerces to `0` instead.
  - **⚠️ It was orphaned because an LLM replaced it, and the replacement never called Maps.** ~~The live distance path is `Addresses Ready?` → `AI Agent` …~~ **Resolved 2026-08-09** — the `AI Agent` branch is deleted and n8n now calls `POST /api/n8n/load-distance`. See "Distance runs in the APP too, not n8n" above for the measurement, the `output`-column trap, and the response-shape rule. The point that survives: **nothing in n8n touches a Google Maps API any more**, so `GOOGLE_MAPS_API_KEY` can be IP-restricted to the VPS without breaking email-ingested rate-per-mile.
- `GET /api/weather` (`server.js`) is **dead twice over**, and is kept only as a stub. (a) It calls `weather.googleapis.com/v1/forecast:lookup`, which **does not exist** — verified with no key sent: that path returns **404 `text/html`**, while the real methods `currentConditions:lookup` and `forecast/days:lookup` return 403 JSON. (b) Nothing calls it: `TrackingMap.vue` has the weather UI but its fetch is disabled (`// Weather fetch disabled to reduce Google API costs`), so `weatherData` stays `null` and the markup never renders. It uses **`GOOGLE_MAPS_API_KEY`**, so if it were ever revived it would need the Weather API enabled on the server key — until then the Weather API does **not** belong on either allowlist.
