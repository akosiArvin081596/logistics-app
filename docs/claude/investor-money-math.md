# Investor trip expenses have a MONTH dimension — reassigning a driver used to restate closed months
`getInvestorDriverSet()` answers *"who is on my trucks **right now**"* and has **no month dimension at all**. Six `expenses` queries used it as an unbounded OR leg (`owner_id = ? OR LOWER(driver) IN (<the live set>)`), so the moment a driver was reassigned onto an investor's truck, **every receipt he had ever filed** — on a different truck, stamped `owner_id = 0` at insert — became a deduction in that investor's already-finalized months.

Measured on production 2026-08-13: one driver moved from a fleet truck onto an investor's truck, and four earlier months restated at once, all downward, none of the receipts that investor's. The frozen `investor_payouts.amount` for those months stayed correct; only the portal's live recompute moved, by the contaminating receipts' total.

- **⚠️ It was ONE-SIDED, which is what made it look like "the app is cutting my earnings in half".** Revenue scopes off the sheet's `Owner ID` column and driver pay reaches drivers through those same load rows; fixed costs scope off `truckChargedInMonth()`. All three correctly ignored the new driver in the old months. **Only costs moved, and only downward.** A symmetric error would have been obvious; this one just looked like less money.
- **The frozen ledger was never wrong** — `reconcileInvestorPayouts()` refreshes `amount` only while `status='owed' && !finalized_at && !isLocked(period)`, so those four figures are pre-contamination and are the **ground-truth oracle** for the fix. The bug lived entirely in the live recompute the portal renders. **Fixing it restates no ledger row**; only 2026-08, the one open month, legitimately moves (≈ +$567 of investor share, from removing $1,133.25 of another owner's costs).
- **`getInvestorDriverMonthWindows()`** (beside `getInvestorDriverSet`, and deliberately so — *the set decides WHO, the windows decide WHEN*) returns `Map<driverLower, [{from,until}]>`. Every window is the **intersection** of the assignment (`truck_assignments.start_date .. end_date`) with the truck's own billing life (`truckChargeFromMonth()` .. `truckChargeUntilMonth()` — the **same** predicate the fixed-cost math uses, not a second copy). A driver sitting in a truck that is not yet in service is not yet an expense.
- **`investorExpenseScopeSql()` is the single builder, six callers** (`/api/investor` monthly + category + all-time, `computeInvestorMonthlyEarnings` monthly + drill-down items, `/api/investor/expenses`, `/api/investor/tax-csv`). The old shape was one SQL string hand-copied six times, which is how a fix to one becomes a fix to none — same lesson as `DRIVER_RENAME_TARGETS`.
- **⚠️ THE MONTH WINDOW ALONE IS NOT ENOUGH; `COALESCE(truck_unit,'') = ''` is the other half of the guard.** `owner_id = 0` is **ambiguous** — `expOwnerId` is `driverTruck ? driverTruck.owner_id : 0`, so it means *either* "no truck resolved at insert" *or* "resolved to a fleet-owned truck". `truck_unit` is what separates them. Concretely: a driver who moves trucks **mid-month** shares that month with both owners, so a month-only bound re-admits the receipts he filed on the **old** truck days before the move (Shorn's 2026-08-04 receipts, $1,118, on a truck he did not leave until 2026-08-12). The fallback may only ever admit a row **no owner is stamped on**.
- **⚠️ `""` MEANS UNBOUNDED AT BOTH ENDS**, the same convention as `truckChargedInMonth()` and with the same inversion risk corrected in PR #205 and again in PR #216. `intersectMonthWindow()` is written as max/min over the **non-empty** operands so `""` can only ever defer to the other bound, never win. An empty intersection returns `null` = *"never yours"*, never *"always yours"*.
- **⚠️ `truck_assignments.start_date` / `carrier_driver_history.started_at` are ISO UTC INSTANTS, unlike `in_service_date`/`retired_at` which are bare calendar days.** `'2026-08-01T02:30:00.000Z'.slice(0,7)` reads `'2026-08'` for a moment that is 2026-07-31 21:30 in Houston — and that is a money boundary. They go through `assignmentMonthKey()` → `houstonDay()`; bare `YYYY-MM-DD` is still **sliced as a string**, because `new Date('2026-08-01')` is UTC midnight = the previous Houston day (the inversion documented above `truckChargeFromMonth`).
- **Leg coverage is deliberately a SUBSET of the set's four.** Kept: (A) `truck_assignments` × owned trucks; (B) `trucks.assigned_driver` where the assignment table knows nothing about that truck (it has only existed since 2026-04-17); (C) `carrier_driver_history` bounded by its **own** `started_at`/`ended_at` — columns that have always been written and that the set's leg 3 simply ignores. **Dropped: the live `drivers_directory` carrier match**, which is a present-tense assertion with no clock and would re-create the bug. Verified on production that every directory-matched driver already has a covering `carrier_driver_history` row, so nothing lost coverage.
- **⚠️ Leg C is a LAST RESORT, not a peer — it runs only for a driver legs A/B could not place at all.** It is carrier-level and carries no truck, so it can start months before that driver's truck entered service; and because windows are deduped by subsumption, the wider carrier window then **swallows the correct truck-bounded one**, handing the driver exactly the over-long reach this whole change removes. (Fixture: carrier history from 2026-06, truck in service 2026-10 → comes back 2026-06.) **Clamping leg C to the fleet's billing life does not fix it and was tried first** — the fleet is the *union* of every owned truck, so one long-serving truck makes the clamp vacuous for everyone else. A known truck pairing is strictly better evidence than a carrier-name one. This also self-corrects stale data: Jayden Morrison's `carrier_driver_history` row under this carrier is still open even though he moved to a fleet truck on 2026-08-12, and leg A's closed stint (`2026-08`..`2026-08`) is the accurate answer.
- Windows are **deduped by subsumption** — clause count grows with assignment history and history only grows. Production collapsed 11 raw windows to 4.
- **Fixed at the same time: the Fixed Costs drill-down printed arithmetic that did not add up.** `fixedCostBreakdown` is a **present-tense fleet rate** built from `allOwnedTrucks` with **no in-service gate** (only the retirement bound), and `EarningsSection.vue` rendered it beside the month-gated `selected.fixedCosts` as one equation. July 2026 read `$3,310 + $100 + $2,410 + $233 + $97 = $3,043/mo` — a left side of $6,149.16 against a right side of $3,043.33, on an investor's money screen, where the $3,106 excess **was the second truck**. `monthlyEarnings[].fixedCostComposition` now comes from `getMonthlyFixedCostParts()`, the same gated loop that produces the total, so the parts sum by construction at every month. `fixedCostBreakdown` is unchanged for the surfaces that legitimately want a current rate. In a zero-activity month the **money** is zeroed with `fixedCosts` but `truckCount` stays truthful — the deferred copy reads "your N trucks were inactive" off it.
- Locked by `node scripts/test-investor-expense-scoping.js` — **69 assertions, 7 mutants**, run against a real SQLite database seeded with the production shape (so a builder emitting valid-but-wrong SQL fails). Includes a **§0 that reproduces the pre-fix numbers** on the same fixtures — so the expectations are a fix and not a preference — and a **§5 universal** that no admitted row may carry another owner's stamp, checked across the whole cross-product rather than on the one row that broke.
## The three "cosmetic" leftovers, all closed 2026-08-14 — two of them were not cosmetic
- **⚠️ `parseFloat(config.investor_split_pct) || 50` read a configured `0` as `50`, because 0 is falsy.** That is the direction that moves money: an investor set to **0%** would have been paid **half of net profit** — on every screen *and* in the payout ledger, with every figure agreeing perfectly, so nothing would look wrong. **`resolveInvestorSplitPct(config)`** is now the single reader (1 definition, 7 callers: `GET /api/investor` twice plus its published `investorSplitPct`, the statement (`computeInvestorMonthlyEarnings()`), the ledger reconcile (`reconcileInvestorPayouts()`), the PDF report (`GET /api/investor/report`) and the load report (`GET /api/investor/load-report`); the tax CSV reads no split). Missing/unparseable still falls back to 50 — only an explicit finite number is honoured — and the result is **clamped to 0..100**, because the value comes from a free-text config row where `500` would otherwise pay 5× net profit and a negative would invert the split and bill the investor. The client already used `?? 50` (nullish), so a server-sent 0 survives the wire; that is asserted, not assumed.
- **⚠️ `Math.min(idx, len-1) || len-1` made the EARLIEST month unreachable.** One expression doing two jobs: it used falsiness to mean *"not initialised yet"*, but a legitimately clamped **0** is also falsy — so an investor viewing their first month was silently thrown to the current one by any refetch (the `@changed="loadData"` the exclude-day / add-day actions emit). An explicit `monthIdxInitialised` flag separates "first load" from "the user picked index 0", and re-arms on an empty `months` so a preview switch still lands on its own current month. **Genuinely cosmetic only in that no number was wrong** — the month you were reading just changed under you.
- **`driverPayFormula` invented numbers it did not have.** The empty state asserted a flat `= $250 × …` (wrong by $100/day for an investor whose truck is $150), the multi-rate branch printed the literal string `"$rate"` (reads as an unsubstituted template variable), the percentage branch printed `"driver %"`, and the drill-down hint printed `× $${d.dailyRate || 250}/day` — a rate the server never sent, in the one place an investor goes to check the arithmetic. All four now **drop** an unknown rather than defaulting it, falling through to prose that is true at any rate. **The rule: this annotation sits beside real money, so a rate stated here is read as fact — never substitute one the component does not have.**
- Locked by §9 (the resolver, incl. `0` staying `0` and both clamps) and §10 of `scripts/test-investor-expense-scoping.js`, which **extracts the month-watcher body out of the SFC and runs it**, with the retired body run through the same driver as a control so the section cannot pass on an inert extraction. ⚠️ That harness needs the body in an **IIFE with the flag written back in a `finally`** — the body's early `return`s skip a trailing assignment, which pins the flag to `false`, makes every case look like a first load, and reads exactly like a passing fix.

## `GET /api/investor/report` was missing insurance entirely — a category ABSENT, not miscomputed
Found in the sweep above and fixed 2026-08-14. `insurance_monthly` appeared **nowhere** in that handler — a grep across all ~430 of its lines returned zero hits — so every downloadable P&L understated `totalExpenses` by the full insurance accrual while `/api/investor` and the payouts ledger both billed it. **$6,460/month fleet-wide**; **$17,430** already absent across the three investors at the time of the fix (`LogisX-#33` $8,150, `Logisx-#91` $1,680, `LogisX-#302` $7,600). An investor comparing the report to their portal saw two different numbers, and **the report was the flattering one**.
- **⚠️ It is NOT folded into Compliance / Regulatory.** The client defined that bucket on 2026-04-13 as exactly *"the ELD, HVUT, IRP added up and divided by 12 months"*; quietly widening a category they named is how the next reconciliation argument starts. Insurance gets its own printed P&L row, the same treatment `truck_payment_monthly` already got when it was split out of the ELD line.
- The per-truck loop now calls the shared **`truckMonthlyFixed(t)`** and buckets its parts, instead of hand-rolling `eld + hvut/12 + irp/12`. That is what makes the report and the portal unable to disagree about what a truck costs per month — and it is why the omission was possible at all: a hand-rolled sum has no way to notice a missing term.
- **Fixed at the same time: `ownerEarnings` was a hardcoded `netCashFlow * 0.5` with a hardcoded `(50%)` in two labels**, on a statement whose entire job is to agree with the portal — which reads `investor_split_pct`. The handler already merged `investor_config` at the top, so it was one line. A **no-op at today's config** (every investor is 50), which is exactly why it would have gone unnoticed until the first investor on a different split, who would have been shown a payout figure that was wrong *and* a label asserting the wrong rate. **Superseded 2026-09-30:** `ownerEarnings` is no longer a split of anything; see the next section. The split still labels the row.
- **⚠️ The guard for this is STRUCTURAL, and it has to be — no value-based test finds an absent category.** The report added up perfectly, to the wrong total. §8 of `scripts/test-investor-expense-scoping.js` parses `truckMonthlyFixed()`'s **own return shape** and asserts every part except `total` is read by the report's loop and reaches `totalExpenses`. Add a sixth fixed cost to that helper and the run fails until the report decides which bucket it belongs in — the decision that was skipped the first time. It also pins the `plLines.length - 3` page-break index (adding a row shifts every absolute index) and runs its negative assertions against a **comment-stripped** copy, since the comments deliberately quote the old hardcoded forms.


## `GET /api/investor/report` READS the payout ledger; it does not compute a payout (2026-09-30)
The downloadable report printed **Investor Payout (X%)** and **Owner Earnings (X%)** as `(revenue − expenses) × split` over the report period. That is a formula of its own, with **no driver pay, no idle-month rule, and no loss carry-forward**. So it printed **more** than the portal and the payouts ledger for the same month, and a **negative** payout for a month with no activity, which the ledger never does. On a local copy of production the gap per month was exactly the missing driver pay × split, plus any carried-in loss, and an idle month showed its fixed costs × split as a negative payout.

- **The payout is now the SUM of the monthly payouts the ledger and the portal publish**, over the months the report's range covers. Three module-scope helpers beside `reconcileInvestorPayouts()`: `investorReportPayoutEntries()` (the reader), `summarizeReportPayout()` (pure: which months, how much) and `reportPayoutNote()` (pure: the sentence printed under the P&L). None of them applies a split or walks the carry. For an investor (or a Super Admin previewing one), the months come from **`reconcileInvestorPayouts()` itself**. A completed month is its row's `effectiveAmount`, the figure the Payouts page lists and the statement prints. The open month is `currentMonth.payableIfClosedNow`, the portal's "projected payout if the month closed today". For a Super Admin who is not previewing, the report is fleet-wide and has no ledger, so it runs `computeInvestorMonthlyEarnings({ isSuperAdmin: true })` plus `computeLossCarryForward()`: the same array and walk as the Super Admin's own portal view.
- **⚠️ A frozen month prints its SETTLED figure, never a recompute.** A paid or processing row, a row with `finalized_at`, or a row in a closed period (`periodWriteLocked`) is read through the reconcile, so its `amount` is whatever the reconcile left there, which for a frozen row is the settled amount. The report adds the recorded correction, exactly as `effectiveAmount` does, and nothing else. That is the statement's rule (`lib/payout-statement.js`): *"The settled figure is the one that was paid; it always wins."* A paid month with a correction recorded on it prints its settled amount plus the correction, never the live recompute. The P&L lines above it are live, like every other line of the report, so the note under the P&L then names that month with the Payouts page's own sentence (*"Your payout for June 2026 is the amount that month was settled at. The figures above reflect current records, which have changed since it closed."*), and names a corrected month separately.
- **⚠️ The report now RECONCILES, i.e. it writes, exactly as opening the Payouts page does**: it inserts a row for a completed month that has none, and refreshes an `owed` row's amount only while the month is still open. Reading the rows back without the reconcile would need a second copy of its refresh guard (`status`, `finalized_at`, `periodWriteLocked`), and a second copy of a money rule is how two surfaces drift apart. The fleet-wide report writes nothing.
- **A day range takes whole months.** `reportRangeMonthKeys()` maps the `start`/`end` date strings to month keys **by string slice**, because `new Date('2026-08-01')` is UTC midnight, i.e. 2026-07-31 in Houston. A month is in the range when its key falls between them, so a report from May 15 to Aug 2 pays May through August in full. A payout is settled per month, and half of one does not exist. The note names the months. Since the choices below, `start` and `end` are checked first (`reportDateRange()`), and `reportRangeMonthKeys()` reads the checked range; a date that is not a real day is 400, not unbounded.
- **Also wrong for the same reason, and fixed with it:**
  - **Driver pay** is now its own P&L line and part of **Total Expenses**, as it is in the portal's `totalExpenses`. It is the monthly driver pay the ledger settles on, over the same months. So **Net Profit / Net Cash Flow, Net Revenue To Date, Payoff Progress and Business ROI** now deduct it as well.
  - **The fixed-cost lines** (Insurance, Compliance / Regulatory, Truck Payment) charge only the months the shared computation charged (`summary.chargedFixedMonths`: a month with `fixedCosts > 0`). An idle month is charged $0 there, and a month before the investor's first load has no figure at all, so neither is charged here. Per month, the trucks and their cost are the same as `getMonthlyFixedCosts()` (Active trucks in scope, `truckChargedInMonth()`, `truckMonthlyFixed()`), so the three lines add up to the ledger's fixed costs over the range. **`truckMonthsInPeriod()` is gone.** It counted months from a truck's in-service date with day granularity, so it charged insurance for months the ledger never charged.
  - **Left alone on purpose:** the trip-expense lines keep the report's own caller-supplied range on plain `date` (the operational basis §11 of `test-investor-expense-scoping.js` pins). The same goes for Gross Revenue's own date filter and the all-time `maintenance_fund` / `compliance_fees` sums, which are empty in production. So a mid-month range can still show a Net Profit whose split is not the payout, and the note says which months the payout covers. **That is now the `"exact-dates"` setting of `RANGE_MODE`**; the shipped `"whole-months"` widens the range to whole months before any line reads it (see "The report's choices" below).
- On the local copy of production, after the fix, every all-time report equals the ledger to the dollar, and the fleet report equals the Super Admin portal. The fixed-cost lines equal the ledger's fixed costs over the range.
- Locked by `node scripts/test-investor-report-payout.js`. It lifts the real `reconcileInvestorPayouts()` and runs it against a real SQLite `investor_payouts` table, fed a fixture monthly array with a driver-pay month, an idle month, a loss month, a carry-forward month and the open month. Each month must equal both the ledger's own published figure and a hand oracle. A paid, corrected row and an owed row in a closed period print their stored figures and are left unchanged. The fixed-cost block is extracted from the shipped handler and run. Its mutants: the old `(revenue − expenses) × split` formula (caught on the driver-pay, idle and carry months), the handler reverting to it, driver pay dropped from Total Expenses, and the fixed-cost loop charging the idle month. `test-truck-retirement.js` now counts **six** `truckChargedInMonth()` gates and names the report's.

## `GET /api/investor/report` counted cancelled and soft-deleted loads (fixed 2026-09-30)
The report reads Job Tracking with its own `values.get` and deduplicates it, but until then it never ran **`excludeDroppedLoads()`**, the one place that decides whether a load is live (CLAUDE.md, "Load exclusion is centralized"). `/api/investor` and the payouts ledger (`computeInvestorMonthlyEarnings()`) both drop such rows, so the report disagreed with them, in two different ways:
- **A soft-deleted load keeps its completed status on the sheet**, so it counted in every revenue figure: Gross Revenue (and through it Net Profit, Net Revenue To Date, Payoff Progress and Business ROI), the Total Revenue and Avg Revenue / Load KPIs, Completed Loads, Total Jobs and the Monthly Revenue table. On a local copy of production's data (the non-production sheet and a copy of `app.db`), the one `deleted_loads` row, `Test load 1234`, is in a completed status with a Payment and Owner ID 5: owner 5's report and the fleet report both printed Gross Revenue at the portal's figure **plus** that load, to the dollar.
- **A cancelled load was kept out of Gross Revenue only by the completed-status test.** It still counted in Total Jobs and, when it had a Payment, in the Monthly Revenue table, which tests no status at all. On the same copy that was 33 cancelled rows, across nine months of the fleet report's table.
- **The fix is one statement:** `excludeDroppedLoads()` on the deduplicated rows, before the first row is read, the same rule and the same order (deduplicate, then exclude) as `liveJobTrackingView(await getJobTrackingCached())` in `/api/investor`. The handler's rows are its own read, not the shared Job Tracking cache, so reassigning `jobTracking.data` there is safe (see `liveJobTrackingView()`). After it, on the same copy, the fleet report's Gross Revenue, Completed Loads, Total Jobs and Monthly Revenue table follow the live rows only, and owner 5's, owner 41's and the fleet's Gross Revenue equal the portal's `totalRevenue`.
- **Still different from the portal after this fix:** the Monthly Revenue table counted a live load in **any** status with a Payment. Fixed the same day; see the next section.
- Locked by `node scripts/test-investor-report-dropped-loads.js`. It lifts the handler's data section (from resolving whose report it is to the last figure before the PDF) out of `server.js` and runs it against a sheet fixture on production's real header row and a real SQLite `deleted_loads` table: two cancelled spellings, a soft-deleted load, a soft-deleted `#`-spelled id, and three loads in progress. An investor's report, a Super Admin's preview of it, the fleet report and a one-month range each count only live loads, against a hand oracle. Its exclusion mutant removes the exclusion and must bring back exactly the soft-deleted loads.

## The report's Monthly Revenue table counted loads still in progress (fixed 2026-09-30)
`GET /api/investor/report`'s Monthly Revenue table added up every live load with a Payment, whatever its status. Gross Revenue, just above it, counts completed loads only (`delivered`, `completed`, `pod received`), and so do the portal's monthly figures (`/api/investor`'s `monthlyData`). So a load At Shipper or At Receiver showed in the table and not in Gross Revenue, and the table's months did not add up to it.
- **Measured on a local copy of production's data** (the non-production sheet and a copy of `app.db`): live loads still At Shipper or At Receiver put the table above Gross Revenue for the month they fell in. Every other month already matched.
- **The fix:** the table now tests the same status column (`rptStatusCol`) with the same regex (`rptCompletedStatuses`) as the Gross Revenue loop. It holds no copy of the rule. After it, on the same copy, the table sums to Gross Revenue for the fleet and for owners 5, 41 and 42, and each month equals the portal's `monthlyData`.
- **Total Jobs is unchanged:** a load in progress is still a job. It is just not revenue yet.
- **Left alone:** the table keys months with `new Date()` and the server's local month, while the portal keys them with `moneySheetDate()`. On the copy every month came out the same both ways. A completed load whose date does not parse still counts in an all-time report's Gross Revenue and in no month of the table. The copy has none.
- Locked by the same runner, `node scripts/test-investor-report-dropped-loads.js`. §1 pins the table to Gross Revenue's own status column and regex. In §2, every case's table must sum to its Gross Revenue. In §3, the mutant without the table's status test must put the in-progress loads in the table and nowhere else. The mutant without both fixes must print exactly what the report printed before either fix.

## `GET /api/investor/tax-csv` counted every copy of a load, and read a carrier database it never requested (fixed 2026-09-30)
The tax CSV reads Job Tracking with its own `batchGet`. Two things were wrong with that read.
- **"Net Revenue to Date" summed the RAW completed rows.** The report and `/api/investor` both keep one row per load id (`deduplicateLoads()`: the most recent copy of a re-entered load). They then drop cancelled and soft-deleted loads (`excludeDroppedLoads()`). The CSV did neither. So a load re-entered on the sheet counted once per copy, and a soft-deleted load still in a completed status counted at all.
  - Measured on the same local copy: the sheet holds older copies of re-entered load ids, all of them completed, plus a soft-deleted test load, and the fleet CSV counted every one of them. After the fix it prints the report's and portal's Gross Revenue minus the same expenses.
  - **The fix** applies the same two steps as the report and `/api/investor`, in the same order: `deduplicateLoads()`, then `excludeDroppedLoads()`, both before the first row is read. Nothing in the handler copies either rule.
- **"At-Risk Capital Remaining" moved with it.** It is `max(0, purchase price + startup − Net Revenue to Date)`, so an overstated revenue understated it. No other line of the CSV reads the sheet, and none changed.
- **The carrier database was always empty.** The handler asked `batchGet` for one range, `["Job Tracking"]`, and then read `valueRanges[1]` as the Carrier Database. The Sheets API answers one value range per range requested. Against the local non-production sheet `valueRanges.length` was 1, so `valueRanges[1]` was `undefined` and `parseSheet()` made it an empty sheet. Because of that, `getInvestorDriverSet()` lost its drivers-directory leg without a sign. The CSV now reads the directory the way `/api/investor` and the report do: `getCarrierDBFromSQLite()` (the directory replaced the Carrier Database sheet). On the local copy, every driver the directory leg finds is also found by another leg, so no figure moved there. The runner's fixture has a driver that only the directory ties to the investor.
- Locked by `node scripts/test-investor-tax-csv.js`. It lifts the real handler out of `server.js`. The `batchGet` stub answers like the API, with one value range per range requested. It runs against a real SQLite database: `deleted_loads`, `drivers_directory`, `truck_assignments` and `carrier_driver_history` are created from `server.js`'s own DDL. The fixture holds re-entered loads (one spelled with `#`), soft-deleted loads, a cancelled load, a load in progress, a Rejected expense, and a blank-Owner-ID load run by a driver that only the directory ties to the investor. The fleet CSV, an investor's CSV and a Super Admin's preview of it must print the hand oracle, At-Risk Capital included. Its mutants remove the deduplication, remove the exclusion, and bring back the `valueRanges[1]` read. Each must be caught and must print exactly what that step alone was keeping out. With all three reverted, it must print exactly what the CSV printed before the fix.

## `GET /api/investor/tax-csv` counted loads stamped to another owner, and priced every truck at the config default (fixed 2026-09-30)
Two more ways the tax CSV disagreed with the report and the portal.
- **Whose loads.** The CSV counted a Job Tracking row for an investor when its Owner ID named them **or** its driver was one of theirs. The portal (`/api/investor`), the payouts ledger (`computeInvestorMonthlyEarnings()`) and the report trust a filled-in Owner ID, and fall back to the driver only when it is blank. So a load stamped to another owner, or to a company truck (`0`), counted in the investor's CSV whenever one of their drivers ran it.
  - After the fix, each investor's CSV "Net Revenue to Date" is that investor's report Gross Revenue less the CSV's expense basis (the report's trip-expense lines). The fleet CSV scopes no owner and did not move.
  - **The rule, as the portal applies it:** a filled-in Owner ID decides. It is the investor's when it names their `users.id`, read with `parseInt` (so `" 5 "`, `"05"` and `"5abc"` name user 5). It is not when it names anyone else, and `"0"` and text that does not start with a number (read as 0) name no investor. Only a blank Owner ID (empty or spaces) falls back to the driver, matched against `getInvestorDriverSet()` after `trim().toLowerCase()`. A Driver cell that reads as a built-in property name counts as blank (`driverNameForTotals()`).
  - **The fix is one helper, `investorJobRowTest(headers, investorOwnerId, investorDriverSet)`**, beside `getInvestorDriverSet()`. It returns a row test, and the CSV and the report both use it. ## The report's choices: `lib/investor-report-options.js` (2026-09-30)
Three choices the downloadable report and tax CSV make were settled by the owner on 2026-09-30, pending the client's review. Each is **one switch or one text table in `lib/investor-report-options.js`**, the one place to change it. The module is pure (no I/O, no require); `server.js` requires it once as `investorReportOptions` and passes each switch explicitly, so a runner can hand a handler either setting.

| Switch | Shipped | Other setting | What it decides |
|---|---|---|---|
| `RANGE_MODE` | `"whole-months"` | `"exact-dates"` | A date range that starts or ends mid-month. `"whole-months"`: the start moves to the 1st of its month and the end to the month's last day before any line reads them, so revenue, trip expenses, Driver Pay, the fixed costs and the payout all cover the same months, and the period label prints the whole months. `"exact-dates"`: revenue and trip expenses cover the dates as given, Driver Pay, the fixed costs and the payout cover whole months (the report before this change). |
| `UNPRICED_TRUCKS` | `"not-available"` | `"zero"` | A truck with no recorded purchase price (a price is recorded when `trucks.purchase_price > 0`). `"not-available"`: a per-truck figure is the average over the priced trucks ("Not recorded" when none has a price); a figure that needs every truck's price reads "Not available" while any truck lacks one; the report prints a footnote and the CSV a count row. Never a silent $0. `"zero"`: such a truck is $0, unflagged (the documents before this change). |

- **To flip a switch:** change its one line (`const RANGE_MODE = "whole-months";` → `"exact-dates"`, or `const UNPRICED_TRUCKS = "not-available";` → `"zero"`) and ship it like any code change. A value that names no setting stops the server at start-up (and fails `scripts/test-investor-report-options.js` in CI) rather than quietly picking one. `GET /api/investor` answers `reportRangeMode` (the `RANGE_MODE` value), and the client shows the hint under the report's date inputs only for `"whole-months"`, so flipping `RANGE_MODE` hides the hint with no client change. ⚠️ The hint's TEXT is copied in `client/src/lib/investorReportText.js` (the client cannot require this file); change both.
- **The text tables:** `NOTE` (every sentence the line under the Income Statement prints, as `{placeholder}` templates, the ones from before this change word for word), `UNPRICED_TEXT` (`Not recorded`, `Not available`, the footnote, the CSV count row's label), `RANGE_HINT` and `DATE_ERRORS`. Every one is listed in `docs/investor-portal-copy.md` §16, awaiting the client's approval.
