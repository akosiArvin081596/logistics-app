# The user routes are finance routes — guards on `PUT`/`DELETE /api/users/:id`
Both cascade into `expenses` and both can restate a **finalized** month. `DELETE` got its guard in PR #205; `PUT` is the same cascade by UPDATE and got the matching one (with the identical `expenseRowPeriodLocked()` / `blockedExpensePeriods()` / fail-closed / guard-before-first-write shape, and **not** gated on `PERIOD_FINALIZE_ENABLED`).
- **⚠️ `driverName: ""` on `PUT` DEFEATED the `DELETE` guard, and that is why the two must stay paired.** `PUT`'s cascade only fires `if (oldName && newName)`, so a blank cleared `users.driver_name` and touched nothing else. `DELETE` then resolves its cascade name as `driver_name || username`, falls back to the **username**, matches zero expense rows, finds no blocker and succeeds — leaving the receipts filed under a name with no account behind them, and silently re-adopted by the next user created with that name. Measured on production 2026-08-08: 165 rows / **$38,476.33** in finalized months were reachable this way (Howard Reddie 75 / $18,381.23; Shorn King 90 / $20,095.10).
  - **`PUT`'s blank-name guard counts other spellings; `DELETE`'s removals do not, on purpose.** `DRIVER_NAME_IN_USE` counts expenses, documents and the truck under every spelling the cascade would take (a doubled or edge space, see [`identity-collation.md`](identity-collation.md)), so blanking is refused while any of them remain. `DELETE` removes `expenses`, `messages`, `notifications`, `driver_locations`, `load_responses` and `documents` by `LOWER(col) = ?` alone, the stored spelling with case aside. Its expense lock check (`userDeleteLockBlockers()` (1)) uses the same match, so every expense it removes was judged; the other tables carry no period. For a removal that is the safe direction. A row under another spelling is neither judged nor removed, so it stays in every month it was counted in, and no closed month loses it. Widening the removals would permanently delete receipts and documents filed under another spelling, and would need the expense check widened in step: more destruction, for a cleanup gain. The cost is that those rows stay behind under a spelling no account holds, and the delete's reported counts do not include them. The truck is the one leg matched wider, because it is cleared and its assignment closed, not deleted (`findTruckForDriverAccount()`).
- **409 codes:** `PERIOD_FINALIZED` (rename or blank touching a locked month; role change de-listing a settled payout), `DRIVER_NAME_IN_USE` (blanking a name that still has **expenses, documents or an assigned truck**, *even in an open month* — the stranding; `messages`/`notifications`/`driver_locations`/`load_responses` are counted and reported but deliberately do not block, being operational chatter; every count goes through the cascade's own legs, so rows under another spacing of the name count too, and the truck is `findTruckForDriverAccount()`'s — see [`identity-collation.md`](identity-collation.md)), `DRIVER_NAME_TAKEN` (renaming onto another account's driver name irreversibly merges two people's finance rows; also another account's username, or a reserved name — asked through `findDriverNameClash()` with `exceptUserId`, so names that differ only in case or spacing count as the same name, see [`identity-collation.md`](identity-collation.md); re-spelling the account's own name is not a rename, except onto the exact spelling, case aside, another account's driver name already has, which is refused the same way), `LAST_SUPER_ADMIN`, `CANNOT_DELETE_SELF`, `PERIOD_LOCK_UNREADABLE`, plus 400s `INVALID_ROLE` / `INVALID_DRIVER_NAME`. Added with the unified cascade: `CONCURRENT_MODIFICATION`, `RENAME_REQUIRES_SHEET`, `SHEET_UNREADABLE`, `DRIVER_RENAME_IS_MERGE`, `INVOICE_ALREADY_PAID`, `INVOICE_WEEK_COLLISION`, `TARGET_UNREADABLE`, plus 500 `UPDATE_ROLLED_BACK`. **None are exercised by `test-suite.js`** — the harness only calls `GET /api/users`. `DELETE`'s whole cascade now runs in **one `db.transaction`** (500 `DELETE_ROLLED_BACK` on failure) — it had no try/catch, so a throw mid-cascade left the finance rows gone and the account intact.
- **⚠️ `PUT` hashes the password ABOVE the guards, and must keep doing so.** The handler is `async` and `await bcrypt.hash` is its only yield point; sitting between the guards and `UPDATE users` it held the loop open ~100 ms inside a check-then-act. Two concurrent requests (`PUT A {"role":"Driver","password":…}` + `PUT B {"role":"Driver"}`) both passed the last-Super-Admin check and **left zero Super Admins** — reproduced against a mutant build, which returns 200/200 and 0 admins where the shipped code returns 409 `LAST_SUPER_ADMIN`. Hashing first leaves no `await` between check and write.
- **A role change is a settlement event.** `listSettlableInvestors()` drives `GET /api/payouts` off `users WHERE role = 'Investor'`, so demoting an Investor drops their settled months out of every payouts surface while the rows sit in `investor_payouts`, and `grandTotals.totalPaid` quietly falls. Keyed on **`user.id`, never the role column** (#205's lesson: those tables record no role). Production carries 19 finalized payout rows across 3 investors, 2 already PAID.
- **⚠️ There is now exactly ONE driver-rename cascade, and `DRIVER_RENAME_TARGETS` is it.** `PUT /api/users/:id` used to carry its own hand-written rename — 8 UPDATEs over 7 tables against `fix-driver-name`'s 19 targets — so a rename made from the Users screen left `invoices`, `truck_assignments`, `carrier_driver_history`, `drivers_directory`, `driver_onboarding`, `load_ratings`, `job_applications`, `users.full_name`, `routemate_dvir` and `routemate_hos_daily` pointing at the old name. Both routes are now thin callers of `planDriverRenameSqlite()` (count + lock-judge, read-only) and `applyDriverRenameSqlite()` (one transaction). **Add a target to the list and both routes get it** — patching one route's list only resets the drift clock.
  - **Every leg also takes the driver's other spellings** (a doubled or edge space) unless another account the rename leaves alone still holds that name, decided once per rename by `driverRenameWidens()` and seen by the planner, the lock judgement, both collision probes, the merge scan and the executor alike; `fix-driver-name` also rewrites the sheet's matching cells. A change of internal spacing is **not** money-neutral, so no lock is relaxed for it, and `fix-driver-name`'s `caseOnly` carve-out holds only while no row on the sheet or a money leg moves from another spelling. That includes the driver's own `drivers_directory` row: stored as `"Shorn  King"`, it is counted as another spelling (`variantRows`), because `getInvestorDriverSet()` leg 2 keys it trimmed and lowercased and the rename changes that key. A row differing only by edge spaces keeps its key and is not counted. Both routes' audit lines list such rows by id with the spelling each had (`spacingVariants`; `PUT /api/users/:id` in its `update_user` line), since renaming back does not restore them. Detail in [`identity-collation.md`](identity-collation.md).
  - **The users route's guard now covers the whole list**, not just `expenses`. `invoices` is the leg it used to write with no check at all: one production driver carries 13 rows, 8 already PAID, in finalized months.
  - **`opts.userId` narrows only the two `users` legs**, and only for the users route. Those legs match by NAME (`users_full_name` is `LOWER(full_name)=? AND role='Driver'`), so unscoped they can rewrite a *different* account that happens to share a full name. `fix-driver-name` has no id and keeps the name-matched form.
  - **409 `RENAME_REQUIRES_SHEET`** — `PUT /api/users/:id` does **not** write the Job Tracking `Driver` column and never has. Rather than half-rename, it refuses when the sheet still carries the old name and points at `fix-driver-name`, which moves sheet + database together and offers `?dryRun=true`. Fails closed (`SHEET_UNREADABLE`) when Job Tracking cannot be read. When the cascade takes the driver's other spellings (the lock guard's `widens`), a cell under another spacing of the old name counts too: the cascade would move that load's directory row, truck and expenses away from it. **⚠️ It reads RAW `values.get`, not `getJobTrackingCached()`** — that helper returns `deduplicateLoads()` output (last row per load id wins), which on the local sheet hid **8 of 28** matching rows. A duplicate-load-id row carrying the old name is a real row `fix-driver-name` would rewrite, so counting the deduped view would let the partial rename in through the guard built to stop it.
  - **409 `DRIVER_RENAME_IS_MERGE`** — guard (b) `DRIVER_NAME_TAKEN` only asks whether another *account* holds the name, but `drivers_directory` has its own lifecycle, so a name with rows and no user row is ordinary. The route runs the shared merge scan and refuses, pointing at the one route with a dry run and a by-id reversal recipe. Two carve-outs are required or it refuses the commonest real rename: a **case-only** change self-matches every leg, and the **`users`/`users_full_name`** legs self-match the account being edited (`jsmith` → `John Smith` matches its own `full_name`). The scan compares case-insensitively and cannot see a **spacing** variant, so a `drivers_directory` row that differs from the new name only in case or spacing (`findDriverNameClash(driverName, { users: false })`) also counts, as `mergeTargets.drivers_directory` — skipped when the new name is the account's own name re-spelled.
    - **The rename's own rows are self-matches, row by row** (`driverRenameMergeScan(new, { oldLower })`, shared with `fix-driver-name`): a row the cascade moves for the old name — its other spellings, and its own directory row — is not counted. So re-spelling `"Shorn King"` onto `"Shorn  King"`, the spelling the driver's own directory row carries, is no longer a false `DRIVER_RENAME_IS_MERGE`. While another account holds a spelling of the name the cascade takes none of them, and rows under the new spelling still count. It is not a blanket skip like the case-only one, and Job Tracking rows under the new spelling still count: re-spelling the truck and directory row to match them would pull those loads into an investor's driver set, whose readers do not collapse internal spacing, in months this route cannot judge. A re-spelling onto another account's exact spelling stays `DRIVER_NAME_TAKEN` (guard (b)).
  - **⚠️ `user` is re-read AFTER the last `await`, and every guard runs on that copy.** "No await between guard and write" is only half the rule; the other half is "no state read *before* the last await". The row was fetched at the top of the handler and the guards reasoned about that snapshot across ~100 ms of bcrypt and then a full sheet read — long enough for another request to promote, demote or rename the same account, yielding either a stale-role skip of the last-Super-Admin check (zero Super Admins, terminal) or a stale `oldName` that matches nothing while `UPDATE users` still writes the new name (account says one thing, every finance row another). A changed row now returns 409 `CONCURRENT_MODIFICATION`.
  - The cascade runs **before** `UPDATE users` and both sit in one `db.transaction()`: the cascade matches the account's *current* `driver_name`, so writing `users` first would blank the value the `users` legs match on. It also lets an explicit `fullName` win. `syncDriverToCarrierSheet` is then called with the **new** name as `oldName` — `drivers_directory` is a cascade target now, so looking it up by the old name misses and that helper's miss branch **inserts a duplicate directory row**.
- **⚠️ `match` and `writes` are independent, and storage case is a function of WHEN a row was written.** Three tables flipped from display case to lowercase at a single datable watermark — `notifications` at id 54 (2026-05-09 13:05), `load_responses` at id 15 (2026-05-11 14:47), `invoices` between #40 and #86 — once each, with no interleaving. So `notifications`/`load_responses` were matched on an *exact lowercase* value and silently skipped every pre-watermark row (37 + 12 for one driver); they now match case-insensitively. And `invoices` now **writes lowercase**, matching its own two INSERT paths (`driverName.toLowerCase()` — since 2026-09-24 `canonicalDriverName(driverName).toLowerCase()`, the identity's own spelling — and `payee.toLowerCase()`). Match wide; write the column's own convention.
- **⚠️ `invoices.driver` case is NOT cosmetic — `idx_invoices_driver_week` is a UNIQUE index on `(driver, week_start)` with BINARY collation**, so a mixed-case row sits outside the one-invoice-per-driver-week guarantee. Production carries exactly one such row (invoice #40, `"Shorn King"`, PAID, inside two locked periods) against 13 lowercase rows for the same driver. **The four readers were fixed 2026-08-09; the row was deliberately left alone** — normalising it is a write into a closed month, and the index is still BINARY (see below).
  - `GET /api/invoices/:id/pdf` + `PUT /api/invoices/:id/submit` did `invoice.driver !== (user.driverName||"").toLowerCase()` — a **one-sided** fold that 403'd the only currently active driver on his own paid $1,500 invoice, while the list that showed it to him used `LOWER(driver) = ?` and rendered it fine. Both now call the shared **`driverOwnsInvoice()`**, which folds both sides through `normalizeDriverName()`. Measured before/after against `origin/main`: 403→200 on the display-case row, 200→200 on the lowercase one, **403→403 on another driver's** (the fold must not widen access).
  - `driverOwnsInvoice()` also **refuses an empty session `driverName` outright** rather than comparing it. The old code compared `"" !== ""` and *granted* a blank-named Driver access to any blank-driver row — reproduced as a 200 on the unfixed build. Zero such invoice rows exist in production, so the narrowing costs no real access.
  - `generateInvoiceNumber()` used `driver = ?` against an already-lowercased parameter. That COUNT **is the sequence suffix**, so a week already holding a display-case invoice restarted at `-01` and minted a **duplicate invoice number** (measured: it re-mints `INV-SK-2026W19-01` over an existing row). Now `LOWER(driver) = ?`, agreeing with the duplicate guard in `generateInvoiceHandler` that always used `LOWER(driver)`. (Since 2026-09-24 both match through `normalizeDriverName()`, and the number also skips any number or PDF name another row holds — see the invoices section of [`backend-server.md`](backend-server.md).)
  - `PUT /api/invoices/:id/restore` compared two stored values, so it *looked* symmetric — but BINARY equality meant restoring a soft-deleted `"shorn king"` row for a week already covered by live `"Shorn King"` found no clash. Reproduced on the unfixed build: the restore **succeeded and left two live weekly invoices on one driver-week**. Now 409 — and since 2026-09-24 the check is `liveWeeklyInvoicesForDriverWeek()`, which matches through `normalizeDriverName()`, so a spacing variant (which the NOCASE index lets in) is refused too.
  - **✅ SHIPPED — the write side** (verified 2026-09-19: `INVOICE_WEEK_IDX_COLS` in `server.js` is `invoices(driver COLLATE NOCASE, week_start) WHERE deleted_at = '' AND is_manual = 0`, with the collision pre-flight, the temp-index-first rebuild, and a predicate testing for both `WHERE` *and* `NOCASE`. Everything the paragraph below asks for was built. Invoice **#40** is still deliberately unnormalised — that part stands.) The original analysis, kept because it explains why the shape is what it is: `COLLATE NOCASE` was deliberately NOT added to `idx_invoices_driver_week` in that PR. Folding readers fixes *reads*; the index is a *write-time* constraint, and while its collation is BINARY the two spellings remain two index entries, so a second live weekly invoice for one driver-week is still structurally insertable. It is also **not** a substitute for the reader fix: in SQLite the collation of `driver = ?` comes from the column's declared collation, never from an index, so a NOCASE index changes no query's semantics. The blocker is the migration shape at ~2508: it `DROP INDEX`es then `CREATE UNIQUE INDEX` inside a try/catch that only `console.error`s, so a single case-insensitive collision would leave the table with **no unique index at all**, silently — strictly weaker than today. Measured 2026-08-09: production currently has **zero** such collisions, so it would succeed; ship it only with a collision pre-flight that leaves the existing index in place on failure, and note the rebuild predicate keys on `/\bWHERE\b/` and needs widening or it never fires.
- **⚠️ `DRIVER_RENAME_HARD_BLOCK_CODES` outranks BOTH escape hatches** — `acknowledgeLockedPeriods` *and* the `caseOnly` money-neutral carve-out. A locked period is a decision a human can own; these two are not. `INVOICE_WEEK_COLLISION`: folding two spellings onto one name puts two rows on one `idx_invoices_driver_week` entry and the UPDATE throws — and because the sheet is written **first**, the throw lands as `PARTIAL_RENAME`. The probe must cover **old ∪ new**, not just old: old-vs-old is the case-only rename, but old-vs-**new** is the reachable one, because `fix-driver-name` *permits* merges (`isMerge` only warns). `TARGET_UNREADABLE`: a money-bearing target that cannot be read cannot be confirmed free of finalized rows — same reasoning as `PERIOD_LOCK_UNREADABLE`, and `planDriverRenameSqlite` must not swallow it into `rows: 0`, which is fail-**open**.
- **⚠️ The two `dispatch_notifications` legs are substring rewrites and are the ONLY place the Deshorn/Shorn trap is reachable.** `"Shorn King"` is a literal substring of `"Deshorn King"` — two different people — so the old `REPLACE(title, 'Shorn King', X)` would rewrite a notification about Deshorn to `"DeX"`. `replaceNameOnWordBoundary()` now decides in JS (SQLite's `LIKE`/`REPLACE` cannot express a word boundary) and writes only rows that genuinely change. Every other leg compares whole values and is immune by construction.
- Both routes now write an `audit_trail` row with per-table cascade counts. `PUT` previously logged **nothing at all**; a password change is recorded as `password reset`, never a value.
- **A driver-name change ends the account's sessions, exactly as a role change or a password reset does, through BOTH rename routes.** Login copies `users.driver_name` into the session as `driverName` and nothing re-reads it — `refreshPasswordChangeFlag` refreshes only the password flag, and `GET /api/auth/session` returns the copy as stored — yet every Driver-scoped check reads that copy: `loadBelongsToDriver()`, `driverOwnsInvoice()`, the `GET /api/driver/:driverName` guard, and the live-update room, which is derived from the session the socket read at its handshake. New expenses, documents and messages are also filed under it (`resolveDriverActor()`, `POST /api/messages`). So both routes call `purgeUserSessions()`, which ends the accounts' live-update sockets too:
  - `PUT /api/users/:id` purges when the account's stored name changes. The `update_user` audit line records the count (`sessions revoked: N`).
  - `PUT /api/admin/fix-driver-name` purges every account whose stored name its cascade changes. `driverRenameAccountIds()` reads them through the cascade's own `users` leg (same target, WHERE and written value), after the route's last await and immediately before the cascade, so the set is exactly what the cascade changes. Nothing is revoked on a dry run, a refusal, a failed sheet write or a rolled-back cascade (`PARTIAL_RENAME`). The `fix_driver_name` audit line carries `sessionsRevoked`.
  - **⚠️ Any change to the STORED value counts: case-only, whitespace and a cleared name included.** The copy's readers do not all normalise the name the same way, so no "same name, different spelling" carve-out is right for all of them. A case-only rename is also still a rename: the cascade moves every row to the new spelling, and a surviving session would keep filing new rows under the old one. The comparison is against what is actually written (trimmed), so resending the same name with stray padding revokes nothing, and neither does a case-only `fix-driver-name` over an account already spelled the new way.
  - `email`, `full_name` and `company_name` are cached in the session too, but no authorization or scoping decision reads them, and no route writes `username`, so none of them revokes. The cascade's `users_full_name` leg therefore revokes nothing either. A new check that reads one of them from the session must add it to the revocation condition.
- **A self-edit spares the session making the request, and `refreshOwnSession()` rebuilds it.** Either route spares the caller's own session, so an admin is not signed out mid-request. When the caller changed their own role, driver name or password, that spared session is rebuilt from the account row with the fields login writes, **under a new session ID**, exactly as change-password does. The response carries the new cookie, and the old ID's live-update sockets end and reconnect on it. A Super Admin who demotes themselves is refused as one on their next request, and no copy of the old cookie outlives a password reset.
  - **⚠️ A new ID, not an in-place edit.** Once the old ID is removed from the store, the old identity ends everywhere it was presented at once: the socket connection gate refuses a session ID the store no longer has, and a copied old cookie stops authenticating.
  - It runs **after** the audit line, which keeps recording the identity that was authorised to make the change.
  - **⚠️ It checks the session is still in the store before rebuilding it.** Both routes await before they write, and the requesting session can be revoked in that window (a password reset or delete by another admin). Rebuilding it would mint a fresh session for the identity just revoked, so such a session is ended instead. So is one whose account row cannot be read.
  - A store that fails to delete the old ID is logged, as a failed `purgeUserSessions()` is, and that ID stays in the store. If the failure is in the rotation, this browser is still answered with a session that holds no user.
  - Editing someone else, or only a profile field (email, full name, company), leaves the editor's session and sockets alone.
- Pinned by `scripts/test-session-sockets.js` §3b–§3d, which run both shipped routes against real sessions and sockets (fix-driver-name on the real cascade), with §8 source pins and §9 mutants.
- **Availability guards, checked before the period guard** because they have no remedy: a Super Admin cannot delete their own account (`CANNOT_DELETE_SELF`, matched on session id **or** username so a session predating `user.id` cannot fail open), cannot delete the last Super Admin, and cannot **demote** the last Super Admin. All three are required — without the demotion twin, `PUT {"role":"Driver"}` then `DELETE` walks around the pair.
