# Identity collation — a case-insensitive reader over a case-sensitive constraint
A driver's name is a **money join key** (`getDriverPayStructures()`, `getInvestorDriverSet()`, `expenses.driver`, `invoices.driver`), and every reader folds case. Two of the columns holding it did **not**, which is the worst combination: the readers merge the spellings, the constraints permit them.

- **`drivers_directory.driver_name` is now `UNIQUE COLLATE NOCASE`** (rename-recreate migration beside the table's `CREATE`). Before it, `"SHORN KING"` inserted *beside* `"Shorn King"`, and because `getDriverPayStructures()` keys on `LOWER(driver_name)` into a plain object with **last row wins**, the shadow row's default `pay_daily 0` beat the real row's `300` — `resolveDailyRate()` then fell back to the truck's `$250`. **Silent, and it is payroll**: on production that is $50/day against the only driver with a rate set, while the original row still reads 300 in the UI.
  - **⚠️ The uppercase variant is the only client's DEFAULT, not an exotic input.** `AddDriverForm.vue` emits `form.driver.trim().toUpperCase()`, so re-adding an existing driver from the Add Driver screen sends exactly the string that minted the shadow.
  - **⚠️ The migration's DDL is rebuilt from `PRAGMA table_info` at runtime, never hardcoded.** Column order genuinely differs between a fresh install (`pay_daily` inline in the `CREATE`) and a migrated one (`pay_daily` arrives by `ALTER`, so it is last). A hardcoded `CREATE` + `INSERT … SELECT *` transposes columns on one of the two shapes — `pay_daily 300` landing in `pay_percentage` is a 300% revenue share. Both shapes are regression-tested.
  - **⚠️ It SKIPS, loudly, if case-duplicates already exist** — never "resolves" them. An unguarded `INSERT … SELECT` throws (reads as "migration failed", so the collation quietly never lands) and an `INSERT OR IGNORE` silently **drops a row**. Which spelling is the real driver is a business question — see the Deshorn/Shorn trap below. Production had **zero** duplicates when this shipped (verified read-only).
  - **Sessions are deliberately NOT cleared.** The two precedents (`users`, `investor_applications`) clear them because a rebuilt `users` table can change a role a live session carries; nothing in a session derives from `drivers_directory`, so forcing every driver to re-login would be pure cost.
  - `getDriverPayStructures()` is the last line of defence on a database that could not migrate: it now reads `ORDER BY id` and keeps the **first** occurrence, so the *established* row wins rather than the newly-minted shadow, and logs the ignored rows. **Its key is `normalizeDriverName()` itself**, computed in JS — the function every caller looks up with — so a row is found under any spelling that normalizes to its name, whichever path re-spelled it (`PUT /api/drivers-directory/:id`, or the rename cascade of `PUT /api/users/:id` or `fix-driver-name`). The answer is unchanged from the old SQL key, `LOWER(TRIM(driver_name))`, for every row whose stored name is already trimmed and single-spaced with no capitals outside A–Z, where no two rows share a key.
  - **⚠️ `COLLATE NOCASE` folds case, not whitespace.** `" Shorn King"` still inserts alongside `"Shorn King"`, which is why `POST /api/drivers-directory` trims at the boundary. Internal whitespace (`"shorn   king"`) is a genuinely **different** name to `getInvestorDriverSet()` — see the `caseOnly` note in `fix-driver-name` — so it is deliberately not folded in storage, in the constraint or in that reader. **The one exception is the create-time clash check** (`findDriverNameClash()`, below), which *refuses to create* such a name rather than folding any stored value — the safe direction, because every ownership check already treats the two as one driver.
- **`POST /api/drivers-directory` is a create verb again.** It was `INSERT OR REPLACE` on a UNIQUE column, i.e. delete-then-insert, so `{"headers":["Driver"],"values":["Shorn King"]}` blanked every column it omitted. PR #216 put the PUT's month-end predicate on that path, which closed the *closed-month* half and explicitly left three things open: an **open** month was still blanked, the replace **changed the row id** (orphaning `legal_documents.driver_id` and the profile picture), and the columns the money guard correctly ignores (address, phone, email, DOT, MC, status) were blanked with no refusal at all. An existing name is now **409 `DRIVER_EXISTS`** naming the row and pointing at the PUT — strictly stronger, and it needs no period data to be right. Blank name is **400 `DRIVER_NAME_REQUIRED`** (it used to insert a nameless row that keys as `""`).
- **`POST /api/users` got the collision check `PUT` has had since #212.** Creating a second account on an existing `driver_name` merges two people's expenses, invoices and documents — every settlement join is `LOWER(driver) = ?` and resolves to both — so it is now **409 `DRIVER_NAME_TAKEN`**. This was also the *front door* on the pay hijack: no check here, plus `syncDriverToCarrierSheet(action:"add")`'s `INSERT OR IGNORE` ignoring nothing when the case differed, minted the shadow directory row **with no period guard anywhere on that path**.
  - **`users.username` is folded in the query, not migrated.** The check compared a **trimmed** needle against the **untrimmed** column and then inserted the raw body string, so `" Bob "` and `"Bob"` coexisted while login (`LOWER(username) = LOWER(?)`) and `DELETE`'s self-delete guard both fold — the undeletable-account state. Trimming on both sides and on the INSERT closes it. **Deliberately no collation migration on `users`**: it fails *closed* (a locked record, not a mis-payment), zero duplicates exist, every reader already folds, and rebuilding that table is the one migration that does force every session to re-login.
  - `driverName` is type-checked (**400 `INVALID_DRIVER_NAME`**) and `bcrypt.hash` is hoisted **above** the guards — same check-then-act as #212's security round, and `users.driver_name` has no UNIQUE index to catch the race the way `username` does.
- **One naming check: `findDriverNameClash(name, opts)` / `findDriverNameClashes(name, opts)`**, beside `normalizeDriverName()` in `server.js`. Every path that creates or renames a driver identity asks it immediately before its write — accepting a job application, `POST /api/users`, `POST /api/drivers-directory`, `PUT /api/users/:id`, `PUT /api/admin/fix-driver-name`, `PUT /api/drivers-directory/:id` and `syncDriverToCarrierSheet()`'s add branch — and the truck routes resolve a driver's spelling through it (`canonicalDriverName()`, below). It compares through `normalizeDriverName()` (trim, lowercase, collapse internal whitespace), the comparison every ownership check uses (`loadBelongsToDriver`, `driverOwnsInvoice`, the expense and document routes), so the naming answer and the ownership answer cannot disagree. It runs in JS over every `users` row and every non-blank `drivers_directory.driver_name` (a few dozen rows on production) because SQLite cannot express that function: `LOWER` folds ASCII only, `TRIM` strips spaces only, and nothing collapses a whitespace run. It is **synchronous** (better-sqlite3), so a caller can sit it beside its write with no `await` between, and every caller does — **except `fix-driver-name`**, which asks in its plan, before its sheet write (its last `await`), like its merge scan and its collision pre-flight: a refusal found after the sheet is written would leave a partial rename. (`PUT /api/trucks/:id` also resolves its driver's spelling, through `canonicalDriverName()`, before its active-load `await`; a stale answer still names the same driver.) A blank or non-string name never clashes, so each caller refuses a blank name itself (`DRIVER_NAME_REQUIRED`) before asking.
  - **The account side is wider than driver names.** A driver's name, an account's username and the names the app itself uses as identities are the same kind of identifier, so on the `users` side a name is also taken when it equals **any account's username** or a **reserved name** (`dispatch`, `investor`; the list lives inside the function so a lifted copy stays self-contained). Each match is `{ source: "reserved", name }`, `{ source: "users", field: "driver_name" | "username", id, username, driver_name }` or `{ source: "drivers_directory", id, driver_name }`. `findDriverNameClashes()` returns every match in a fixed order (reserved names, accounts by id, directory rows by id); `findDriverNameClash()` returns the first, or `null`. Options: `exceptUserId` / `exceptUserIds` skip those accounts' driver names *and* usernames, never a reserved name; `exceptDirectoryId` skips one directory row; `users: false` / `directory: false` leave a side out.
  - **One operational cost, accepted:** a person who already holds a non-driver account whose username is their legal name (an investor applying to drive, say) is refused at acceptance with the generic message, and nothing edits `job_applications.full_name`. Create the driver account through `POST /api/users` with a distinct driver name instead.
  - **The rule: a naming check must be at least as wide as the widest reader that merges two names** — today that is `normalizeDriverName()`, over every name in the same namespace. Refusing is always the safe direction; nothing stored is rewritten.
  - **Both sides are checked by default; a caller opts out of one**, so a new caller cannot forget the wider answer:

    | Path | Sides asked | On a match |
    |---|---|---|
    | `PUT /api/applications/:id/status` → `Accepted` | both | 409 `DRIVER_NAME_TAKEN`; body is `{ error, code }` only; one `accept_application_blocked` audit row per refusal naming what matched |
    | `POST /api/users` | account side | 409 `DRIVER_NAME_TAKEN`; the message says whether the name is another account's driver name, its username, or reserved |
    | `POST /api/drivers-directory` | directory | 409 `DRIVER_EXISTS` (body unchanged) |
    | `PUT /api/users/:id` guard (b) | account side, `exceptUserId: id` | 409 `DRIVER_NAME_TAKEN`, audited, the message saying which; "is it a change" is decided with `normalizeDriverName()` too, so re-spelling the account's own name is not a clash — unless it lands on the exact spelling (trimmed, case aside) another account's driver name already has, since the finance rows match on `LOWER(driver)` |
    | `PUT /api/users/:id` guard (e) | directory | a directory row that differs only in case or spacing counts as a merge: 409 `DRIVER_RENAME_IS_MERGE` with `mergeTargets.drivers_directory` |
    | `PUT /api/admin/fix-driver-name` | both, `exceptUserIds`: the accounts it renames | another driver's name or a directory row → a merge (`isMerge`, the by-id reversal recipe); a reserved name or another account's username → 409 `DRIVER_NAME_TAKEN`; a directory row when the old name's own directory row is renamed too → 409 `DIRECTORY_NAME_VARIANT` (both hard blocks, below) |
    | `PUT /api/drivers-directory/:id` | directory, `exceptDirectoryId: id` | 409 `DRIVER_EXISTS` naming the other row; re-spelling the row's own name is refused the same way only onto another row's exact spelling, case aside (the pair the NOCASE constraint rejects); the name is stored trimmed, a blank one is 400 `DRIVER_NAME_REQUIRED`, one that is not text is 400 `INVALID_DRIVER_NAME`, and a request without the `Driver` column keeps the name |
    | `syncDriverToCarrierSheet()` add branch | directory | adds nothing — that row is this driver's already (`INSERT OR IGNORE` folds case through NOCASE, not spacing) |

    Acceptance asks both because the account it creates is joined, once onboarding completes, to the directory row of the same name (`checkAndCompleteOnboarding` → `syncDriverToCarrierSheet`), so a directory-only driver is as much an existing identity as an account. `POST /api/users` asks only the account side: giving a login to a driver who is already in the directory is the ordinary way such a driver gets one. `POST /api/drivers-directory` asks only the directory: a row for a name an account holds is that account's own row (an accepted applicant gets one only once onboarding completes). A **first** driver name set through `PUT /api/users/:id` is the same "give a login to a directory driver" case, so it links to that driver, and the add-branch rule keeps the sync from adding a second row.
  - **A truck names its driver by the spelling that driver already has.** `canonicalDriverName(name)` returns an account's driver name, else the driver's `drivers_directory` spelling, else the trimmed input (usernames and reserved names are not driver identities and are never substituted). The account's spelling comes first because it is the one a driver's own session looks the truck up by (`LOWER(assigned_driver) = LOWER(?)` in the driver app's routes); a directory-only driver gets the directory's. `POST /api/trucks` and `PUT /api/trucks/:id` resolve `assignedDriver` through it before their guard, so the lock check, `assignDriverToTruck()`, `trucks.assigned_driver`, `truck_assignments` and the directory sync all see one spelling. That is resolve, not refuse, on purpose: the route already accepts any name (the Trucks form picks from the directory; a new name gets a pending directory row, as before), and `assignDriverToTruck()` releases the driver's previous truck by case-insensitive equality, which does not fold spacing — so a second spelling would leave two trucks naming one driver.
    - **`PUT /api/trucks/:id` compares DRIVERS, not spellings, when it decides whether the edit moves a driver.** The Trucks screen sends the driver only when it changed, but an older page or a direct API caller may still re-send the stored driver on every save, and the resolved spelling can differ from the stored one; the active-load check (`checkDriverActiveLoad()`) and the previous driver's directory sync both run only when `normalizeDriverName()` says the driver changed — otherwise every save of a truck whose driver is on a load would be refused by that driver's own load.
    - Both truck routes answer **400 `INVALID_DRIVER_NAME`** to an `assignedDriver` that is not text, before anything is resolved, awaited or written; `null` still means no driver, like `""`.
  - **The directory sync and the driver page find a driver's row the same way** (2026-09-26): `findDirectoryRowForDriver()` is the row equal to the name case aside, else the first row by id that `findDriverNameClashes(name, { users: false })` matches. `syncDriverToCarrierSheet()`'s `update` and `delete` and `GET /api/driver/:driverName` use it, so a row stored with a doubled or edge space is refreshed, removed and read rather than skipped. A row found only through `normalizeDriverName()` keeps its stored spelling unless an explicit `oldName` rename asks for another. `scripts/test-directory-spacing-match.js`.
    - **The driver's truck is found the same two ways, by one helper**: `findTruckForDriver()` (the truck naming the driver case aside, else the first by id that `normalizeDriverName()` matches). The sync, `GET /api/driver/:driverName` and `GET /api/driver/me/truck-photo` use it, so the page and its photo name one truck. The routes the driver app calls for what the page lists compare names through `normalizeDriverName()` too: `GET /api/driver/truck-documents/:id/view` (the active assignment, else the truck's `assigned_driver`), `GET /api/driver/shared-documents/:id/download` and `POST /api/drivers-directory/:id/profile-picture`; a blank session name is still refused. `scripts/test-driver-page-role-gate.js` §6. The users routes find it the same way too, through `findTruckForDriverAccount()` (below): the truck `PUT /api/users/:id` counts when it blanks a driver name (`DRIVER_NAME_IN_USE`) and the one `DELETE /api/users/:id` clears (with its open assignment). Other name-keyed truck reads still fold case only — the dispatch Owner ID stamp, the expense truck stamp, the public tracker's unit and `assignDriverToTruck()`'s release — and `resolveTruckForDriverName()` (fuel, position) answers from the active assignment first.
    - **The rename cascade's `drivers_directory` leg renames that row too** (`match: "directory_row"` on `DRIVER_RENAME_TARGETS`, resolved by `driverRenameDirectoryRowId()`): the row `findDirectoryRowForDriver()` finds for the old name, by id, so a row stored under a spacing variant of it moves with the driver, and the sync after `PUT /api/users/:id` adds no second row at the default terms. The `DIRECTORY_NAME_COLLISION` pre-flight counts that row as well. The merge scan still asks case-insensitively; each route's naming check finds a spacing variant of the new name. Two directory rows for one driver are not both renamed (the column is UNIQUE): the one `findDirectoryRowForDriver()` finds moves, and the other is left for a person to resolve.
    - **Every other leg takes the driver's other spellings too** (2026-09-26). Each `"ci"` and `"ci_driver_role"` leg of `DRIVER_RENAME_TARGETS` matches `LOWER(col) = ?` **or** one of the column's stored spellings that `normalizeDriverName()` reads as the old name — a doubled or edge space, or a capital `LOWER()` cannot fold (it folds ASCII only). `driverRenameSpellings()` resolves those spellings in JS (`SELECT DISTINCT` of the column, then `normalizeDriverName()`), and they are bound as one JSON array through `json_each(?)`, so the placeholder count never changes and an empty array is exactly the old match. So a rename moves the rows a driver's spacing variants hold on the money legs — `trucks.assigned_driver`, `truck_assignments`, `carrier_driver_history`, `users.driver_name` / `full_name`, `expenses`, `invoices` (written lowercase, as always) — and on the cosmetic ones. The planner counts them (`variantRows` per target), the month-end lock judges them, the `invoices` week-collision probe and the `DIRECTORY_NAME_COLLISION` pre-flight probe them, and `PUT /api/users/:id`'s blank-name counts (`DRIVER_NAME_IN_USE`) count them, through the same WHERE the executor writes with.
      - **⚠️ One decision per rename, `driverRenameWidens()`.** The planner asks it once and returns it as `widens`; the executor asks once, before its first write, and resolves every leg's rows before writing any (it writes `users` part-way through its legs, so asking again later could answer differently); `fix-driver-name` hands the plan's answer to the executor and to `driverRenameAccountIds()`, so a change during its sheet write cannot widen the rename past the rows the plan judged.
      - **The Job Tracking sheet moves with it.** A rename that moved a driver's directory row, truck and expenses away from a spelling the sheet still carries would leave those loads resolving to the default rates — a partial rename. So when the cascade widens, `fix-driver-name` rewrites a `Driver` cell that `normalizeDriverName()` reads as the old name, lock-judges its month like any other, and `PUT /api/users/:id` refuses such a cell as `RENAME_REQUIRES_SHEET` (it does not write the sheet).
      - **⚠️ A change of internal spacing is NOT money-neutral**, which is why none of this relaxes a lock: `getInvestorDriverSet()` folds with `trim().toLowerCase()` and `getDeductibleExpensesByDriverMonth()` keys on `LOWER(driver)`, and neither collapses internal whitespace, so moving a row from `"Shorn  King"` to `"Shorn King"` can move an investor's driver set and a percentage driver's deductible. `fix-driver-name`'s `caseOnly` carve-out therefore holds only while the rename moves no row from another spelling on the sheet or a money leg (`moneyNeutral`; a notification or message in another spelling moves no figure); `PUT /api/users/:id` judges the lock on every rename, as it always did. Rows moved from another spelling are not restored by swapping the names back, so `fix-driver-name`'s audit line lists them by id and sheet range with the spelling each had (`spacingVariants`), and its reversal recipe says so.
    - **⚠️ A row another remaining account holds is never taken.** A legacy account spelled `"Shorn  King"` beside the real `"Shorn King"` normalizes to the same name, so the helpers above would otherwise hand it the real driver's row — and the pay terms on it. `syncDriverToCarrierSheet()`'s `delete` (called by `DELETE /api/users/:id` after its own account row is gone) deletes nothing, and logs it, while any remaining account's `driver_name` normalizes to the deleted name, whichever way the row matched. The rename cascade takes a row it found only through `normalizeDriverName()` — the directory row, and every other leg's spacing variants — only when no account the rename leaves alone still holds that name (`driverRenameWidens()`: the accounts it moves are the one `PUT /api/users/:id` edits, by id, or the ones `fix-driver-name`'s `users` leg matches case-insensitively); a case-aside match moves as the case-insensitive match always did. The users routes' truck lookups apply it through `findTruckForDriverAccount(name, exceptUserIds)`: `findTruckForDriver()`'s truck, unless it names the driver only through a spelling another account holds. `POST /api/drivers-directory/:id/profile-picture` applies the same rule: a Driver whose session name matches the row only through spacing (not equal to it case aside) is refused 403 while another account holds that name. All of them ask one helper, `driverNameHeldByOtherAccount(name, exceptUserIds)`. `scripts/test-directory-spacing-match.js` §3b–§3c; the upload in `scripts/test-driver-page-role-gate.js` §6; the other legs, the sheet and the users routes' trucks in `scripts/test-driver-rename-clash.js` §4d.
  - **Accepting an application hashes first, checks, then writes everything in one transaction.** The temporary password's `bcrypt.hash` is the handler's only `await` and sits above every check; then: application exists (404) → already onboarded (answers "already exists" — its own account is not a clash) → blank name (400 `DRIVER_NAME_REQUIRED`) → clash (409) → the status, the account, the onboarding row and the onboarding documents in one `db.transaction`. A refused or failed acceptance leaves the application's status as it was; a failure part-way leaves no account behind to hold the name and refuse the retry; a double-submitted accept finds the first one's account. The refusal is audited with `logAudit`, not the coalescing `logAuditRefusal` — it needs a Super Admin and a human decision, so it cannot flood, and on a shared login each refused application keeps its own row. The success row quotes the applicant's name through `auditText()` (capped, one line).
  - `scripts/test-driver-name-clash.js` pins the helper's cases (the plural and its skip options included), its agreement with `driverOwnsInvoice()` over a table of spellings in both tables, the three create routes run for real, and seven mutants. `scripts/test-driver-rename-clash.js` runs the rename and assignment paths for real — `PUT /api/users/:id`, `fix-driver-name`, `PUT /api/drivers-directory/:id`, both truck routes and the directory sync — against every rename target with the shipped planner, merge scan and cascade, checks that a re-spelled directory row keeps its pay structure and that the cascade renames a spacing-variant directory row, runs every leg's spacing variants through both routes and `DELETE /api/users/:id` (§4d), pins where each check sits, and catches twenty-eight mutants.
- **The weekly invoice path reads a driver the same way** (2026-09-24). `POST /api/invoices/generate`, the Friday batch, invoice numbering, the existing-invoice check and the invoice readers match through `normalizeDriverName()`, and the invoice's pay structure and truck rate are the P&L's (`getDriverPayStructures()`, the last truck naming the driver). A new `invoices.driver` is `canonicalDriverName()` lowercased — the spelling the identity already has, account first — so every new row of one driver lands on one `idx_invoices_driver_week` entry; stored rows are not rewritten. That index folds case, not spacing, so the one-live-invoice-per-driver-week rule for spacing variants is held by the write (`commitInvoiceWithPdf()`), not the index. Detail: the invoices section of [`backend-server.md`](backend-server.md).
- **`fix-driver-name` gained the `drivers_directory` UNIQUE pre-flight** it was missing — **409 `DIRECTORY_NAME_COLLISION`**, the sibling of `INVOICE_WEEK_COLLISION` and a `DRIVER_RENAME_HARD_BLOCK_CODE` for the same reason: the executor writes every matched row the *same* value, so two rows folding onto one name violate the constraint and the UPDATE throws — and because **the sheet is written first**, that lands as `PARTIAL_RENAME`, the one outcome the route exists to prevent. Probes **old ∪ new**; the merge half (`"Deshorn King"` → `"Shorn King"`, two real people who both hold a directory row) is reachable on every database because `fix-driver-name` *permits* merges. Declared as `uniqueName: true` on the target, so the next target that gains a UNIQUE is one flag rather than a second forgotten pre-flight.
  - **It still mirrors the constraint, and only the constraint** — case-folded `LOWER(TRIM())`, no helper. Two directory rows whose names differ in **spacing** never trip it, because NOCASE does not fold spacing and the UPDATE would succeed; the route refuses that pair separately, as **409 `DIRECTORY_NAME_VARIANT`**, from the naming check next to the merge scan: it would leave two directory rows for what every ownership check reads as one driver. Same remedy — merge or delete the redundant row first.
  - **`DRIVER_RENAME_HARD_BLOCK_CODES` is now five codes**: `INVOICE_WEEK_COLLISION`, `TARGET_UNREADABLE`, `DIRECTORY_NAME_COLLISION`, `DIRECTORY_NAME_VARIANT` and `DRIVER_NAME_TAKEN` (a reserved name or another account's username). None can be waved through with `acknowledgeLockedPeriods`, a dry run reports each as `decision: "block"`, and each has its own `verdict.rationale` — `DIRECTORY_NAME_COLLISION` used to borrow `TARGET_UNREADABLE`'s.
  - The naming check runs in the plan, before `isMerge` is decided and before the sheet is written, so it sits outside the account-read → cascade window `scripts/test-session-sockets.js` §8 pins. It leaves out the accounts the rename moves (`driverRenameAccountIds()`), so renaming a driver to their own username is not a refusal, and it is skipped when the new name is the old one re-spelled.
