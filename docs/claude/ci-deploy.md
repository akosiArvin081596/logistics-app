# CI/CD, deploy and the VPS

**CI/CD (GitHub Actions, added 2026-08-25).** Four workflows — `ci.yml`, `deploy.yml`, `deploy-drift.yml` and, since 2026-09-23, `backup-freshness.yml`; full setup and reasoning in **[`.github/workflows/README.md`](../../.github/workflows/README.md)**.
- **`ci.yml`** — every PR into `main` and every push to `main`. `npm ci` on **both** lockfiles (which is itself the drift test), `node --check server.js`, `npm run test:unit` (every standalone runner but the timing one — see below), `npm run build:client`, plus an assertion that the build actually emitted a bundle. **Pinned to Node 22.23.2 via `.nvmrc` because that is the runtime pm2 executes both apps with** — see the Node table in [`node-and-deps.md`](node-and-deps.md). ⚠️ Do **not** re-align this to the box's `/usr/bin/node` (still 20.20.1): that binary belongs to ~23 other tenants, not to this app.
- **`deploy.yml`** — push to `main` auto-deploys **staging, then PRODUCTION** (`needs: staging`, so production runs only if staging went green). **⚠️ Production auto-deploys with NO approval gate** (enabled 2026-08-25 at the owner's request). What replaces the human: staging as a hard prerequisite, a smoke check plus a public-edge check, and **automatic rollback** — if production fails verification the workflow returns the box to its last *live* commit (the last one started there that still served, else its last verified deploy, and never the commit that just failed unless it is the verified deploy), rebuilds and re-verifies (tested for real). The job still goes red; a successful rollback is not a successful deploy. **Staging deliberately does NOT roll back** — it is the canary and a failure should stay put. **To re-arm the gate, add a required reviewer to the `production` Environment; the workflow needs no change.** Manual dispatch still picks one target and any plain branch, tag or commit name as `ref` (that is the rollback path; letters, digits and `._/-` only, at most 100 characters, no leading `-`, or it is refused before any ssh). The remote halves live in `scripts/deploy/*.sh` and are shared by both jobs via `.github/actions/vps-deploy` so they cannot drift. **Since 2026-09-23 a push deploys exactly its own commit** (`sha: github.sha`) on both jobs, so production receives the very commit its staging job verified: fast-forward only, never backwards (a run that starts after a newer main commit is already *live* prints `DEPLOY_RESULT=noop` and does nothing), with every step of the checkout verified. **⚠️ Since 2026-09-24 the box records which commit it VERIFIED, not which it checked out.** HEAD moves at checkout, before install, build and restart, so a deploy that died after its checkout used to leave HEAD on a commit that never ran. A later deploy of that commit, or of one it contains, was then a `DEPLOY_NOOP` whose smoke check passed on the old process, and the drift check read the box as `in-sync`. The record is the ref `refs/logisx/verified-deploy` inside `.git`: out of the working tree and `git status`, written atomically by `git update-ref`, and it keeps its commit alive through gc; `git reflog show refs/logisx/verified-deploy` lists every verified deploy. Only two things write it. `remote-record-verified.sh` runs from `.github/actions/vps-deploy` after the restart, the smoke check and (production) the edge check all passed, never for a no-op, under the box lock, and only if HEAD is still that commit (a failure there fails a production job, never a staging one). `remote-rollback.sh` writes it once a rollback serves again, but only when its target is not the commit that failed, the deploy reported a consistent record and the rollback's own install and build were clean; it writes the drift marker for the failed commit even when it returns to that same commit, and never replaces a marker that already names main's tip with a commit that is not main's tip (so a failed pin cannot unblock `main`). The drift check reads the record, never HEAD. **The record lags a deploy whose checks passed but whose record step then failed**, so the box also marks every commit it starts (`refs/logisx/started-deploy`, written by `remote-deploy.sh` once pm2 has proven the restart took and reports the app online, and by `remote-rollback.sh` after its own proven restart). **⚠️ Since 2026-09-24 a restart must be proven**: pm2 must exit 0 and the process's `pm_uptime`, read by name from `pm2 jlist`, must change. Otherwise the old process may still be serving, so nothing is marked or recorded, and the deploy (or the rollback) fails. The deploy's *live* commit is that mark while it follows the record and HEAD contains it; otherwise the record. The no-op check and the floor `main` may move back to read the live commit, never HEAD, **whatever the app answers**, and `main` never moves back past a started commit HEAD contains. The rollback target (`DEPLOYED_FROM`) is the live commit only while it is the record or the app answers before the deploy changes anything (3 tries, 2 s apart), else the record. It is also never the commit that run's checks judge unless that is the record, so a heal of a started commit that failed and whose rollback never ran rolls back to the record. The drift check still gives an unrecorded deploy its one heal. Redeploying after a half-finished deploy is therefore a full deploy, of the same commit or of an ancestor; for an ancestor, `main` moves back only across commits past the last live deploy, and only when `origin/main` contains them all. Every deploy warns which commits a rollback of it would drop. With no record (the first deploy after this shipped, or a fresh clone) it fails safe: never a no-op, `main` never moves back, and the drift check compares HEAD as before. The deploy's stdout ends with `DEPLOY_RESULT=deployed|noop`, and the action reads every value from the last whole line of its kind. Production's edge check also asks the live-update (Socket.IO) handshake: the app's own `Origin` must get 200 and, unless the deploy reported that the commit serving predates the Origin check (`DEPLOY_HANDSHAKE_GUARD=0`), a foreign one 403, or production rolls back. Only an unanswered or 5xx request is retried (3 tries, 10 s apart). Each production deploy or heal therefore leaves one `LIVE-UPDATE: … refused … Origin=https://example.invalid` line in the app's log, on purpose. `remote-deploy.sh`, `remote-rollback.sh` and `remote-record-verified.sh` also take a **box-level lock** — `flock -n` on `/var/lock/logisx-deploy<dir>.lock` — so a second deploy of the same app fails fast with exit **75**, which `ssh-retry.sh` never retries; it catches a deploy that did not come through Actions. The native-module probe opens an in-memory `better-sqlite3` database instead of only `require()`-ing it (the binding loads lazily, so `require` alone passes under the wrong Node), and a module still broken after `npm rebuild` fails the deploy before any restart. The build's Node is the interpreter pm2 runs the app with, read by name from `pm2 jlist`'s JSON line (a notice pm2 prints ahead of it changes nothing). A deploy or rollback that cannot read it refuses to build rather than guess with PATH's `node`, which on the box is the system Node 20.
- **⚠️ Runner→VPS ssh connectivity is intermittently flaky, and with production auto-deploying that means a silent stall.** Measured 2026-08-25: **2 of 25 deploy runs (8%)** failed with `ssh: connect to host … port 22: Connection timed out`. It is a network-level SYN blackhole between GitHub's runners and the VPS. The retry helper therefore spans **~5 minutes (5 attempts, 15/30/60/90 s backoff)**, sized from a real outage that exhausted the earlier 3-attempt/70 s budget at 13:19:29 / 13:19:59 / 13:20:39. **A transport failure fails SAFE** — nothing is deployed, production keeps serving the previous SHA — but it fails **silently**. **`deploy-drift.yml` closes that**: on a schedule (every 30 min on paper, every 2.5–6 h in practice) it compares production's last *verified* deploy (its HEAD while no record exists yet) to `origin/main`. `in-sync` passes. **`behind-healable`** (behind but serving 200 — the transport-failure shape, or a deploy that died after its checkout) re-runs the deploy **once**, as a full deploy, **but only if main's exact commit passed the `staging` job of its Deploy run** (`scripts/deploy/drift-gate.js` asks the GitHub API). The heal runs the same `vps-deploy` action as production, with auto-rollback, in the `production` environment. **`behind-already-attempted`**, **`behind-and-unhealthy`**, **`behind-staging-failed`**, **`behind-staging-unverified`**, **`behind-staging-unreached-retried`** and **`verified-record-inconsistent`** (the record names a commit HEAD does not contain: HEAD was moved back by hand, a manual deploy of an older ref died after its checkout, or a verified pin off main was followed by a deploy of main that died after its checkout) deliberately do NOT heal and fail the job loudly instead. `behind-staging-pending` only posts a notice. **`behind-staging-unreached`** re-runs main's Deploy run once (below). ⚠️ **Drift is serialized with deploys**: both workflows share one literal concurrency group with `queue: max`, and `remote-deploy.sh`, `remote-rollback.sh` and `remote-record-verified.sh` hold the box-level `flock` above. Full state table in [`.github/workflows/README.md`](../../.github/workflows/README.md). ⚠️ **The one-heal-per-commit marker (`.drift-heal-attempted`, written on the box BEFORE the deploy) is what stops a genuinely broken commit restarting production every 30 minutes.** It is written first on purpose: if the heal dies halfway the marker still records the attempt, so the next tick alarms rather than retries — fail-closed. **It has three writers**, and all three mean "a human decides now": the heal itself, an auto-rollback (it records the rejected commit, even when it returns to that commit, but keeps a marker that already blocks main's tip), and a manual Deploy with a non-`main` `ref` (it records main's tip, because a pin is a human decision). `behind-and-unhealthy` is treated as an incident, not a missed deploy: healing would paper over it. **A transport failure in the STAGING job is re-run, not healed** (since 2026-09-24; before that it alarmed as `behind-staging-failed` and waited for a human, which happened on two of the three most recent deploys as of 2026-09-23). The heal needs main's commit to have *passed* staging, and a staging job that never reached the VPS has no verdict at all. `ssh-retry.sh` prints `::error title=VPS unreachable::ssh failed to connect after N attempts — …` only after its last attempt. `drift-gate.js` reads that back from the failed staging job's check-run annotations (`checks: read`), by the title or by the message prefix, which older runs carry. **`behind-staging-unreached`** then makes the workflow's `rerun` job ask GitHub to re-run that Deploy run's failed jobs. The re-run replays the same run on the same commit: staging deploys and smoke-checks first, and production runs only if staging passes, so the staging gate is never skipped. "Once" is GitHub's own `run_attempt`: only attempt 1 is re-run. Right before asking, the job reads the run back. It must still be main's push-triggered Deploy run for the checked commit and still on attempt 1, or it is an error. It must also still be main's newest Deploy run: a re-run since the check, or a newer push (whose own Deploy run goes first and decides), is a notice and no re-run. A second failure to reach the VPS, or a run already re-run by hand, alarms as **`behind-staging-unreached-retried`**. A staging job that failed for real, or whose annotations cannot be read, still alarms as `behind-staging-failed`.

  ⚠️ **"Never reached the VPS" means every ssh attempt exited 255.** That covers the network, but also a refused deploy key, a changed host key and a dropped session, so check those too before re-running by hand. ⚠️ **A Deploy run that is not completed reads as `behind-staging-pending`, whatever its jobs say.** A queued re-run still lists its previous attempt's jobs. The gate never keys on the staging job's own `run_attempt`, because after a re-run of production alone staging keeps attempt 1 and its pass still counts toward a heal. ⚠️ **Two side effects.** A persistent staging ssh failure now alarms one drift tick later: the first tick re-runs, the next alarms. And a re-run deploys main's commit to staging again, moving staging back to main over any branch someone deployed there by hand in between.

  ⚠️ The `rerun` job holds the workflow's **only write permission** (`actions: write`, set on the job, so it replaces the read-only workflow set there). It runs no action and checks nothing out. The check job shreds the deploy key as soon as the box has been read. `remote-smoke.sh` prints the pm2 error log with workflow commands switched off (a random `::stop-commands::` token), so no line of the app's log becomes an annotation. No remote script exits 255 itself (literal exit codes, no errexit), so a 255 is always ssh's own. `scripts/test-drift-gate.js` and `scripts/test-deploy-scripts.js` pin all of this, and the rerun job's own script runs against a stub `gh`.
- **`npm run ci`** runs the exact same gate locally. Run it before pushing and the pipeline holds no surprises.
- **⚠️ `test-suite.js` is BANNED from CI and a step in `ci.yml` fails the build if any workflow invokes it** — it writes, defaults to port 3000 (production on the VPS), and with no `SPREADSHEET_ID` override writes to the live sheet. That tripwire strips comments before matching, because the first version matched its own comment text and failed 100% of runs.
- **⚠️ CI does NOT cover `test-pdf-cold-start.js`** — `scripts/run-unit-tests.js` skips it when `UNIT_TEST_SKIP_TIMING` is set, which `ci.yml` sets. It induces an event-loop stall and asserts on catching the recovery, so it is a race by construction. **⚠️ It is flakier than first measured**: the original figure (6/6 idle, 3/6 at load ~11) was optimistic — it has since been observed failing at load average ~2.2 as well, roughly 1 run in 3. Treat a single local failure of this runner as noise and re-run before investigating; treat a *reproducible* failure as real. The skip prints at both ends of the run and in the job summary — never silent. **Run `npm run test:unit` locally (no env var) before touching `lib/pdf-browser.js` or the PDF render path.**
- **`backup-freshness.yml`** (2026-09-23) — daily at 04:00 UTC and strictly read-only: the newest nightly `app.db` snapshot must be under 25 h old (so the first missed night alarms), over the size floor and pass `gzip -t`, and the last *scheduled* backup run must have succeeded (either of `backup.sh`'s failure lines counts); anything else fails the job. It exists because `backup.sh` can only report into a log nothing reads, which cost two silent multi-night outages. Deliberately **not** self-healing, on its own concurrency group, and it never takes the deploy lock.
- **⚠️ The retry allow-list is exactly one runner and must never become a blanket retry** — retrying everything turns a real regression into "passes sometimes", which is worse than no CI. A retry that succeeds still prints as `FLKY` so it cannot quietly rot into permanent failure.

**Deploy:** production runs on a VPS at `76.13.22.110` under `/var/www/logistics-app`, managed by pm2 (process name `logistics-app`). The workflow above automates this. To deploy or roll back by hand, dispatch it: `gh workflow run deploy.yml -f target=production -f ref=main` redeploys main's tip, and `-f ref=<sha>` pins production to that commit, detached — a pin writes the drift marker, so drift alarms and never deploys `main` over it until `main` is deployed again. ⚠️ **Do not use the old ssh one-liner below any more**: it skips the box lock, the dirty-tree guard and the `better-sqlite3` probe, and it builds with the box's system Node 20 rather than the interpreter pm2 runs the app with. It is kept as a record of what the deploy does:
```bash
ssh root@76.13.22.110 "cd /var/www/logistics-app && git checkout -- client/package-lock.json && git pull --ff-only origin main && npm install --silent --no-audit --no-fund && npm run build:client --silent && pm2 restart logistics-app --silent"
```
⚠️ **The leading `git checkout -- client/package-lock.json` is load-bearing, not tidiness.** The box's npm strips the `"libc": [...]` field that a newer npm writes onto optional platform-specific deps, so **every `npm install` there leaves `client/package-lock.json` permanently modified**. ⚠️ **Moving the build to Node 22 did NOT fix this** — the deploy now builds with npm 10.9.8 (via `/opt/node22`) rather than the system npm 10.8.2, and the drift not only persists but grew: **15 deletions measured 2026-08-17, 81 on 2026-08-25**. `lockfileVersion` is 3 on both sides, so it stays pure metadata churn and nothing is broken by it. But `git pull --ff-only` **refuses to overwrite a locally-modified tracked file**, so the first PR that touches the lockfile would abort the deploy. That aborts *before* anything is installed or restarted, so it fails safe — it just looks alarming and blocks the release until someone clears it by hand. Discarding this one file is safe because npm regenerates it on the very next line and nothing reads it at runtime. **Keep the reset scoped to that one path** — a blanket `git checkout -- .` or `git reset --hard` on production could silently discard a deliberate hotfix. The alternative fixes (upgrade Node/npm on a box running 20+ other clients' processes, or switch the deploy to `npm ci`, which also needs the root `postinstall`'s `cd client && npm install` changed) both carry more blast radius than they are worth.

A staging process (`logisx-staging`) also runs on the same VPS, at `/var/www/logisx-staging` on **port 3003** (production leaves `PORT` unset and defaults to 3000; both bind localhost behind nginx). Staging **does** set `SPREADSHEET_ID`; production does not, which is why an unset override there means the live sheet.

**⚠️ This VPS is SHARED — it runs ~23 pm2 processes for other clients** (LendyPH, binhs-coop, dromic, and more; verified 2026-08-25). **Never `pm2 restart all`, `pm2 reload all`, `pm2 delete`, or restart by numeric id** — that is a multi-client outage, not a LogisX one. Always restart by exact process name. The same applies to anything system-wide: a Node/npm upgrade on this box touches 20+ other applications, which is one of the reasons the npm-skew lockfile workaround exists instead of just upgrading npm.

**⚠️ `ecosystem.config.js` reaches the live process on the next deploy — but not `/root/.pm2/dump.pm2`.** `remote-deploy.sh` and `remote-rollback.sh` restart production through the file (`pm2 restart ecosystem.config.js --update-env` whenever it names the process; staging, which it does not name, is restarted by name), and nothing runs `pm2 save` — so the dump keeps the old settings, and a `pm2 resurrect` or a reboot brings them back. Apply a change with `pm2 restart ecosystem.config.js --update-env && pm2 save`, then confirm against `pm2 jlist`. Its value is that it is the only human-readable record of *why* the settings exist — chiefly `NODE_OPTIONS=--max-old-space-size=4096`, which is what stopped the app OOM'ing at the 2 GB default, and the only thing standing between a `pm2 delete && pm2 start` and a silent revert to it. Note `logisx-staging` has **none** of these settings (`NODE_OPTIONS` unset), so staging still runs at the 2 GB default — this config has only ever applied to prod. Read the header comment in the file before changing any number.
