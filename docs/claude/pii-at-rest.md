# PII at rest — why the answer was NOT encryption (2026-08-08)
A review flagged that SSN/EIN and bank routing/account numbers sit in plaintext in `app.db`, and asked for encryption at rest. **Assessed and deliberately not done.** The inventory is ~30 values in 5 tables (`job_applications.ssn|dob|drivers_license` ×8, `driver_payment_info.bank_routing|bank_account` ×4, `investor_payment_info.routing_number|account_number` ×3, `investors.ein_ssn` ×3, `investor_applications.ein_ssn` ×3). Encryption was rejected because **the same plaintext already lives in four places outside the database**, none of which a column cipher touches:
- **21 signed W-9 PDFs** in `uploads/onboarding-signed/` + `uploads/investor-onboarding-signed/` with the SSN/EIN flattened into the IRS AcroForm by `fillW9Form()`, plus contractor agreements carrying full routing/account via `lib/policy-field-maps.js`.
- **Unencrypted nightly backups** (`backups/`, gzip is not encryption). Measured on the VPS 2026-08-12: **54 files, 8.1 GiB**, and **the permissions exposure is now CLOSED** — `backups/` is **0700** and **all 54 files are 0600** (`scripts/secure-backups.sh --apply` has been run; earlier revisions of this file saying "51 of 56 still mode 644" and "it has not been run" are stale). ⚠️ **The "6 files escape the 30-day prune regex" line that used to sit here is STALE and was inverted twice over** — the regex bug was fixed in #231 (selection is now a `app.db.` **prefix** test with an mtime fallback, so a naming change can no longer make a file immortal), and the same six pre-surgery snapshots were then **deliberately pinned** in `backups/.retention-keep` on 2026-08-09 because they are the only record of the state before irreversible data work in months that are now closed and paid. They are a retention *decision* today, not a defect, and **the owner has decided the pins STAY** (2026-08-12) — all six verified present at 0600. `app.db.pre-expense-backfill-20260708-055919` (184.9 MiB) is the only one the pin is actually load-bearing for; the other five are inside 30 days anyway. Locked by `node scripts/test-backup-retention.js` (47 assertions, 5 mutants; the historical rule is mutant M1 and is caught by 10 of them).
  - **⚠️ `--adopt-strays` is deliberately NOT being run either** (owner decision, 2026-08-12). The strays are 15 `app.db.bak*` files in the **application directory**, not `backups/` — April/May copies plus their `-shm`/`-wal` siblings, largest `app.db.bak-20260509-truckdocs` at 30 MB. `secure-backups.sh` has already chmodded them to **0600**, so the confidentiality problem is solved where it mattered; what `--adopt-strays` adds is *moving* them under retention, and as that script's own banner says it **is a deletion decision in disguise** — their names start with `app.db.` so the prefix rule adopts them immediately, and their dates are far past any sane `--keep-days`, so the next nightly run deletes them. Leaving them is the conservative option and costs ~35 MB. If they are ever adopted, pin anything worth keeping in `backups/.retention-keep` **first**.
- **Sent email** — the investor-application admin notification embedded the tax id and routing number and attached the signed W-9, to a Gmail mailbox outside this system. Unrecoverable once sent.
- **`GET /api/db/query/:table`** — `SELECT *` on any table, no column filter, so every SSN was readable as JSON without downloading the 313 MB file.

**A fifth plaintext location was added 2026-08-17, and it is deliberately NOT in the list above** — that list is the *identity* plaintext (SSN/EIN/routing/account) that made the case against column encryption, and this is a different class, so folding it in would both break the "four places" count and blur the argument. Inventoried here so a future "where does plaintext PII live on this box" sweep finds it:
- **Rendered payout statement PDFs** in `storage/payout-statements/` — the cache behind `GET /api/investor/payouts/:period/statement`. One PDF per `(investor, period, fingerprint)`, each carrying the investor's legal entity name and the month's net payout: **financial PII, not identity PII** — no SSN/EIN, no banking. **Deliberately outside `uploads/`** so `express.static` can never reach it (the API route is the only reader; see the `uploads/invoices/` IDOR in #228 for why a guessable name under a static mount is not safe). Verified locally that the boot `umask 0027` covers it — `drwxr-x---` directory, `-rw-r-----` files, materially better than the `backups/` finding — **but that measurement is LOCAL: the directory does not exist on the VPS yet, so re-check permissions after the first production render.** Regenerated on demand, so the directory is safe to delete at any time; `scripts/refresh-env.js` moves only the database and never file trees, so nothing propagates to staging. ⚠️ `investor_payouts.statement_pdf_file_name` will still point at files a refreshed local/staging DB does not have — harmless, since a missing file is treated as a cache miss.

**The key-location argument is the other half.** `.env` is `600 root`, `app.db` is `644 root`, the app runs as **root**, and the box has no KMS/TPM/vault. A key in `.env` would defend a DB copy that leaves *without* the `.env` (backup, `/api/db/download`, stolen image) and a non-root local reader — real, but narrow. It would do **nothing** about the threat actually named in the finding: `super_admin` is a **shared login**, and the app decrypts for whoever is authenticated. Encryption is the wrong tool for "which person read this"; masking plus an audit row is the right one. Checked and cleared: git history is clean (the tracked `app.db` was a 16 KB stub, 1 user row, no PII tables), and `scripts/refresh-env.js` redacts every column named above and *asserts* every one of them — staging holds 0 populated values. (The assertion list was a strict **subset** of the scrub list until 2026-08-13: `dob`, `signature`, `signature_image`, `consent_text`, `signed_ip_source` and every column replaced with a *placeholder* rather than emptied (`REDACTED_LITERAL` — including four personal **home address** columns) were scrubbed but never checked. None is email- or SSN-shaped, so the free-text sweep could not cover for them either: a `setCols()` that silently stopped matching would have shipped real addresses with every check green.) **⚠️ Do not read that as "the nine columns are covered", which is how this line read until 2026-08-13.** The nine-column framing *is* the column-aware assumption: a scrub that names its columns only ever covers what it was told about, and 21 routable third-party addresses shipped past it in free text (`job_applications.reference_info`, `audit_trail.details`, `load_invoice_drafts.recipient`) under a run that printed "clean". The sanitizer now also sweeps every text column of every table (stage 3h) and treats a free-text address or SSN as a hard refusal — see the environment-refresh section above.

**What shipped instead** (`lib/pii-mask.js` — pure, no network/DB; fixed-width masks so length is never republished; idempotent so the client components that mask again cannot eat the last four):
- **⚠️ The IDOR was the real finding.** `/uploads` is mounted `requireAuth` **only**, and signed-PDF filenames are `${docKey}-${userId}-signed.pdf` — a five-key vocabulary crossed with a small sequential id. **Any authenticated Driver could read any other person's W-9.** The existing `confidential` flag (set on `w9` + `contractor_agreement`) was only ever a *listing* filter, which is not an access control when the URL it hides is guessable. Both signed-doc directories now resolve `signed_pdf_url` back to its row and require Super Admin, the owner, or (non-confidential only) a Dispatcher. **Authority is the DB, not the filename** — that also fails closed on the **54 of 88 files that are orphans** with no row, which breaks nothing because every UI link is built from a row. Refusal is **404, never 403**: a 403 confirms the document exists. Unconditional — *not* governed by `PII_MASK_ENABLED`.
- **⚠️ `uploads/invoices/` was the SAME hole, left open for another day, and it was the exact case the code comment predicted.** That comment justified leaving `uploads/onboarding/` unguarded purely on filename unguessability and warned *"if anything ever makes those names predictable … add it here immediately"* — but weekly invoice PDFs were **always** predictable: `${invoiceNumber}.pdf` where `generateInvoiceNumber()` builds `INV-{≤3 initials}-{YYYY}W{WW}-{NN}`, i.e. ~53 weeks × a tiny sequence, on the order of **100 requests to sweep a year for one named colleague**. `GET /api/invoices/:id/pdf` enforced ownership; the static mount served the same bytes to **any** authenticated session and simply skipped it. Measured on a scratch server against `origin/main`: a Driver read another driver’s pay PDF (weekly pay, active days, load/BOL list, expense deductions) in **all seven** path shapes tried — plain, `//`, `%2F`, mixed-case dir, `/./`, `%69nvoices`, and `/uploads/../uploads/…` — plus an eighth, a **lower-cased filename** resolving on a case-insensitive filesystem. Fixed by `guardInvoicePdf` as the **third** `GUARDED_UPLOAD_DIRS` entry, so it inherits the one normalizing guard rather than adding a sub-path mount (issue #228, 2026-08-09). ⚠️ The list is exactly three — `/onboarding-signed/`, `/investor-onboarding-signed/`, `/invoices/` (`server.js:5642-5646`). **`rate-cons/` never became a list entry**: it is a hardcoded role branch *above* the loop, so a count of four double-counts it and reads as if it carried an ownership rule. It does not — see the next bullet.
  - **MEMBERSHIP TEST, not fetch-one-then-compare** — `invoices.pdf_file_name` has **no unique index**, and the duplicate invoice-**number** bug `generateInvoiceNumber()` carried until PR #225 is precisely how two rows come to share one filename. `.get()` would return an arbitrary one and could refuse the real owner while admitting a stranger. Verified with two rows deliberately sharing a file: **both** owners get 200, everyone else 404. (Production currently has 0 such collisions — the shape is for the day it does.)
  - It reuses **`driverOwnsInvoice()`** rather than re-deriving the rule. This bug *is* "the ownership rule had a second door"; giving it a second *copy* of the rule as well is how the next drift starts. Refusing a blank `driverName` is also what denies a Dispatcher/Investor here without naming either role.
  - Soft-deleted invoices mirror the API route: **Super Admin only**. Orphan files fail closed — production has **2 of 29** (`INV-HR-2026W20-01.pdf.base`, `INV-RB-2026W31-01.pdf`) and **0 of 27 rows** has a missing PDF, so no live invoice loses its reader, and nothing in the client ever links to `/uploads/invoices/…` in the first place.
  - **Swept at the same time and deliberately left**, all four timestamped and therefore weak-secret rather than enumerable: `uploads/` root PODs (`${loadId}_POD_${Date.now()}.pdf`), `uploads/chat/` (`chat_${Date.now()}_${rand5}`), `uploads/expense-receipts/` (`${Date.now()}-${12 hex}`), `uploads/legal/` (`${scope}_${DocType}_${Date.now()}.pdf`). `uploads/onboarding-templates/` is blank forms. **⚠️ `uploads/rate-cons/` is `${loadId}.pdf` — fully enumerable — and is held ONLY by a role check (`server.js:5671-5675`, a hardcoded `Super Admin || Dispatcher` branch *above* the `GUARDED_UPLOAD_DIRS` loop), not by an ownership rule**, so any Dispatcher reads any load's broker rate con. That is the current intent, not an oversight.
    - **It cannot be patched, and that is the finding.** Dispatch is fleet-wide by design — `GET /api/dashboard` hands every Dispatcher the whole fleet, and **no table or sheet column records which Dispatcher owns which load**. Ownership has to be invented before it can be enforced, so this is a product decision, not a guard. Assessed in full in **`docs/ratecon-ownership-recommendation.md`** (2026-08-11): two concrete models priced, **recommendation is to keep the role gate** and revisit only if Dispatcher scope narrows generally.
    - **⚠️ The exposure delta is smaller than it reads.** `/api/dashboard` strips financial columns for `role === "Driver"` **only** (`server.js:24276`), so a Dispatcher already sees every load's `Payment` in the primary UI — guarding the file does **not** withhold the rate. The genuine delta is the broker contact block and commercial terms, which `sanitizeBrokerColumns()` does withhold from non-Super-Admins on the dashboard. Price the leak before spending a decision on it.
    - **⚠️ The "a DB guard would 404 files that work today" objection was measured and is EMPTY here: 6 of 6 production files resolve to a live `documents` row** (matching on both `load_id` and `file_name`; 0 soft-deleted). `uploads/rate-cons/` has exactly one writer — `POST /api/loads/from-ratecon` (`server.js:28126-28137`) — which writes file and row in the same `try` and `DELETE`s any prior RATECON row, so there was never a pre-row era; n8n writes to Drive, never here. **Any future backfill that mirrors the Drive-hosted email rate cons into `uploads/` resurrects the failure mode**, so it must write the row in the same transaction as the file.
    - **⚠️ If a guard is ever built, key on `documents.drive_url`** (which already stores the exact `/uploads/rate-cons/<file>` path), **never on a `load_id` reconstructed from the filename stem** — `from-ratecon` sanitizes the stem via `replace(/[^A-Za-z0-9._-]/g,"_")` while storing the raw id, so a `#`-prefixed load id gives `file_name = "_562787563.pdf"` against `load_id = "#562787563"` and the lookup misses. And it must be a **membership test**, not `.get()`: `documents` carries one non-unique index (`idx_documents_load_live`) and none on `file_name`/`drive_url`. Same two traps `guardInvoicePdf` already learned.
- **⚠️⚠️ A GUARD ON A SUB-PATH OF A STATIC MOUNT DOES NOT HOLD. Mount it where `express.static` is mounted.** `app.use("/uploads/onboarding-signed", …)` decides using the request's **literal** path, while `express.static` at `/uploads` **decodes and normalizes** before resolving a file — so every path shape the two disagree about is protected by neither. Three bypasses were confirmed against a running server, each returning the victim's file body to a Driver session: `/uploads//onboarding-signed/<f>` (extra slash), `/uploads/onboarding-signed%2F<f>` (encoded separator), and `/uploads/Onboarding-Signed/<f>` (case). The guard is now a **single `app.use("/uploads", …)`** that does its own `decodeURIComponent` → backslash-fold → collapse-slashes → `path.posix.normalize`, and matches the directory **case-insensitively**, so it judges the same string `express.static` will resolve. **Case-insensitivity is load-bearing, not tidiness**: Express's own mount matching is case-insensitive by default, and macOS (every dev machine) has a case-insensitive filesystem — on production's ext4 the mixed-case path 404s *by accident*, i.e. the filesystem is doing the authorization, which stops being true on an overlay/CIFS mount or a Mac.
- **The same bypass class applied to the pre-existing `app.use("/uploads/rate-cons", requireRole(…))`** — a Driver could read any rate con via those shapes. Fixed in the same unified guard (403 kept for that directory, since a rate con's existence is already implied by the load id). The old line is retained only as defence in depth and is explicitly marked as not holding on its own.
- **Masking on read**, because all masking was previously **client-side only** — the server shipped full values and Vue hid them behind a reveal toggle. Applied to `GET /api/applications` (licence), `/api/applications/:id` (SSN + licence), `/api/drivers-directory/:id/documents` (SSN), `GET /api/investor-applications` **and** `/:id` (tax id + routing + account), and `/api/db/query/:table` (by column name, matched **exactly** — a substring rule would also mask `account_type`). **`dob` is deliberately left unmasked**: it is routine for DOT eligibility review and a masked date is unreadable rather than redacted.
- **Two audited reveal routes** — `GET /api/applications/:id/sensitive` and `/api/investor-applications/:id/sensitive`, `piiRevealLimiter` 20/15 min, one `audit_trail` row each. This is what makes masking cost no capability, and it is the only real answer to the shared login.
- `/api/db/*` gained `dbAdminLimiter` (10/15 min) + audit rows; `/api/db/download`'s fixed temp filename became per-request (two concurrent downloads raced and one unlinked the other's file).
- **⚠️ Masking is only safe where no edit form round-trips the value** — a masked value saved back would overwrite the real one. Verified before shipping: `job_applications` has no full-record update route (only `/status`, `/restore`), `investor_applications` writes only `/status`, and no client ever submits `einSsn`. **That invariant is now ENFORCED, not documented**: `PUT /api/investors/:id` does accept `einSsn` and write `investors.ein_ssn`, and is safe only because `GET /api/investors` happens to omit the column — so it now falls back to the stored value when `piiMask.isMasked()`. One line, and every future masking decision is safe by construction.
- **⚠️ Masking the NUMBER while shipping the DOCUMENT is not masking.** `GET /api/applications/:id` masked `ssn` + `drivers_license` and still returned `cdl_front` / `cdl_back` / `medical_card` — base64 photographs of the licence, carrying the number, DOB, address, face and signature. Now stripped (the sibling `/api/drivers-directory/:id/documents` already did). Verified first that no admin screen renders them: the only client references are the applicant's own upload form and `DriverKit.vue`'s `*_type` columns.
- **⚠️ `access_token` is dropped from the investor-application payloads UNCONDITIONALLY** — not masked, and not subject to `PII_MASK_ENABLED`. `SELECT ia.*` was shipping it beside the tax id being masked. It is a **non-expiring bearer credential**: `verifyInvestorToken()` accepts it with **no session**, authorizing the signed W-9 PDF, e-signing as that investor, and `POST …/banking`, which rewrites where money is sent. Actionable, not merely disclosive — strictly worse than the SSN next to it.
- **⚠️ `isMasked()` matches the shapes this module EMITS, never "contains a `*` or `•`".** A content test is a content test on attacker-supplied data: `ssn` and `drivers_license` come from the unauthenticated `POST /api/public/apply` and a licence field routinely carries operator notes, so `maskLicense("D*1234567")` returned it **unchanged** — the one input that must never pass through was the one that did.
- **Ownership is a MEMBERSHIP test, not fetch-one-then-compare.** `investors.application_id` is `INTEGER DEFAULT 0` with **no unique index**, so `.get()` returns an arbitrary row when two investors share one — admitting whichever SQLite returned and refusing the real owner. Ask the DB "is this user an owner of this application?" instead.
- **`..` is rejected BEFORE `path.posix.normalize`, not after.** normalize absorbs `..` on an absolute path, so a post-normalize test is dead code — and `/uploads/../uploads/onboarding-signed/<f>` normalizes to a path that no longer carries the guarded prefix, falling through to `express.static` with only `send`'s own traversal check stopping it. That is a dependency doing our authorization.
- **`/api/db/download` writes its temp copy to `os.tmpdir()`, not `__dirname`.** Making the name per-request fixed a race but created a worse problem: unique names **accumulate**, and each is a full ~313 MB dump of every SSN and account number, in the repo working tree, matched by no `.gitignore` rule (`app.db*` does not cover `app_backup*`). `app_backup*.db` is now ignored as a second guard.
  - **⚠️ That temp copy is created `0600` BEFORE the backup runs, not chmodded after it.** `db.backup()` creates its destination at **0644** (measured). On macOS that is harmless — `os.tmpdir()` is a per-user 0700 dir — but on the **Linux VPS `os.tmpdir()` is `/tmp`, mode 1777**, and the box has four non-root login accounts, so a chmod-after would still publish the whole multi-second write of the dump. `fs.openSync(tmpPath, "wx", 0o600)` is `O_CREAT|O_EXCL`, which also refuses to follow a symlink planted at that path; the chmod after the backup is belt and braces for a future better-sqlite3 that recreates the inode.
  - **⚠️ The `res.download` callback covers every request outcome but NOT process death — and `pm2 restart` is step 4 of the deploy.** `purgeOrphanedDbExports()` runs once at **boot** (never on an interval: the only producer is a dead process) and unlinks `app_backup-*.db` in `os.tmpdir()` older than **1 h**. The age floor is load-bearing — `logistics-app` and `logisx-staging` share `/tmp`, so restarting one must not delete the other's in-flight copy. `lstat` + `isFile()`, never `stat`: any local user can plant `app_backup-<x>.db` as a symlink in a 1777 `/tmp`.
- **Both reveal routes set `Cache-Control: no-store`** — the whole point is that the value is not ambient, and an undirected JSON 200 is heuristically cacheable.
- **⚠️ `PII_MASK_ENABLED` defaults ON**, breaking the ships-dormant convention on purpose — see the note in `.env.example`. It is a kill switch, not an enable switch.

**Known, deliberately left** (each is real and none is fixed by encryption): the backups are still **plaintext**, but the permissions half of that finding is **RESOLVED** — re-measured 2026-08-12, `backups/` is **0700** and **all 54 files are 0600** (57 files as of 2026-08-18, still all 0600 — the count drifts nightly as snapshots are added and pruned, so a mismatch here is not an escaped file), as are the 15 `app.db.bak*` strays in the app directory. `scripts/secure-backups.sh --apply` has been run. ⚠️ Earlier revisions of this paragraph read "51 of 56 files (7.97 GiB) are still mode 644 in a mode-755 directory … **it has not been run**"; that was true when written and is not now. The finding it recorded was real and worth keeping in mind for anything new that writes here: verified 2026-08-11 by `sudo -u <acct> test -r` that **all four** non-root login accounts (`ubuntu`, `nodeapp`, `deploy` and `postgres` — uid 109 but a real `/bin/bash`, so a uid>=1000 filter misses it) could read a full plaintext snapshot with no exploit, just `cp`. `backup-db.js` writes every NEW file 0600 and warns nightly, but it deliberately never re-permissions existing files or the directory from inside a 02:00 cron job — which is why the one-time remediation is a separate script. Still open and genuinely unfixed: the W-9/contractor PDFs hold plaintext on disk; and `POST /api/public/apply` and the invest wizard persist SSN/EIN/banking to browser **`localStorage`** (`logisx_apply_state`, `logisx_invest_state`) with no expiry, cleared only on successful submit.
- ⚠️ **A third item used to sit in that list — "`app.db` itself is still `644`" — and it is STALE. Re-measured 2026-08-18: `app.db` is `0600 root:root`**, as are its live `-wal` (93 MB) and `-shm` siblings and all 15 `app.db.bak*` strays. Verified the same way the original finding was, by `sudo -u <acct> test -r`: **all four** non-root accounts (`ubuntu`, `nodeapp`, `deploy`, `postgres`) are **denied** on both the live database and a backup snapshot. Its parent `/var/www/logistics-app` is still `0755`, which is traversable but does not confer read on a `0600` file. **The whole non-root read path is therefore closed** — the "just `cp` it" exposure no longer exists anywhere in this finding. Do not cite it as a live hole.
- **What that leaves is residual, not exploitable-today.** The data is still unencrypted at rest, so reading it now requires **root** (and the app runs as root, so an RCE in it qualifies), a copy leaving the box (a disk image, a provider-side VPS snapshot, an `scp` to a laptop, `POST /api/db/download`), or the host's own infrastructure. Real, but none of it is reachable by anything already on the machine. Encrypted **off-box archival** is the only option that materially changes this; column encryption was assessed and rejected for the reasons at the top of this section, and those reasons still hold.
