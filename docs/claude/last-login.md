# `users.last_login_at` — the Users screen shows when each account last signed in (2026-08-14)
Client ask: *"Can we say the last time they signed in?"* The Users screen listed 13 accounts with a CREATED date and nothing indicating whether an account was still in use.

**⚠️ There was NO history to backfill, and the reason is worth keeping — it is the same "looks implemented, never fired" shape as the geofence bug.** Three independent stores could each plausibly have held it and none did: `users` had no such column; **`audit_trail` has no login action at all** (30 distinct actions over ~1,400 rows, only `setup_super_admin` / `setup_refused` are even auth-adjacent, and only 7 of 13 users appear in it — it records *writes*, not sign-ins); and `POST /api/auth/login` performed **zero database writes**, so a successful login left no trace beyond the express-session row. So every account reads **"Never"** until its next sign-in. That is the expected day-one state, not a defect, and a dormant account *staying* on "Never" is the useful signal.
- **One choke point, therefore one stamp.** `POST /api/auth/login` is the only sign-in path in the app — there are exactly two `bcrypt.compare` call sites (login, and change-password's current-password check) and three `req.session.user =` assignments (setup, login, change-password's regenerate). So a single `stampLastLogin()` covers admin, dispatcher, driver **and** investor. Called from login (after the password check, so a failed attempt never looks like a sign-in) and from `POST /api/auth/setup` (which signs the new Super Admin straight in). Deliberately **not** called from change-password's regenerate — that user was already signed in, and treating a password rotation as a fresh sign-in would overstate the column.
- **⚠️ THE `try/catch` IN `stampLastLogin()` IS LOAD-BEARING, NOT DEFENSIVE HABIT.** It is bookkeeping for one display column and it sits *inside the login route* — an unhandled write error there would 500 `/api/auth/login` and lock **every user out of the entire app**. A missing stamp is cosmetic; a failed login is not. Verified by pointing the UPDATE at a nonexistent column: login still returned **200** and the error was logged, not thrown. Re-run that check if this code is ever refactored.
- **⚠️ Stored as an explicit ISO-8601 `Z` string, never a bare `CURRENT_TIMESTAMP`.** SQLite serialises that zone-less (`"2026-08-14 12:26:41"`), which the browser parses as **local** time and renders hours out — the trap documented at the top of `client/src/utils/datetime.js`. Storing the zone is also why `GET /api/users` needs **no `strftime()` wrapper** on this column, unlike the `created_at` directly beside it; wrapping it would be a second conversion of an already-zoned value.
- **The boot seed is EXACT, not an estimate.** The session config sets no `rolling: true`, so `sessions.expire` is stamped once at session creation as `login + cookie.maxAge` and `touch()` only ever rewrites that same absolute value — it does not slide with activity. So `expire − originalMaxAge` **is** the login instant. Each session's own `cookie.originalMaxAge` is read out of the `sess` JSON rather than hardcoding 24 h, so it cannot drift from the cookie config; the newest session per user wins. Fills only rows still at `''`, so the seed runs every boot and can never overwrite a real stamp (verified: restart changed 0 rows). ⚠️ It guards on `sqlite_master` first because **`sessions` is created by the express-session store, constructed far *below* the migration block** — on a fresh install the table does not exist yet.
- `''` means "never signed in since this shipped"; `GET /api/users` maps it to `null` and the UI renders **"Never"** (italic, muted) rather than the em dash the other columns use for a blank field — an empty value here is a real answer, not missing data.
- **Rendering is hybrid**, matching `AdminToolsView`'s `formatRmTs` and `DriverPayOverridesView`'s `formatTs`: `just now` / `12m ago` / `3h ago` / `4d ago`, then absolute past a week via the shared `fmtTimestamp()` (Houston-zoned with a visible zone label). The absolute instant is always in the cell's `title`. The relative window is kept short because the house default on admin screens is absolute — see the rationale note in `NotificationsView`. ⚠️ Computed at render, so a value left open on screen goes stale; that is fine (the page refetches on `users:changed`) and a ticking `now` ref is deliberately **not** wanted.
- **⚠️ `super_admin` is a SHARED login**, so its last sign-in says the account was used, not *who* used it. Attributing that to a person needs a login history (an `audit_trail` `login` action carrying the IP), which was **scoped out** — if that is ever built, note the `PURGEABLE_REFUSAL_ACTIONS` retention machinery beside `logAudit` would need to classify it.
- The Team Members table is now 9 columns and is wrapped in the shared `.table-wrapper` (`shared.css`, `overflow-x: auto`). **Not cosmetic**: `.admin-page` sets `overflow-x: hidden`, so at 8 columns the table was already **clipped rather than scrollable** on phones — measured at 390 px the 1,086 px table now scrolls inside a 324 px wrapper with the last column reachable, and the page body does not scroll sideways.
- **⚠️ `test-suite.js` does not exercise this** — it calls `GET /api/users` but asserts nothing about `LastLoginAt`, and nothing checks that a login stamps. A regression here is silent.
