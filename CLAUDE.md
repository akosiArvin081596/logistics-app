# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
# Backend (Express server)
npm start            # Run server (node server.js) on port 3000
npm run dev          # Run with nodemon for auto-restart on file changes

# Frontend (Vue 3 + Vite SPA)
npm run dev:client   # Start Vite dev server on port 5173 (proxies to Express:3000)
npm run build:client # Production build to client/dist/

# Docs (Puppeteer-driven static doc/screenshot generation from scripts/docs/)
npm run docs:build       # node scripts/docs/generate-docs.js
npm run docs:screenshots # node scripts/docs/capture-screenshots.js
```

Development requires two terminals: `npm run dev` + `npm run dev:client`. Open http://localhost:5173 during development.

For production: `npm run build:client` then `npm start` — Express serves the built SPA from `client/dist/`.

`postinstall` auto-runs `cd client && npm install`, so `npm install` at root installs both backend and frontend deps.

**Repo layout & parallel dev:** the git repo root is *this* folder (the app), with sibling worktrees `LogisX-wt-1` / `LogisX-wt-2` for running parallel feature branches side by side. To run two full stacks at once, give each worktree its own ports in its `.env`: `PORT` (Express), `VITE_DEV_PORT`, and `VITE_API_TARGET` (the Express URL Vite proxies `/api` + `/socket.io` to — read in `client/vite.config.js`); leave all three unset for the default `5173 → :3000` pairing.

**Branch & PR workflow:** cut `feat/…` or `fix/…` branches off `main`; PRs target `main`, and merging to `main` is what ships to production (run the deploy command below). The `/start-task` (or `/logisx-start`) skill freshens the branch from `origin/main` and cuts a fresh feature branch; `/end-task` (or `/logisx-end`) commits, pushes, and opens/locates the PR to `main`. These skills never merge or switch branches for you.

**Deploy:** production runs on a VPS at `76.13.22.110` under `/var/www/logistics-app`, managed by pm2 (process name `logistics-app`). Standard deploy flow after merging to `main`:
```bash
ssh root@76.13.22.110 "cd /var/www/logistics-app && git pull --ff-only origin main && npm install --silent --no-audit --no-fund && npm run build:client --silent && pm2 restart logistics-app --silent"
```
A staging process (`logisx-staging`) also runs on the same VPS.

**Tests & linting:** No Jest/Mocha/Vitest/ESLint configured. Integration harness at `test-suite.js` — **144** HTTP tests against a running server. Prepare fixtures first, or nearly everything fails at the login on test 2.

**⚠️ The suite WRITES — point the server at a copy, never the live sheet.** Test 46 logs an expense, so this is not a read-only harness. Production's `.env` sets **no `SPREADSHEET_ID` at all**, so `server.js` falls through to its hardcoded production default (`1ey1n0AA…`) — meaning *any* server started without an explicit override (this suite's, a helper script's, a stray `npm start`) writes to the live Dispatch Management sheet. **And never identify a sheet by its title:** the VPS `logisx-staging` process uses a sheet *titled* **"logisx-production"**. Its ID is not production — the title is a leftover from how the copy was made — but read in a hurry it says the opposite of the truth. Check the ID, never the name. The safe local copy, used in the command below, is `156Y5-OUUEZspiY7dRsJZ57iyKWLJAjdVP8a4yw0PMN0` ("Dispatch Management (LOCAL)"). Same class of accident on the port: the suite defaults to **3000, which is production on the VPS** — pass `TEST_PORT` (and the server's `PORT`) to run anywhere else.

### Environment refresh (local + staging)
`./scripts/refresh-local.sh` and, on the VPS from `/var/www/logisx-staging`,
`./scripts/refresh-staging.sh --yes [--restart]`. Both bring the checkout to `origin/main`,
rebuild the client, and hand the database half to `scripts/refresh-env.js`. Full runbook,
including the drift audit that motivated it, in **`scripts/README-env-refresh.md`**.

- **The source is the nightly snapshot** (`/var/www/logistics-app/backups/app.db.*.gz`), never
  the live production `app.db` — that file already has a consistent Online-Backup-API copy that
  passed `integrity_check`, so re-snapshotting the live file adds risk for nothing.
- **The spreadsheet gate is the load-bearing safety.** `refresh-env.js` reads the `.env` beside
  its `--to` target and **refuses** when `SPREADSHEET_ID` is missing or is production's — because
  `server.js` falls through to the production sheet when it is unset, so a refreshed DB next to
  such an `.env` is a production writer on first boot. It checks the resolved **ID**, never the
  directory name, for the same reason the staging sheet is *titled* "logisx-production" and is
  not production. It also refuses an `.env` that can send mail (`GMAIL_USER` +
  `GMAIL_APP_PASSWORD`, override `--allow-mail`) or that has `INVOICE_AUTOGEN_ENABLED=true`.
- **⚠️ Telemetry is trimmed to 45 days by default, and that is not a neutral shrink.**
  `routemate_telemetry` is 99.7% of all rows (933,893 of ~936,000). Trimming does *not* zero old
  driver pay — `getEldTravelDaysByVehicle()` is coverage-aware, so a window with **no** pings
  falls back to the **full scheduled window**. Months older than the cutoff therefore pay *more*
  than production and their investor payouts come out *lower*. Bounded in practice (15 months are
  already locked and frozen), but **never reconcile a historical month on a trimmed copy** — pass
  `--telemetry-all`.
- **Sanitization is asserted, not assumed**: sessions cleared, every password re-hashed to the
  harness default (`Password123!`, so `test-suite.js` runs with no extra step), emails rewritten
  to RFC-2606 `.invalid` (can never resolve), bank/tax/identity fields and signatures redacted,
  investor onboarding `access_token`s regenerated, `driver_locations` emptied. The run fails if a
  routable address, a session, or a bank account number survives.
- **Not copied:** `uploads/` (receipts/PODs/rate-cons are on disk — they 404 in a refreshed
  environment, and the tree is unredacted PII) and the Google Sheets themselves.

## Architecture

### Backend (`server.js`)
Single-file Node.js/Express server (~18,450 lines, ~185 REST endpoints). Google Sheets is the primary database (Sheets API v4); SQLite for local data; Drive API for uploads; Socket.IO for real-time. Body limit raised to 50mb for large payloads with embedded base64 photos/signatures.

**Static file serving**: Express serves `client/dist/` if it exists (production build), else `public/` (legacy vanilla HTML/JS). SPA catch-all `app.get("*")` serves `index.html` for client-side routing.

**SQLite** (`app.db`, WAL mode) — ~35 tables organized by domain:

| Domain | Tables |
|--------|--------|
| Auth & users | `users` |
| Messaging | `messages`, `notifications`, `dispatch_notifications` |
| Dispatch | `load_responses`, `load_ratings`, `load_coordinates`, `deleted_loads` |
| Fleet | `trucks`, `truck_assignments`, `trailers`, `drivers_directory`, `carrier_driver_history` |
| Finance | `expenses`, `maintenance_fund`, `compliance_fees`, `invoices`, `investor_config` |
| Investors | `investors`, `investor_applications`, `investor_onboarding`, `investor_onboarding_documents`, `investor_payment_info`, `investor_outreach_log` |
| Driver onboarding | `job_applications`, `driver_onboarding`, `onboarding_documents`, `driver_payment_info` |
| Documents | `documents`, `legal_documents` |
| Tracking | `driver_locations`, `geocode_cache` |
| Admin | `audit_trail` |

Session store also in SQLite.

**Schema migrations**: On boot, server runs two types of migrations:
- `ALTER TABLE ... ADD COLUMN` for adding new columns. Checks for existing columns first.
- **Rename-recreate** for CHECK constraint changes: a test insert in try-catch; on failure, rename the table, create a new one with the updated constraint, migrate data, drop the old, and clear all sessions to force re-login.

**Notable libraries**:
- **pdfkit**: PDFs for applications, invoices, onboarding docs; converts base64 camera photos to PDF for Drive uploads (`imageToPdf()`).
- **pdf-lib**: alongside pdfkit for document manipulation (e.g., embedding signatures into onboarding PDFs).
- **tesseract.js**: OCR fallback on POD image uploads only (`extractReceiptText()` at `POST /api/documents/upload`). Once hooked into expense receipts but unwired for low accuracy — that path now uses Gemini (see below). Errors are silently swallowed — OCR failure never blocks the upload.
- **nodemailer**: emails for driver onboarding acceptance and investor outreach. Needs `GMAIL_USER` + `GMAIL_APP_PASSWORD`.
- **compression**: Gzip response compression middleware.
- **archiver**: Streams zip downloads directly to the response — currently the per-truck expense-receipts bundle (lazy `require`d inside the handler; error handler installed before `pipe()`).
- **express-rate-limit**: Per-endpoint limiters; see the rate-limiting section below.

**AI / vision services**:
- **Gemini 2.5 Flash vision** — expense receipt OCR (`POST /api/expenses/ocr`). Called via `fetch` (no SDK) with `responseSchema` enforcing the JSON shape. Requires `GEMINI_API_KEY`; falls back to 503 + silent manual-entry when unset. Key is shared across Alchemy projects (rotate in one place). Retry (2 retries, exp backoff, 15 s `AbortController` timeout) mirrors the Google Routes integration. **Autofill surfaces:** the driver `ExpenseForm`, the admin/dispatcher single "Log Expense" form in `ExpensesTab` (enhance→OCR→prefill, with Undo), and the **Bulk Upload** sub-tab (`components/dashboard/expenses/BulkReceiptScan.vue`) — pick a default driver, drop N receipts (≤25/batch), each image is OCR'd (concurrency 3; bulk skips the ScanKit enhance pass to save credits) into an editable review grid, then one create per row via `POST /api/expenses`. Write-timeouts (ambiguous re: whether the insert landed) are parked in a non-auto-retried `timeout` state to avoid double-booking the P&L, since `POST /api/expenses` is not idempotent.
- **ScanKit.io document scanning** — server-side crop / deskew / lighting-correction (and optional searchable-PDF with OCR layer) via `POST /api/documents/scan`, backed by the `lib/scankit-client.js` adapter (single point of contact; `Authorization: Bearer`, multipart upload, retry/timeout mirror the Routemate/Gemini pattern). **Replaced** the old client-side jscanify + OpenCV-WASM (~9 MB) scanner in `DocumentUpload.vue`. Used by driver POD/BOL scanning, the admin dashboard upload (`ActiveLoadsTab` reuses the same component), and receipt enhancement before Gemini OCR (`ExpenseForm`, `ExpensesTab`). Requires `SCANKIT_API_KEY` + `SCANKIT_ENABLED=true`; returns 503 (client falls back to attaching the raw photo) when unset. Credit-billed (`scanKitLimiter` caps spend) — **rotate the key if it is ever exposed**.

REST endpoints (grouped by domain):

**Sheets CRUD** (Google Sheets as database):
- `GET /api/tabs` — list all sheet tab names
- `GET /api/data?sheet=&page=&limit=` — read rows (paginated, max 200/page)
- `POST /api/data?sheet=` — append row (`{ values: [...] }`)
- `PUT /api/data/:rowIndex?sheet=` — update row by 1-based index
- `DELETE /api/data/:rowIndex?sheet=` — delete row (shifts rows up, Super Admin only)

**Dashboard & dispatch**:
- `GET /api/dashboard` — aggregated KPIs, job board, active loads, fleet data. Each job row is enriched with `_pickupLocation` / `_dropLocation` (clean "City, ST ZIP" from `load_coordinates.pickup_address` / `dropoff_address` or parsed from the sheet) plus `_pickupStreet` / `_dropStreet` (line 1, the street; "" when none); JobBoardTab + ActiveLoadsTab + CompletedLoadsTab render these as a two-line address (street over "City, ST ZIP") in place of the raw broker-reference columns. Split by `splitAddressLines()` / `resolveAddressParts()` in server.js (mirrored client-side in `client/src/lib/address.js` for surfaces with only the raw string, e.g. driver LoadDetail). The public tracker shows "City, State" + a separate ZIP line — never the street.
- `POST /api/dispatch` — assign load to driver (writes to sheet + notifies via socket)
- `POST /api/dispatch/reassign` — reassign load to different driver
- `POST /api/dispatch/cancel` — **Super Admin only**. Sets status `Cancelled` (not `Unassigned`) so the load drops from every KPI via `excludeDroppedLoads()`. Per 2026-04-19 client decision, dispatchers lost this; use the Driver reassign dropdown for swaps. **Requires `reason`** (≥3 chars, else 400 `CANCEL_REASON_REQUIRED`) — enforced server-side so the guard holds for any caller, not just the UI. The reason is stored on the `load_status_history` row, echoed to the driver notification and the dispatch feed, and the cancel is `logAudit`ed (`cancel_load`). Added 2026-08-05 after a live $1,050 load was cancelled instead of the one the broker called off: the old confirm read only "Cancel this assignment?" with **no load id**, so the right and wrong rows prompted identically, and nothing recorded *why*. Both cancel surfaces (`ActiveLoadsTab`, `JobBoardTab`) now use `ConfirmModal` showing load id / driver / route / payment plus a required reason. `computeStatusPhases` returns `reason`, and the **public tracker strips it alongside `actor`** — never leak dispatch's internal note to a customer.
- `DELETE /api/loads/:loadId` — **Super Admin only**. Soft-delete via the `deleted_loads` table; row stays in the Sheet for audit but is filtered from all admin lists + KPIs. Reversible via `DELETE FROM deleted_loads WHERE load_id = ?`.
- `POST /api/loads/ratecon/extract` — Super Admin/Dispatcher. `{pdfBase64, fileName}` → `{fields, warnings}` via the shared `runRateConGemini()`. **Writes nothing** (no sheet, no DB, no Drive) — it exists so the dispatcher can review before committing. Rejects non-PDFs on the `JVBERi` magic prefix, caps size, 503s without `GEMINI_API_KEY`. Rate-limited by `rateConLimiter`.
- `POST /api/loads/from-ratecon` — Super Admin/Dispatcher. `{fields, pdfBase64, fileName}` (fields = what the dispatcher reviewed/edited) → creates the load. See "Load ingestion" below.
- `POST /api/driver/respond` — driver accepts/declines a load assignment
- `GET /api/load/:loadId` — single load details
- `PUT /api/load/:loadId` — update load fields

**Driver**:

**Investor payout ledger** (settlement layer over `/api/investor` earnings; table `investor_payouts`, one row per `(owner_id, period)`):
- `GET /api/investor/payouts?as_user_id=N` — one investor's ledger. `GET /api/payouts` — Super Admin fleet-wide console (`/payouts` view), summing every investor into `monthlyTotals` + `grandTotals`. Both run the **same** `reconcileInvestorPayouts()`, which idempotently UPSERTs a row per completed past month and refreshes `amount` **only while the row is still `owed`** — a settled row's figure is frozen.
- `POST /api/investor/payouts/:id/status` — Super Admin moves a payout **either direction**: forward `owed → processing → paid` (`owed → paid` allowed), or backward ("reopen") `paid → processing → owed` (`paid → owed` allowed). A reopen **requires `reason`** (400 without one), clears the stamps it undoes (leaving `paid` nulls `paid_at`/`paid_by`; going to `owed` also nulls `processed_at`/`processed_by`), and records `reopened_at`/`reopened_by`/`reopen_reason` on the row plus a `REOPENED …` line in `audit_trail`. Reopening is exempt from the "$0 is not settleable" guard, which still blocks forward moves. Same-status transitions 409. **Reopening to `owed` re-links the row to live earnings** so the next reconcile refreshes its amount; reopening to `processing` keeps it frozen.
- `PUT /api/investor/payouts/:id/adjust` — signed correction on **any** period including a settled one (late receipts). Capped at ±$10,000, can never invert a payout below $0. Effective payout = `amount + adjustment`; the reconcile only writes `amount`, so adjustments survive recomputes.
- UI (`client/src/views/PayoutsView.vue`): `owed` rows offer Mark Processing / Mark Paid, settled rows offer Reopen / Adjust. **"Mark Paid" is confirm-gated** — it is the only status asserting money actually moved, and an unguarded click once booked $8,703 as paid that was never sent. Reopened rows carry a `reopened` badge with the reason on hover.

**Month-end close** (`PERIOD_FINALIZE_ENABLED`, default off — ships dormant). Client ask: stop hand-adjusting a prior month every time a late receipt lands. A work month now runs `accruing` → `pending` (books open `settlement_grace_days`, default 7, past month end) → `finalized` (frozen; statement published). Table `period_locks` (one row per closed month, **fleet-wide** — one carrier, one month-end; a per-investor lock is incoherent because the super-admin branch of the monthly math sums all expenses with no owner scope). Presence of a `status='locked'` row *is* the lock; `'reopened'` keeps the row so the per-minute sweep can't re-lock what an admin just reopened. No new `investor_payouts.status` value, so **no CHECK rebuild and no forced re-login** — the phase is the pair `(status, locked(period))`.
- **Three legs, all required.** *Lock*: the reconcile's refresh guard becomes `status='owed' && !finalized_at && !isLocked(period)`, which freezes the figure against **all six** drift sources (sheet revenue, driver pay, `trucks.status='Active'` fixed costs, live-read split %, maint/compliance, trip expenses) — not just expenses. *Document*: `finalized_breakdown` JSON snapshot so the statement prints the composition as of close instead of a live recompute. *Posting rule*: `expenses.posted_period` — a receipt whose own month is already finalized books to the **current open month** (prior-period adjustment) while `date` keeps the true purchase date. Legs 1+2 without 3 lose the money; 3 without 1+2 leaks through five other doors.
- **`EXPENSE_PERIOD_EXPR`** (beside `EXPENSE_PNL_FILTER`) is the single source of truth for *which month* an expense counts in. The rule: **settlement basis uses it; operational basis keeps plain `date`.** Applied at 8 sites — incl. `getDeductibleExpensesByDriverMonth()`, whose `substr(date,1,7)` is invisible to a grep for `strftime('%Y-%m'` and drives percentage-driver pay at three call sites. Deliberately *not* applied to the weekly invoice week, fuel CPM, IFTA, or expense trend charts.
- **Scheduled sweep**, not a lazy read-path close (ported from the invoice-autogen batch): a lazy close freezes whatever value is present on the first page load after day 7, so a day-9 receipt lands inside a "final" number and two investors finalize at different values depending on who logged in first. `finalizePeriods()` takes every due lock first (pure clock math, cannot fail), then reconciles **once per investor** and stamps across all periods. Stamps `recomputedAmount`, **not** `amount` — `amount` only refreshes on a page GET, so freezing it would lose receipts that landed while nobody was looking.
- Guards, all inert when the flag is off: forward settle (409 `PERIOD_NOT_FINALIZED`, reopen exempt), adjust (closes a hole the UI was faking client-side; a finalized-but-unpaid row *is* adjustable), statement (**finalized OR paid** — monotone, so legacy paid months stay printable), and expense status flips (`PUT /api/expenses/:id/status` + `/bulk-status`, which could otherwise move three closed months while clearing a backlog; bulk skips locked rows and names the periods rather than failing wholesale).
- `POST /api/periods/:period/finalize` (close early) and `/reopen` (**requires `reason`**; re-links only `status='owed'` rows — a paid row keeps its snapshot because its statement already went out; returns the count of receipts redirected away, which reopening does **not** pull back). `GET /api/periods` is the close calendar.
- **`lib/payout-statement.js` is dual-mode.** Statements now publish at finalization, i.e. possibly before money moves, so the doc keys on `paidAt`: FINAL prints "Final Amount", the finalized/due dates, and "not a receipt"; PAID is unchanged. Shipping without this mails investors a PDF saying they were paid when they weren't.
- Rollout: deploy flag-off (ledger byte-identical), then enable — a baseline seed locks every period whose window already passed, so nothing is retroactively reopened and a month still inside its window closes naturally.

- `GET /api/poi/fuel-stops?loadId=|originLat=&originLng=&destLat=&destLng=[&limit=]` — diesel truck stops along a load's route (Google Places). No regional-average fallback — a coarse estimate would sort as if it were the cheapest stop. `poiLimiter`-capped (`fuelOptions` bumps these to the higher Places SKU). Feeds the tracking-map POI layer + cheapest-diesel list. **Super Admin / Dispatcher / Driver** — a Driver must pass `loadId` (400 without one), is `loadBelongsToDriver()`-checked against it (403), and any **parseable** raw `originLat/originLng/destLat/destLng` is refused (403) then `NaN`-ed for defense in depth, so `load_coordinates` is the only coordinate source. Empty-string coord params are tolerated as no-ops rather than 403s, so a stray querystring key can't break the driver panel. Same reasoning as `GET /api/geocode/load/:loadId` (route coordinates are competitive intel) plus a cost one: a free coordinate pair is an arbitrary route-pricing oracle billed at 4–8 Places calls a shot. Dispatch keeps the raw-coordinate form — they price prospective lanes that have no load yet.

**`poiStopsCache` — the Places fan-out cache (the actual cost control).** This endpoint shipped with a cost asymmetry: `getRoute()` was cached 15 min (`ROUTE_CACHE_TTL`) but the *expensive* half was not, so the cheap Routes call was memoized while the 4–8 billed Places calls were re-issued on every request, including repeat polls of a load whose route hadn't moved. `poiStopsCache` (Map + TTL + FIFO cap, mirroring `trackResponseCache`, 15 min TTL aligned to `ROUTE_CACHE_TTL` so both halves expire together, 200 entries) sits **after** coordinate resolution and **after** the Driver ownership check, so a hit can never bypass authorization. Responses carry `cached: <bool>` as an ops/QA signal for whether the request billed Google.
- **Keyed on the resolved coordinates**, rounded to 3 decimals (~111 m) exactly like `routeCacheKey()` — *not* on the query string or the raw `loadId`. So `?loadId=%23123` and `?loadId=123` land on the same `load_coordinates` row → same coords → same entry; two loads on the same lane share one fan-out; dispatch's raw-coordinate form reuses a driver's cached lane; and re-geocoding a load moves its key automatically, so there is no stale route and no invalidation hook to maintain.
- **`limit` is not part of the key and never refetches.** The fill always requests `POI_FETCH_CAP` (25) and the handler slices on read. This is **billing-neutral**: `limit` only feeds `maxResultCount` per call, while the billed call count is the waypoint count — `clamp(ceil(routeMiles/75), 4, 8)` — which `limit` cannot influence. Consequence worth knowing: the returned set is now the *N genuinely cheapest* rather than the lib's internal top-N re-sorted, which matches the endpoint's stated cheapest-first contract. `cheapest` is stable across limits (the global cheapest sorts to index 0); `livePriceCount` describes the returned slice, so it stays consistent with `stops`.
- **Empty results are deliberately NOT cached.** `findFuelStopsAlongRoute()` degrades a failed waypoint to `[]` silently, so an empty array is ambiguous between "no truck stops on this lane" and "Places was briefly down" — caching the latter would pin a blip into a 15-minute outage for that lane.

### Fuel range honesty — the range panel was ~2x optimistic
Client ask (2026-08-07), verbatim: *"the 449 miles to empty — we need to write a script that verifies that… we should know how much fuel it's gonna take to get the load done."* The panel showed `LogisX-#33` **23% · 69/300 gal · 6.5 mpg → 449 mi** against a **346.9 mi** route (load `562620213`, Laredo TX → Tomball TX) — i.e. "you arrive with 100 miles spare". Backtested against that truck's own fill history it was wrong by about 2x, and **the truck would have run dry ~117 miles short.**

- **The primitive is MILES PER SENSOR POINT, not `tank × mpg`.** That product multiplied two separately-wrong numbers (#33: tank 300 vs ~198 measured = 1.51x; mpg 6.5 vs 5.04 receipt-derived = 1.29x; 1.51 × 1.29 = the observed 1.95x). The tank half has since been fixed in the data (2026-08-07), which is precisely the argument for a primitive that needs neither input: **miles-per-point did not have to be re-derived when the tank changed, and the constant that did is the one that broke** (see `ESTIMATED_BASIS_DERATE`). Miles-per-point is measured end-to-end from the ELD odometer and the gauge between two consecutive `fuel_events`, so it needs neither input and inherits neither error. `burnLegsForVehicle()` builds the legs (server.js, beside `receiptMpgForVehicle`), `burnRateForVehicle()` memoizes 10 min.
- **The measured verdict** (95-day window, production data, **as of 2026-08-06 — see the ⚠️ below, these have since moved**): the formula overstated on **123 of 125** tank-to-tank legs — #33 56/56 at 1.95x, #2372 64/66 at 1.97x, #302 3/3 at 2.25x. Robust: the aggregate moves only 9.98→12.0 on #33 across every filter combination tried. **Re-measured 2026-08-07 after the tank correction: #33 1.30x, #2372 0.99x, #302 0.83x.** Run `GET /api/fuel/verify` rather than quoting either set.
- **The spread is the real finding.** At the same 23%, #33's legs run p10 164 mi / p50 265 / p90 383. No single number is honest however good the tank and MPG get, so `GET /api/fuel/range` now returns an **interval** — `rangeLowMiles`/`rangeTypicalMiles`/`rangeHighMiles`, `rangePlanningMiles`, `rangeBasis` (`measured` > `estimated` > `unknown`, ranked like `mpgSource`/`tankSource`), `milesPerFuelPoint`, `rangeEvidence`. **`rangePlanningMiles` is the low end and is the number any single-figure UI must render** — rendering `typical` (never mind `rangeMiles`) re-creates the original bug. `rangeMiles` is unchanged for existing callers.
- **⚠️ Plan against the low end — the errors are not symmetric.** Overestimating strands a truck on a shoulder; underestimating costs one fuel stop.
- **⚠️ Never substitute the calibration's `lowerMode` for `fuel_tank_gallons`.** `summarizeCalibration` is bimodal at ~1.8-2x because the sender reads ONE saddle tank; #33's lower mode is ~117 gal but the truck has twice taken a single **202.7-gallon fill** (hard floor ≥203 gal). Setting 117 would show HALF the true range — the more dangerous direction. `GET /api/fuel/verify` therefore reports it as `sensedGallonsPer100Pct` with `burnImpliedGallonsPer100Pct` (~198) and `largestSingleFillGallons` beside it. **Sensed volume ≠ capacity**; telling the client "your 300 is wrong, it's 117" is worse than telling them nothing. Nothing auto-writes `trucks.fuel_tank_gallons` — a human decides.
- **⚠️ `BURN_LEG_MIN_POINTS` must stay small (5).** It is a quantization floor, NOT a quality filter: `points` is the outcome being measured, so filtering on it selects. At 20 only anomalously-thirsty short legs survived, manufacturing a 10x "economy varies with trip length" effect and moving the driver-facing planning number 15%. Percentiles are **mile-weighted** for the same reason — each mile of history gets one vote, not each leg.
### Gallons recovery — reading the missing volume back off the receipt image
29 production fuel receipts carried a dollar amount and **no gallons** ($6,131.54; 28 on `LogisX-#33`). Gallons are the denominator of every honest fuel number, so this capped everything downstream — #33's tank-to-tank MPG rested on 25 of its 105 detected fills, and cost-per-mile could only be published as a floor. They were typed by hand and never OCR'd; the volume is printed on paper the server already stored.
- **`lib/receipt-gallons-recovery.js`** is pure (no network/DB/fs): `cpgBand()`, `judgeGallonsRecovery()`, `summarizeRecovery()`. server.js owns candidate selection, the lock, the file read, the Gemini call, the UPDATE and the audit line.
- **Two independent corroboration gates, and both are load-bearing.** (1) **Amount** — the model's total must reproduce the row's stored amount, so gallons are believed only from a reading demonstrably of *that* receipt. Measured on all 24 unlocked candidates the delta was **$0.00, 24 of 24**. (2) **Implied $/gal** must sit in a band derived from the fleet's *own* priced receipts (p05/p95 padded ×0.75/×1.35, hard-clamped to $1.50–$8.00, fixed $2.50–$7.00 fallback under 20 samples). Gate 1 catches "read the wrong paper"; gate 2 catches "right paper, wrong line" — and it is not theoretical: expense #149 returned a **perfectly matching total** with `gallons: 10` on a $90 receipt, i.e. $9.00/gal. Only gate 2 refuses it.
- **Deliberately NOT gates:** the receipt **date** (agreed 22/24; both disagreements were on cent-exact totals, so gating would refuse 2 real recoveries to catch nothing) and the model's self-reported **confidence** (the amount match is strictly harder evidence; stacking a soft signal on a hard one only adds false refusals). Both are *reported* for the human.
- **Measured hit rate on production (2026-08-07): 21 recovered / 24 attempted (87.5%)**, 1,211.93 gal across $4,975.49. Refusals, each named: 5 `locked_period`, 2 `no_gallons_on_receipt` (#118 is an Oklahoma Corporation Commission fee misfiled as Fuel — correctly volumeless; #130 prints no volume), 1 `implausible_cpg`.

- **⚠️ Both verbs carry `refuseCrossSite`** (refuses a `Sec-Fetch-Site` that is *present and cross-site*; absent = a non-browser client, allowed). Not a general CSRF defence — a **cost** guard. Session cookies are `sameSite:'none'`, there is no CSRF token in this app, and the GET is a *simple* request, so `<img src="…?limit=40">` on any page a Super Admin opens would fire up to 40 billed Gemini calls with their cookie. CORS hides the response, not the effect. The adjacent `fuel-events` GET deliberately does **not** get this guard — its dry run is ~140 ms of local CPU, so "a GET that cannot write is harmless" is true there. **It is the cost, not the verb, that decides.** `GEMINI_API_KEY` is shared across Alchemy projects and an exhausted key already took rate-con ingestion down once (2026-08-05).
- **`GET /api/admin/fuel-gallons-recovery`** proposes (structurally read-only — `apply` is hardcoded false, no query parameter reaches the UPDATE); **`POST …/apply`** writes. The POST **re-runs the identical pipeline and never accepts gallons from the client** — a route that stores a body-supplied number in a settlement figure makes the corroboration decorative. It takes a *selection* (`ids`) or an explicit `applyAll:true`; an empty body is a **400 `SELECTION_REQUIRED`**, same reasoning as the confirm on Mark Paid.
- **⚠️ The lock is judged BEFORE any Gemini call**, so a closed month costs nothing to refuse — and re-checked twice more, last against a row re-read from the DB immediately before the write, because a period can finalize while a long batch is in flight. Uses `expenseRowPeriodLocked()` (fails closed on an unreadable table, on a malformed date, and on *either* the settlement or operational month), not a fresh predicate.
- **`expenses.gallons_source`** ('' = a person typed it, `'ocr'` = recovered here) mirrors `odometer_source` exactly, is surfaced as `gallonsSource` on `/api/expenses/fuel-analytics` → `recentFills`, and makes the whole run reversible: `UPDATE expenses SET gallons = 0, gallons_source = '' WHERE gallons_source = 'ocr'`.
- The UPDATE's `WHERE … AND (gallons IS NULL OR gallons <= 0)` is what makes it idempotent and non-destructive — a re-run, a double-click, or a race with someone typing the number by hand all resolve to zero rows changed. Verified: second `applyAll` wrote 0.

The one that can't is #172, dated `2017-07-15` (a typo — the receipt itself reads 2022 and no telemetry goes back that far).

Three rows today, and `ORDER BY date DESC` puts them at the head — if refusals ever exceed the batch cap they would starve the recoverable tail. Enabling the feature is what creates that state. Two independent guards: `clears` is decided on `planning` and never on the point estimate, **and** an `estimated` basis is derated by `ESTIMATED_BASIS_DERATE` first. So 348 needs `1.8 × (346.9 + 50) = 714` mi to claim a pass; it returns `insufficient`. On an estimated basis `typical`/`high` are left **null**, not invented, which lands every non-clearing estimate in `insufficient` rather than the softer `tight`.
- **⚠️ `ESTIMATED_BASIS_DERATE` is 1.8, re-derived 2026-08-07, and it is NOT "the formula's overstatement" any more.** It was 2.0 on that basis (#33 1.95x / #2372 1.97x / #302 2.25x) — figures that stopped describing production the day `trucks.fuel_tank_gallons` was corrected (#33 300→198, #2372 200→100, #302 200→80), since the tank was the larger of the two factors. Re-measured on the same fill histories the aggregate overstatement is now #33 **1.30x**, #2372 **0.99x**, #302 **0.83x** — i.e. an estimated-basis truck was being derated twice, and #302 (4 legs, on the estimated basis today) was derated 2.0x on a formula already reading 17% *low*. The constant is now calibrated **end-to-end** as `predictedMilesPerPoint / measured p10` — the p50→p10 step a measured basis gets free from its own percentiles, which is a permanent property of driving (#33 spans 7.15/11.29 mi-per-point, #2372 4.31/7.22) and does *not* decay as tank data improves. Fleet **max** at the **worst** MPG source (#33 1.72 receipts / **1.80** default; #2372 1.50/1.51; #302's 1.06 excluded — 4 legs is not a percentile). **A data fix silently invalidated a code constant; re-measure this whenever tank sizes or MPG sources change.**
- **Fuel stops are NOT fetched here.** `GET /api/poi/fuel-stops` fans out to 4-8 billed Places calls per cache miss; folding it into an endpoint the panel polls would multiply that by the poll rate. Trip-plan returns `fuelStopsRecommended` + `refuelWithinMiles` and the client makes that call once, deliberately.
- **⚠️ `gallonsNeeded` is a LOWER bound.** It inherits `mpgSource`. On the one truck where MPG is cross-checkable (#2372, 71 of 72 receipts carry gallons) leg-derived `receipts` MPG reads 6.18 while total-gallons/total-miles reads ~5.0 — ~24% optimistic, because a leg attributes the gallons of the fill that ENDS it and a partial fill doesn't restore the tank to where the leg began. `pointsNeeded` is the trustworthy half: measured, and free of both tank and MPG.

Both are strictly **widening** — every name/truck that matched before still matches — so Dispatcher/Super Admin results only ever improve. ### PII at rest — why the answer was NOT encryption (2026-08-08)
A review flagged that SSN/EIN and bank routing/account numbers sit in plaintext in `app.db`, and asked for encryption at rest. **Assessed and deliberately not done.** The inventory is ~30 values in 5 tables (`job_applications.ssn|dob|drivers_license` ×8, `driver_payment_info.bank_routing|bank_account` ×4, `investor_payment_info.routing_number|account_number` ×3, `investors.ein_ssn` ×3, `investor_applications.ein_ssn` ×3). Encryption was rejected because **the same plaintext already lives in four places outside the database**, none of which a column cipher touches:
- **21 signed W-9 PDFs** in `uploads/onboarding-signed/` + `uploads/investor-onboarding-signed/` with the SSN/EIN flattened into the IRS AcroForm by `fillW9Form()`, plus contractor agreements carrying full routing/account via `lib/policy-field-maps.js`.
- **~46 unencrypted nightly backups** (8.4 GB, `backups/`, gzip is not encryption), 6 of them outside the 30-day prune regex and never deleted.
- **Sent email** — the investor-application admin notification embedded the tax id and routing number and attached the signed W-9, to a Gmail mailbox outside this system. Unrecoverable once sent.
- **`GET /api/db/query/:table`** — `SELECT *` on any table, no column filter, so every SSN was readable as JSON without downloading the 313 MB file.

**The key-location argument is the other half.** `.env` is `600 root`, `app.db` is `644 root`, the app runs as **root**, and the box has no KMS/TPM/vault. A key in `.env` would defend a DB copy that leaves *without* the `.env` (backup, `/api/db/download`, stolen image) and a non-root local reader — real, but narrow. It would do **nothing** about the threat actually named in the finding: `super_admin` is a **shared login**, and the app decrypts for whoever is authenticated. Encryption is the wrong tool for "which person read this"; masking plus an audit row is the right one. Checked and cleared: git history is clean (the tracked `app.db` was a 16 KB stub, 1 user row, no PII tables), and `scripts/refresh-env.js` already redacts all nine columns and *asserts* it — staging holds 0 populated values.

**What shipped instead** (`lib/pii-mask.js` — pure, no network/DB; fixed-width masks so length is never republished; idempotent so the client components that mask again cannot eat the last four):
- **⚠️ The IDOR was the real finding.** `/uploads` is mounted `requireAuth` **only**, and signed-PDF filenames are `${docKey}-${userId}-signed.pdf` — a five-key vocabulary crossed with a small sequential id. **Any authenticated Driver could read any other person's W-9.** The existing `confidential` flag (set on `w9` + `contractor_agreement`) was only ever a *listing* filter, which is not an access control when the URL it hides is guessable. Both signed-doc directories now resolve `signed_pdf_url` back to its row and require Super Admin, the owner, or (non-confidential only) a Dispatcher. **Authority is the DB, not the filename** — that also fails closed on the **54 of 88 files that are orphans** with no row, which breaks nothing because every UI link is built from a row. Refusal is **404, never 403**: a 403 confirms the document exists. Unconditional — *not* governed by `PII_MASK_ENABLED`.
- **⚠️ `uploads/invoices/` was the SAME hole, left open for another day, and it was the exact case the code comment predicted.** That comment justified leaving `uploads/onboarding/` unguarded purely on filename unguessability and warned *"if anything ever makes those names predictable … add it here immediately"* — but weekly invoice PDFs were **always** predictable: `${invoiceNumber}.pdf` where `generateInvoiceNumber()` builds `INV-{≤3 initials}-{YYYY}W{WW}-{NN}`, i.e. ~53 weeks × a tiny sequence, on the order of **100 requests to sweep a year for one named colleague**. `GET /api/invoices/:id/pdf` enforced ownership; the static mount served the same bytes to **any** authenticated session and simply skipped it. Measured on a scratch server against `origin/main`: a Driver read another driver’s pay PDF (weekly pay, active days, load/BOL list, expense deductions) in **all seven** path shapes tried — plain, `//`, `%2F`, mixed-case dir, `/./`, `%69nvoices`, and `/uploads/../uploads/…` — plus an eighth, a **lower-cased filename** resolving on a case-insensitive filesystem. Fixed by `guardInvoicePdf` as a fourth `GUARDED_UPLOAD_DIRS` entry, so it inherits the one normalizing guard rather than adding a sub-path mount (issue #228, 2026-08-09).
  - **MEMBERSHIP TEST, not fetch-one-then-compare** — `invoices.pdf_file_name` has **no unique index**, and the duplicate invoice-**number** bug `generateInvoiceNumber()` carried until PR #225 is precisely how two rows come to share one filename. `.get()` would return an arbitrary one and could refuse the real owner while admitting a stranger. Verified with two rows deliberately sharing a file: **both** owners get 200, everyone else 404. (Production currently has 0 such collisions — the shape is for the day it does.)
  - It reuses **`driverOwnsInvoice()`** rather than re-deriving the rule. This bug *is* "the ownership rule had a second door"; giving it a second *copy* of the rule as well is how the next drift starts. Refusing a blank `driverName` is also what denies a Dispatcher/Investor here without naming either role.
  - Soft-deleted invoices mirror the API route: **Super Admin only**. Orphan files fail closed — production has **2 of 29** (`INV-HR-2026W20-01.pdf.base`, `INV-RB-2026W31-01.pdf`) and **0 of 27 rows** has a missing PDF, so no live invoice loses its reader, and nothing in the client ever links to `/uploads/invoices/…` in the first place.
  - **Swept at the same time and deliberately left**, all four timestamped and therefore weak-secret rather than enumerable: `uploads/` root PODs (`${loadId}_POD_${Date.now()}.pdf`), `uploads/chat/` (`chat_${Date.now()}_${rand5}`), `uploads/expense-receipts/` (`${Date.now()}-${12 hex}`), `uploads/legal/` (`${scope}_${DocType}_${Date.now()}.pdf`). `uploads/onboarding-templates/` is blank forms. **⚠️ `uploads/rate-cons/` is `${loadId}.pdf` — fully enumerable — and is held ONLY by a role check, not an ownership one**, so any Dispatcher reads any load’s broker rate; that is the current intent, not an oversight, but it is the next thing to revisit if Dispatcher scope ever narrows.
- **⚠️⚠️ A GUARD ON A SUB-PATH OF A STATIC MOUNT DOES NOT HOLD. Mount it where `express.static` is mounted.** `app.use("/uploads/onboarding-signed", …)` decides using the request's **literal** path, while `express.static` at `/uploads` **decodes and normalizes** before resolving a file — so every path shape the two disagree about is protected by neither. Three bypasses were confirmed against a running server, each returning the victim's file body to a Driver session: `/uploads//onboarding-signed/<f>` (extra slash), `/uploads/onboarding-signed%2F<f>` (encoded separator), and `/uploads/Onboarding-Signed/<f>` (case). The guard is now a **single `app.use("/uploads", …)`** that does its own `decodeURIComponent` → backslash-fold → collapse-slashes → `path.posix.normalize`, and matches the directory **case-insensitively**, so it judges the same string `express.static` will resolve. **Case-insensitivity is load-bearing, not tidiness**: Express's own mount matching is case-insensitive by default, and macOS (every dev machine) has a case-insensitive filesystem — on production's ext4 the mixed-case path 404s *by accident*, i.e. the filesystem is doing the authorization, which stops being true on an overlay/CIFS mount or a Mac.
- **The same bypass class applied to the pre-existing `app.use("/uploads/rate-cons", requireRole(…))`** — a Driver could read any rate con via those shapes. Fixed in the same unified guard (403 kept for that directory, since a rate con's existence is already implied by the load id). The old line is retained only as defence in depth and is explicitly marked as not holding on its own.
- **Masking on read**, because all masking was previously **client-side only** — the server shipped full values and Vue hid them behind a reveal toggle. Applied to `GET /api/applications` (licence), `/api/applications/:id` (SSN + licence), `/api/drivers-directory/:id/documents` (SSN), `GET /api/investor-applications` **and** `/:id` (tax id + routing + account), and `/api/db/query/:table` (by column name, matched **exactly** — a substring rule would also mask `account_type`). **`dob` is deliberately left unmasked**: it is routine for DOT eligibility review and a masked date is unreadable rather than redacted.
- **Two audited reveal routes** — `GET /api/applications/:id/sensitive` and `/api/investor-applications/:id/sensitive`, `piiRevealLimiter` 20/15 min, one `audit_trail` row each. This is what makes masking cost no capability, and it is the only real answer to the shared login.
- `/api/db/*` gained `dbAdminLimiter` (10/15 min) + audit rows; `/api/db/download`'s fixed temp filename became per-request (two concurrent downloads raced and one unlinked the other's file).
- **⚠️ Masking is only safe where no edit form round-trips the value** — a masked value saved back would overwrite the real one. Verified before shipping: `job_applications` has no full-record update route (only `/status`, `/restore`), `investor_applications` writes only `/status`, and no client ever submits `einSsn`. **That invariant is now ENFORCED, not documented**: `PUT /api/investors/:id` does accept `einSsn` and write `investors.ein_ssn`, and is safe only because `GET /api/investors` happens to omit the column — so it now falls back to the stored value when `piiMask.isMasked()`. One line, and every future masking decision is safe by construction.
- **⚠️ Masking the NUMBER while shipping the DOCUMENT is not masking.** `GET /api/applications/:id` masked `ssn` + `drivers_license` and still returned `cdl_front` / `cdl_back` / `medical_card` — base64 photographs of the licence, carrying the number, DOB, address, face and signature. Now stripped (the sibling `/api/drivers-directory/:id/documents` already did). Verified first that no admin screen renders them: the only client references are the applicant's own upload form and `DriverKit.vue`'s `*_type` columns.
- **⚠️ `access_token` is dropped from the investor-application payloads UNCONDITIONALLY** — not masked, and not subject to `PII_MASK_ENABLED`. `SELECT ia.*` was shipping it beside the tax id being masked. It is a **non-expiring bearer credential**: `verifyInvestorToken()` accepts it with **no session**, authorizing the signed W-9 PDF, e-signing as that investor, and `POST …/banking`, which rewrites where money is sent. Actionable, not merely disclosive — strictly worse than the SSN next to it.
- **⚠️ `isMasked()` matches the shapes this module EMITS, never "contains a `*` or `•`".** A content test is a content test on attacker-supplied data: `ssn` and `drivers_license` come from the unauthenticated `POST /api/public/apply` and a licence field routinely carries operator notes, so `maskLicense("D*1234567")` returned it **unchanged** — the one input that must never pass through was the one that did.
- **Ownership is a MEMBERSHIP test, not fetch-one-then-compare.** `investors.application_id` is `INTEGER DEFAULT 0` with **no unique index**, so `.get()` returns an arbitrary row when two investors share one — admitting whichever SQLite returned and refusing the real owner. Ask the DB "is this user an owner of this application?" instead.
- **`..` is rejected BEFORE `path.posix.normalize`, not after.** normalize absorbs `..` on an absolute path, so a post-normalize test is dead code — and `/uploads/../uploads/onboarding-signed/<f>` normalizes to a path that no longer carries the guarded prefix, falling through to `express.static` with only `send`'s own traversal check stopping it. That is a dependency doing our authorization.
- **`/api/db/download` writes its temp copy to `os.tmpdir()`, not `__dirname`.** Making the name per-request fixed a race but created a worse problem: unique names **accumulate**, and each is a full ~313 MB dump of every SSN and account number, in the repo working tree, matched by no `.gitignore` rule (`app.db*` does not cover `app_backup*`). `app_backup*.db` is now ignored as a second guard.
- **Both reveal routes set `Cache-Control: no-store`** — the whole point is that the value is not ambient, and an undirected JSON 200 is heuristically cacheable.
- **⚠️ `PII_MASK_ENABLED` defaults ON**, breaking the ships-dormant convention on purpose — see the note in `.env.example`. It is a kill switch, not an enable switch.

**Known, deliberately left** (each is real and none is fixed by encryption): the 46 plaintext backups; the W-9/contractor PDFs still hold plaintext on disk; `POST /api/public/apply` and the invest wizard persist SSN/EIN/banking to browser **`localStorage`** (`logisx_apply_state`, `logisx_invest_state`) with no expiry, cleared only on successful submit; and `app.db` is `644` on a box with four non-root login accounts.

### Identity collation — a case-insensitive reader over a case-sensitive constraint
A driver's name is a **money join key** (`getDriverPayStructures()`, `getInvestorDriverSet()`, `expenses.driver`, `invoices.driver`), and every reader folds case. Two of the columns holding it did **not**, which is the worst combination: the readers merge the spellings, the constraints permit them.

- **`drivers_directory.driver_name` is now `UNIQUE COLLATE NOCASE`** (rename-recreate migration beside the table's `CREATE`). Before it, `"SHORN KING"` inserted *beside* `"Shorn King"`, and because `getDriverPayStructures()` keys on `LOWER(driver_name)` into a plain object with **last row wins**, the shadow row's default `pay_daily 0` beat the real row's `300` — `resolveDailyRate()` then fell back to the truck's `$250`. **Silent, and it is payroll**: on production that is $50/day against the only driver with a rate set, while the original row still reads 300 in the UI.
  - **⚠️ The uppercase variant is the only client's DEFAULT, not an exotic input.** `AddDriverForm.vue` emits `form.driver.trim().toUpperCase()`, so re-adding an existing driver from the Add Driver screen sends exactly the string that minted the shadow.
  - **⚠️ The migration's DDL is rebuilt from `PRAGMA table_info` at runtime, never hardcoded.** Column order genuinely differs between a fresh install (`pay_daily` inline in the `CREATE`) and a migrated one (`pay_daily` arrives by `ALTER`, so it is last). A hardcoded `CREATE` + `INSERT … SELECT *` transposes columns on one of the two shapes — `pay_daily 300` landing in `pay_percentage` is a 300% revenue share. Both shapes are regression-tested.
  - **⚠️ It SKIPS, loudly, if case-duplicates already exist** — never "resolves" them. An unguarded `INSERT … SELECT` throws (reads as "migration failed", so the collation quietly never lands) and an `INSERT OR IGNORE` silently **drops a row**. Which spelling is the real driver is a business question — see the Deshorn/Shorn trap below. Production had **zero** duplicates when this shipped (verified read-only).
  - **Sessions are deliberately NOT cleared.** The two precedents (`users`, `investor_applications`) clear them because a rebuilt `users` table can change a role a live session carries; nothing in a session derives from `drivers_directory`, so forcing every driver to re-login would be pure cost.
  - `getDriverPayStructures()` is the last line of defence on a database that could not migrate: it now reads `ORDER BY id` and keeps the **first** occurrence, so the *established* row wins rather than the newly-minted shadow, and logs the ignored rows. Byte-identical wherever no duplicate exists. Its key is `LOWER(TRIM(...))` because every caller looks up via `normalizeDriverName()`, which trims.
  - **⚠️ `COLLATE NOCASE` folds case, not whitespace.** `" Shorn King"` still inserts alongside `"Shorn King"`, which is why `POST /api/drivers-directory` trims at the boundary. Internal whitespace (`"shorn   king"`) is a genuinely **different** name to `getInvestorDriverSet()` — see the `caseOnly` note in `fix-driver-name` — so it is deliberately not folded anywhere.
- **`POST /api/drivers-directory` is a create verb again.** It was `INSERT OR REPLACE` on a UNIQUE column, i.e. delete-then-insert, so `{"headers":["Driver"],"values":["Shorn King"]}` blanked every column it omitted. PR #216 put the PUT's month-end predicate on that path, which closed the *closed-month* half and explicitly left three things open: an **open** month was still blanked, the replace **changed the row id** (orphaning `legal_documents.driver_id` and the profile picture), and the columns the money guard correctly ignores (address, phone, email, DOT, MC, status) were blanked with no refusal at all. An existing name is now **409 `DRIVER_EXISTS`** naming the row and pointing at the PUT — strictly stronger, and it needs no period data to be right. Blank name is **400 `DRIVER_NAME_REQUIRED`** (it used to insert a nameless row that keys as `""`).
- **`POST /api/users` got the collision check `PUT` has had since #212.** Creating a second account on an existing `driver_name` merges two people's expenses, invoices and documents — every settlement join is `LOWER(driver) = ?` and resolves to both — so it is now **409 `DRIVER_NAME_TAKEN`**. This was also the *front door* on the pay hijack: no check here, plus `syncDriverToCarrierSheet(action:"add")`'s `INSERT OR IGNORE` ignoring nothing when the case differed, minted the shadow directory row **with no period guard anywhere on that path**.
  - **`users.username` is folded in the query, not migrated.** The check compared a **trimmed** needle against the **untrimmed** column and then inserted the raw body string, so `" Bob "` and `"Bob"` coexisted while login (`LOWER(username) = LOWER(?)`) and `DELETE`'s self-delete guard both fold — the undeletable-account state. Trimming on both sides and on the INSERT closes it. **Deliberately no collation migration on `users`**: it fails *closed* (a locked record, not a mis-payment), zero duplicates exist, every reader already folds, and rebuilding that table is the one migration that does force every session to re-login.
  - `driverName` is type-checked (**400 `INVALID_DRIVER_NAME`**) and `bcrypt.hash` is hoisted **above** the guards — same check-then-act as #212's security round, and `users.driver_name` has no UNIQUE index to catch the race the way `username` does.
- **`fix-driver-name` gained the `drivers_directory` UNIQUE pre-flight** it was missing — **409 `DIRECTORY_NAME_COLLISION`**, the sibling of `INVOICE_WEEK_COLLISION` and a `DRIVER_RENAME_HARD_BLOCK_CODE` for the same reason: the executor writes every matched row the *same* value, so two rows folding onto one name violate the constraint and the UPDATE throws — and because **the sheet is written first**, that lands as `PARTIAL_RENAME`, the one outcome the route exists to prevent. Probes **old ∪ new**; the merge half (`"Deshorn King"` → `"Shorn King"`, two real people who both hold a directory row) is reachable on every database because `fix-driver-name` *permits* merges. Declared as `uniqueName: true` on the target, so the next target that gains a UNIQUE is one flag rather than a second forgotten pre-flight.

### The user routes are finance routes — guards on `PUT`/`DELETE /api/users/:id`
Both cascade into `expenses` and both can restate a **finalized** month. `DELETE` got its guard in PR #205; `PUT` is the same cascade by UPDATE and got the matching one (with the identical `expenseRowPeriodLocked()` / `blockedExpensePeriods()` / fail-closed / guard-before-first-write shape, and **not** gated on `PERIOD_FINALIZE_ENABLED`).
- **⚠️ `driverName: ""` on `PUT` DEFEATED the `DELETE` guard, and that is why the two must stay paired.** `PUT`'s cascade only fires `if (oldName && newName)`, so a blank cleared `users.driver_name` and touched nothing else. `DELETE` then resolves its cascade name as `driver_name || username`, falls back to the **username**, matches zero expense rows, finds no blocker and succeeds — leaving the receipts filed under a name with no account behind them, and silently re-adopted by the next user created with that name. Measured on production 2026-08-08: 165 rows / **$38,476.33** in finalized months were reachable this way (Howard Reddie 75 / $18,381.23; Shorn King 90 / $20,095.10).
- **409 codes:** `PERIOD_FINALIZED` (rename or blank touching a locked month; role change de-listing a settled payout), `DRIVER_NAME_IN_USE` (blanking a name that still has **expenses, documents or an assigned truck**, *even in an open month* — the stranding; `messages`/`notifications`/`driver_locations`/`load_responses` are counted and reported but deliberately do not block, being operational chatter), `DRIVER_NAME_TAKEN` (renaming onto another account's driver name irreversibly merges two people's finance rows), `LAST_SUPER_ADMIN`, `CANNOT_DELETE_SELF`, `PERIOD_LOCK_UNREADABLE`, plus 400s `INVALID_ROLE` / `INVALID_DRIVER_NAME`. Added with the unified cascade: `CONCURRENT_MODIFICATION`, `RENAME_REQUIRES_SHEET`, `SHEET_UNREADABLE`, `DRIVER_RENAME_IS_MERGE`, `INVOICE_ALREADY_PAID`, `INVOICE_WEEK_COLLISION`, `TARGET_UNREADABLE`, plus 500 `UPDATE_ROLLED_BACK`. **None are exercised by `test-suite.js`** — the harness only calls `GET /api/users`. `DELETE`'s whole cascade now runs in **one `db.transaction`** (500 `DELETE_ROLLED_BACK` on failure) — it had no try/catch, so a throw mid-cascade left the finance rows gone and the account intact.
- **⚠️ `PUT` hashes the password ABOVE the guards, and must keep doing so.** The handler is `async` and `await bcrypt.hash` is its only yield point; sitting between the guards and `UPDATE users` it held the loop open ~100 ms inside a check-then-act. Two concurrent requests (`PUT A {"role":"Driver","password":…}` + `PUT B {"role":"Driver"}`) both passed the last-Super-Admin check and **left zero Super Admins** — reproduced against a mutant build, which returns 200/200 and 0 admins where the shipped code returns 409 `LAST_SUPER_ADMIN`. Hashing first leaves no `await` between check and write.
- **A role change is a settlement event.** `listSettlableInvestors()` drives `GET /api/payouts` off `users WHERE role = 'Investor'`, so demoting an Investor drops their settled months out of every payouts surface while the rows sit in `investor_payouts`, and `grandTotals.totalPaid` quietly falls. Keyed on **`user.id`, never the role column** (#205's lesson: those tables record no role). Production carries 19 finalized payout rows across 3 investors, 2 already PAID.
- **⚠️ There is now exactly ONE driver-rename cascade, and `DRIVER_RENAME_TARGETS` is it.** `PUT /api/users/:id` used to carry its own hand-written rename — 8 UPDATEs over 7 tables against `fix-driver-name`'s 19 targets — so a rename made from the Users screen left `invoices`, `truck_assignments`, `carrier_driver_history`, `drivers_directory`, `driver_onboarding`, `load_ratings`, `job_applications`, `users.full_name`, `routemate_dvir` and `routemate_hos_daily` pointing at the old name. Both routes are now thin callers of `planDriverRenameSqlite()` (count + lock-judge, read-only) and `applyDriverRenameSqlite()` (one transaction). **Add a target to the list and both routes get it** — patching one route's list only resets the drift clock.
  - **The users route's guard now covers the whole list**, not just `expenses`. `invoices` is the leg it used to write with no check at all: one production driver carries 13 rows, 8 already PAID, in finalized months.
  - **`opts.userId` narrows only the two `users` legs**, and only for the users route. Those legs match by NAME (`users_full_name` is `LOWER(full_name)=? AND role='Driver'`), so unscoped they can rewrite a *different* account that happens to share a full name. `fix-driver-name` has no id and keeps the name-matched form.
  - **409 `RENAME_REQUIRES_SHEET`** — `PUT /api/users/:id` does **not** write the Job Tracking `Driver` column and never has. Rather than half-rename, it refuses when the sheet still carries the old name and points at `fix-driver-name`, which moves sheet + database together and offers `?dryRun=true`. Fails closed (`SHEET_UNREADABLE`) when Job Tracking cannot be read. **⚠️ It reads RAW `values.get`, not `getJobTrackingCached()`** — that helper returns `deduplicateLoads()` output (last row per load id wins), which on the local sheet hid **8 of 28** matching rows. A duplicate-load-id row carrying the old name is a real row `fix-driver-name` would rewrite, so counting the deduped view would let the partial rename in through the guard built to stop it.
  - **409 `DRIVER_RENAME_IS_MERGE`** — guard (b) `DRIVER_NAME_TAKEN` only asks whether another *account* holds the name, but `drivers_directory` has its own lifecycle, so a name with rows and no user row is ordinary. The route runs the shared merge scan and refuses, pointing at the one route with a dry run and a by-id reversal recipe. Two carve-outs are required or it refuses the commonest real rename: a **case-only** change self-matches every leg, and the **`users`/`users_full_name`** legs self-match the account being edited (`jsmith` → `John Smith` matches its own `full_name`).
  - **⚠️ `user` is re-read AFTER the last `await`, and every guard runs on that copy.** "No await between guard and write" is only half the rule; the other half is "no state read *before* the last await". The row was fetched at the top of the handler and the guards reasoned about that snapshot across ~100 ms of bcrypt and then a full sheet read — long enough for another request to promote, demote or rename the same account, yielding either a stale-role skip of the last-Super-Admin check (zero Super Admins, terminal) or a stale `oldName` that matches nothing while `UPDATE users` still writes the new name (account says one thing, every finance row another). A changed row now returns 409 `CONCURRENT_MODIFICATION`.
  - The cascade runs **before** `UPDATE users` and both sit in one `db.transaction()`: the cascade matches the account's *current* `driver_name`, so writing `users` first would blank the value the `users` legs match on. It also lets an explicit `fullName` win. `syncDriverToCarrierSheet` is then called with the **new** name as `oldName` — `drivers_directory` is a cascade target now, so looking it up by the old name misses and that helper's miss branch **inserts a duplicate directory row**.
- **⚠️ `match` and `writes` are independent, and storage case is a function of WHEN a row was written.** Three tables flipped from display case to lowercase at a single datable watermark — `notifications` at id 54 (2026-05-09 13:05), `load_responses` at id 15 (2026-05-11 14:47), `invoices` between #40 and #86 — once each, with no interleaving. So `notifications`/`load_responses` were matched on an *exact lowercase* value and silently skipped every pre-watermark row (37 + 12 for one driver); they now match case-insensitively. And `invoices` now **writes lowercase**, matching its own two INSERT paths (`driverName.toLowerCase()`, `payee.toLowerCase()`). Match wide; write the column's own convention.
- **⚠️ `invoices.driver` case is NOT cosmetic — `idx_invoices_driver_week` is a UNIQUE index on `(driver, week_start)` with BINARY collation**, so a mixed-case row sits outside the one-invoice-per-driver-week guarantee. Production carries exactly one such row (invoice #40, `"Shorn King"`, PAID, inside two locked periods) against 13 lowercase rows for the same driver. **The four readers were fixed 2026-08-09; the row was deliberately left alone** — normalising it is a write into a closed month, and the index is still BINARY (see below).
  - `GET /api/invoices/:id/pdf` + `PUT /api/invoices/:id/submit` did `invoice.driver !== (user.driverName||"").toLowerCase()` — a **one-sided** fold that 403'd the only currently active driver on his own paid $1,500 invoice, while the list that showed it to him used `LOWER(driver) = ?` and rendered it fine. Both now call the shared **`driverOwnsInvoice()`**, which folds both sides through `normalizeDriverName()`. Measured before/after against `origin/main`: 403→200 on the display-case row, 200→200 on the lowercase one, **403→403 on another driver's** (the fold must not widen access).
  - `driverOwnsInvoice()` also **refuses an empty session `driverName` outright** rather than comparing it. The old code compared `"" !== ""` and *granted* a blank-named Driver access to any blank-driver row — reproduced as a 200 on the unfixed build. Zero such invoice rows exist in production, so the narrowing costs no real access.
  - `generateInvoiceNumber()` used `driver = ?` against an already-lowercased parameter. That COUNT **is the sequence suffix**, so a week already holding a display-case invoice restarted at `-01` and minted a **duplicate invoice number** (measured: it re-mints `INV-SK-2026W19-01` over an existing row). Now `LOWER(driver) = ?`, agreeing with the duplicate guard in `generateInvoiceHandler` that always used `LOWER(driver)`.
  - `PUT /api/invoices/:id/restore` compared two stored values, so it *looked* symmetric — but BINARY equality meant restoring a soft-deleted `"shorn king"` row for a week already covered by live `"Shorn King"` found no clash. Reproduced on the unfixed build: the restore **succeeded and left two live weekly invoices on one driver-week**. Now 409.
  - **⚠️ Still open — the write side.** `COLLATE NOCASE` was deliberately NOT added to `idx_invoices_driver_week` in that PR. Folding readers fixes *reads*; the index is a *write-time* constraint, and while its collation is BINARY the two spellings remain two index entries, so a second live weekly invoice for one driver-week is still structurally insertable. It is also **not** a substitute for the reader fix: in SQLite the collation of `driver = ?` comes from the column's declared collation, never from an index, so a NOCASE index changes no query's semantics. The blocker is the migration shape at ~2508: it `DROP INDEX`es then `CREATE UNIQUE INDEX` inside a try/catch that only `console.error`s, so a single case-insensitive collision would leave the table with **no unique index at all**, silently — strictly weaker than today. Measured 2026-08-09: production currently has **zero** such collisions, so it would succeed; ship it only with a collision pre-flight that leaves the existing index in place on failure, and note the rebuild predicate keys on `/\bWHERE\b/` and needs widening or it never fires.
- **⚠️ `DRIVER_RENAME_HARD_BLOCK_CODES` outranks BOTH escape hatches** — `acknowledgeLockedPeriods` *and* the `caseOnly` money-neutral carve-out. A locked period is a decision a human can own; these two are not. `INVOICE_WEEK_COLLISION`: folding two spellings onto one name puts two rows on one `idx_invoices_driver_week` entry and the UPDATE throws — and because the sheet is written **first**, the throw lands as `PARTIAL_RENAME`. The probe must cover **old ∪ new**, not just old: old-vs-old is the case-only rename, but old-vs-**new** is the reachable one, because `fix-driver-name` *permits* merges (`isMerge` only warns). `TARGET_UNREADABLE`: a money-bearing target that cannot be read cannot be confirmed free of finalized rows — same reasoning as `PERIOD_LOCK_UNREADABLE`, and `planDriverRenameSqlite` must not swallow it into `rows: 0`, which is fail-**open**.
- **⚠️ The two `dispatch_notifications` legs are substring rewrites and are the ONLY place the Deshorn/Shorn trap is reachable.** `"Shorn King"` is a literal substring of `"Deshorn King"` — two different people — so the old `REPLACE(title, 'Shorn King', X)` would rewrite a notification about Deshorn to `"DeX"`. `replaceNameOnWordBoundary()` now decides in JS (SQLite's `LIKE`/`REPLACE` cannot express a word boundary) and writes only rows that genuinely change. Every other leg compares whole values and is immune by construction.
- Both routes now write an `audit_trail` row with per-table cascade counts. `PUT` previously logged **nothing at all**; a password change is recorded as `password reset`, never a value.
- **Availability guards, checked before the period guard** because they have no remedy: a Super Admin cannot delete their own account (`CANNOT_DELETE_SELF`, matched on session id **or** username so a session predating `user.id` cannot fail open), cannot delete the last Super Admin, and cannot **demote** the last Super Admin. All three are required — without the demotion twin, `PUT {"role":"Driver"}` then `DELETE` walks around the pair.

### `POST /api/auth/setup` — the unauthenticated admin minter
Creates the first Super Admin with no session and no role check. Its only gate was `SELECT COUNT(*) FROM users == 0`, i.e. the contents of one table — so anything emptying `users` republished an open admin minter. There is **no** `scripts/reset-super-admin-password.js` in this repo despite the reference above, so a zero-Super-Admin state means hand-editing `app.db` on the VPS.
- Now `setupLimiter` (5/15 min), audit-logged (`setup_super_admin`), and the count-check + INSERT run in **one synchronous transaction** — `await bcrypt.hash` sits between them and yields, so two concurrent requests could both pass the check and both insert.
- **The latch:** `usersEverExisted()` refuses setup when `users` is empty but the DB still carries a live system's data — a row in any of `LIVE_SYSTEM_EVIDENCE_TABLES` (`audit_trail`, `expenses`, `trucks`, `investor_payouts`, `documents`), all of which need an authenticated writer. Fails **closed** on an unreadable `users` table. A genuinely fresh install has none of them and setup works unchanged.
- **⚠️ NEVER latch on `sqlite_sequence`.** `users.id` is AUTOINCREMENT so its high-water mark looks like the perfect durable signal (413 vs 12 live rows in production) — but the CHECK-constraint probe at the top of `server.js` inserts and deletes a `__test_sa__` row on **every boot**, so the sequence climbs once per restart on an empty database. The first draft of this feature used it and refused first-time setup on a fresh install. `invoices` and `investor_applications` carry the same kind of probe.
- **What it deliberately does not cover:** a *missing* `app.db`. No content test can — the file is new and empty, which is indistinguishable from a fresh install because it is one. Mitigated by the limiter, the audit row, and backups; the structural fix is that the API can no longer reach a zero-admin state.
- **`SETUP_RECOVERY_TOKEN`** is the owner's way back: with the latch armed, setup proceeds only for a caller presenting it (via `X-Setup-Token`, `Authorization: Bearer`, or `setupToken` in the body). Unset — the normal state — the latch is simply closed. An unset token plus an empty presented token is refused *explicitly*, because `safeEqual("", "")` is true. **A token under 24 chars is treated as UNSET** (with a boot warning): it is the only control between the network and an admin, and `safeEqual` compares length first, so a short one is both guessable and length-leaking. Every refusal is `logAudit`ed (`setup_refused`) — a distributed guess would otherwise be invisible in `audit_trail`, the one place anyone looks afterwards.
- `GET /api/auth/setup-check` still returns **only** `{needsSetup}` — unchanged shape — but it now means "setup would actually succeed". **⚠️ Do not add a `locked` flag.** The route is unauthenticated and unlimited, so that flag is a free, pollable oracle for "this instance has lost its accounts but still holds data" — exactly the state in which `SETUP_RECOVERY_TOKEN` is the only remaining control. A latched system renders the ordinary login page. Rate-limiting this GET is not the alternative: the SPA calls it on every boot.
- **Session revocation is part of the guard, not a nicety.** `requireRole()` reads `req.session.user.role` and never re-reads the DB, and the cookie lasts 24 h — so before `purgeUserSessions()`, demoting or *deleting* a Super Admin left them holding a working admin cookie, and they could simply `PUT /api/users/:self {"role":"Super Admin"}` back or mint a new admin. `LAST_SUPER_ADMIN` never fires, because they are transacting as a valid Super Admin. `PUT` purges on a role change or password reset (sparing the caller's own sid), `DELETE` purges unconditionally. This also makes "reset their password" a real incident response again.

### Load ingestion — two paths, one shape
A load reaches Job Tracking two ways. **They must stay in lockstep** — a load that arrived one way has to be indistinguishable from one that arrived the other.

1. **Rate-con email (original, unattended).** `info@logisx.com` receives the rate con → a Gmail filter **stars** it + applies the **`RATECONs`** label → n8n "Dispatch v2 (Fixed)" (`ydFgTSFpKTyyZbXW`, see `Dispatch-v2-fixed.json`) fires → Drive upload, Gemini parse, dedupe, then writes **three tabs**. Blind spot: if the email never arrives, or arrives from a sender the filter doesn't match, there is **zero signal** — no execution, no alert, no row. **Two fixes shipped 2026-08-05 after two loads were lost in one day:** (a) n8n's `Validate Load ID` was a **Filter** node — one output, so a bad extraction was discarded with *no alert* while the execution still reported `success`; it is now an **If** node whose false branch feeds `Send Failure Alert` (same for `Critical Fields Complete?`, which silently dropped a written-but-rateless row). `Row Already Has Payment?`'s dead branch is **intentional** — it stops an existing payment being overwritten. (b) the reconciliation below, which catches the failure modes that produce no signal at all.

**Extraction runs in the APP, not n8n** (wired 2026-08-06). n8n's own chain was `LlamaParse (PDF→markdown) → Information Extractor`, two lossy steps that flatten the tables rate-con data lives in. Measured on the same PDF: n8n returned **`Load Number: null, Broker: null, Rate: null`** (while LlamaParse's quality gate reported `isValid: true` and pulled the word *"Confirmation"* as the load id) — the app returned every field. The row is **created before any address is examined**; `Validate Load ID` checks the load number and `Critical Fields Complete?` checks the Rate, and *nothing between them looks at the two addresses*. `Addresses Ready?` only decides whether a load gets a **mileage** — never whether it gets **created**. A guard downstream of the write cannot stop a bad write.

The check therefore lives in **`POST /api/n8n/extract-pdf-via-gemini`**, the one place that sees the fields before any sheet does and the one we own:
- **Lockstep with the drag-and-drop route.** That route normalized Gemini's output and re-ran it once when a critical field came back blank; this one returned the raw first pass. The divergence is measurable — **37 `Pickup Address` and 34 `Drop-off Address` cells in production still carry the broker's raw line breaks**, because only the attended half ever ran `collapseAddress()`. The second pass is the half that matters: it is the only mechanism that recovers a drop-off address the first pass missed.
- **⚠️ The retry is BUDGETED here and unbudgeted there.** The caller is n8n's `Extract via LogisX` node with a hard **120 s** timeout (and `retryOnFail`), while `runRateConGemini`'s own worst case is ~93 s. An unbudgeted second pass could push a *thin-but-usable* extraction past the node timeout and turn it into **no load at all** — the trade backwards. A `Promise.race` caps the retry at the remaining budget (deadline 105 s, and a retry never *starts* with under 20 s left, so a starved retry is unreachable).
- **It never fails the request.** A load with one bad field beats no load, and a non-2xx here sends n8n down its error branch. The extraction still ships; it just also raises its voice, **once per load id** (`ratecon_extract_alerts`, same shape and same reasoning as `ratecon_reconcile_alerts`). `warnings` / `unusableFields` are returned as **siblings of `output`**, never inside it, so no n8n expression changes.
- **`addressLooksUsable()` is deliberately a low bar** — a ZIP or a bounded US state token — because the two errors cost differently: a false negative costs one email, a false positive re-creates the silence. Calibrated against **all 413** production Job Tracking rows: **5 flags, all true positives** (two `Awaiting Rate Con` sentinels, and one cell holding a raw JSON blob `{"Street":…,"State":"TX","Zip":"752331402"}` that no geocoder resolves), **0 false positives**. Do not make it stricter — no city list, no street-suffix rule.
- **Replayed against the 6:** catches **5**; `554102888` correctly stays quiet, because its addresses really were fine.
- **⚠️ `RATECON_EXTRACT_ALERT_ENABLED` defaults ON**, breaking the ships-dormant convention on purpose (same call as `PII_MASK_ENABLED`): it is a kill switch, not an enable switch.
- **⚠️ Two spend ceilings, because neither the dedupe key nor `pdfOcrLimiter` is one.** The retry fires on *content* — a rate con with no rate makes it fire every request — and the dedupe key is Gemini's reading of the caller's PDF, so an incrementing load number mints fresh keys. Given the n8n secret sits in plaintext in a node parameter, treat the caller as semi-trusted. So: the load id is validated against the same `/^[A-Za-z0-9\-_.#]{1,40}$/` whitelist the public tracker uses before it may become a key (junk collapses into one `unidentified:<UTC-day>` bucket — 500 crafted ids → 1 alert); `RATECON_EXTRACT_ALERT_MAX_PER_DAY` (25) caps alerts on a key nobody controls, because `sendEmail` is shared with onboarding/outreach/invoices and a flood here would silence *all* app mail; and `RATECON_RETRY_MAX_PER_WINDOW` (20/15 min) plus a 2-slot in-flight cap bound the extra Gemini calls and the doubled peak memory. Exceeding any of them is never an error — the first-pass fields still ship.
- **⚠️ `alerted_at` is stamped only on CONFIRMED delivery**, which is why `sendEmail()` now returns a boolean (it used to return `undefined` on every path and swallow failures; existing callers ignore it, so nothing else changes). Stamping before the send is the obvious shape and it is wrong: a transient Gmail 4xx or an unconfigured mailbox would mark the load "alerted" forever, and in this table an alert that never went out would look exactly like one that did. The in-app dispatch notification counts as delivery in its own right — it is the channel that still works with no `GMAIL_*` at all.

2. **Drag-and-drop (added 2026-07-25, attended).** Dispatcher drops the rate-con PDF on the Job Board or the New Job form (scoped to the Job Board only — removed from Active Loads per client request, since a freshly-dropped load is Unassigned and lands on the Job Board anyway). `POST /api/loads/ratecon/extract` parses it and **returns without writing**; the dispatcher reviews/corrects; `POST /api/loads/from-ratecon` then replicates the n8n steps server-side. This exists because dispatchers regularly learn about a load from the driver while the app has nothing.

`POST /api/loads/from-ratecon` runs the n8n sequence in order: validate Load Number (400 if blank) → dedupe against Job Tracking (**409 `DUPLICATE_LOAD`**) → Distance Matrix + rate-per-mile → append **Job Tracking** → upsert **Payments Table** (key `" Job ID"`, leading space is real) → upsert **Job Details** → **archive the PDF** (below) → `load_coordinates` + `audit_trail` + `dispatch-notification`, then `jtCacheInvalidate()` so the load shows up before the 60s cache expires.

Gotchas worth knowing before you touch this:
- **Anchor every sheet write to column A explicitly.** `values.append` with a bare tab range lets Sheets auto-detect the table's anchor column from *existing* data; when a tab's leading column is empty in that data (**Job Details' column A is blank-named; Payments Table's early columns are sparse**) the appended row lands **shifted right into the wrong columns** — broker name into Payment Amount, distance into Rate Per Mile. The upserts therefore write via `values.update` at a computed `A{lastRow+1}`, never bare `append`. Job Tracking's own append is safe only because its column A ("Contract ID") is populated in existing rows. A synthetic-header unit test will *not* catch this — it only reproduces against the real sheet's layout.
- **The rate-con archive is what makes a dropped load invoiceable, and it is LOCAL, not Drive.** Invoice drafting finds a rate-con via `getRateConBytes()`, whose 3 sources are tried in order: (a) the Drive folder, (b) a `documents` row of type `RATECON`, (c) a base64 in the request body. Source (a) **cannot be written by this app**: the prod "Rate Confirmations" folder is a *My Drive* folder owned by `info@logisx.com` (`canAddChildren:false` for the service account, which also has zero storage quota) — n8n only writes there via OAuth delegation. So `from-ratecon` writes the PDF to `uploads/rate-cons/<loadId>.pdf` + a `documents(type=RATECON)` row (source **b**, the same local-first pattern PODs use), and only *mirrors* to Drive best-effort (silent on the expected service-account failure). Do not "fix" the archive by making Drive the primary — it will fail in prod.
- **`Contract ID` on Job Tracking stays blank.** n8n writes `Contract ID = Broker Name` on the *Payments Table* tab only. Verified against production: Job Tracking's `Contract ID` is blank for email-ingested loads and holds a numeric reference when set at all. Do **not** prefill it with the broker/agent name — that makes a dropped load diverge from an email one.
- **`Driver` is left blank** even when the rate-con names one. Dispatching from the dashboard is what emits the driver socket event and notification; writing the name directly would create a silently-assigned load.
- **Job Details has no matchable Load ID column** (its column A header is blank in prod *and* staging), so the upsert can't dedupe there — but a re-drop is already stopped by the Job Tracking 409 upstream, so the Job Details upsert only ever runs for a genuinely new load.
- **⚠️ That missing `Load ID` column is also why the Job Details tab is 93% junk today (2026-08-09, NOT yet cleaned — awaiting owner approval).** n8n's `Update Job Details (Distance)` uses `mappingMode: autoMapInputData` with `matchingColumns: ["Load ID"]`. With no such column the match can never hit, so every run **appends**; and auto-map writes the input item's keys into like-named columns, so the agent's `{output:{…}}` item lands entirely in the one column whose name it does match — a column literally called **`output`** (column **T**, the last one). Production Job Details is **163 rows: 151 `output`-only rows + 12 real drag-and-drop rows**, the two sets **disjoint**, and *no* row carries anything else. Facts that matter before anyone "tidies" this:
  - **Nothing reads `output`.** Zero references in `server.js`, `client/`, or `scripts/`; the only surface that renders it is the generic Data Manager, which renders whatever columns exist. `Distance` / `Rate Per Mile` on this tab are likewise **write-only** (`from-ratecon`) and read by nothing.
  - **Deleting the column shifts nothing** — `output` is the **last** column, and `upsertByKey` resolves everything by header *name* on a fresh read anyway.
  - **⚠️ But deleting it while the n8n node still runs makes things worse, not better:** with no matching column at all, auto-map appends an **empty row** per load, converting junk *cells* into junk *rows*. Any cleanup must land **after** the workflow stops writing `output`.
  - **The 12 real rows are interleaved** (rows 128, 141–142, 149–154, 159, 162, 164), 11 of them inside the junk block — so "delete the junk rows" is a non-contiguous, index-shifting operation, whereas clearing is a single `values.clear` on `T2:T`.
- **Every step after the Job Tracking append is best-effort** and degrades to a `warnings[]` entry rather than failing the request — the row already exists at that point, and there are no transactions.
- Steps 3-8 are ported into `lib/ratecon-load.js` as pure functions; `buildJobTrackingRow` mirrors `NewJobView.vue`'s mapping. One deliberate deviation from n8n: an unparseable rate coerces to `0` instead of writing the literal string `"NaN"` into the sheet.

## Key Conventions

- **Row indexing**: Row 1 = headers, row 2+ = data. API uses 1-based row indices. Each data object includes `_rowIndex`. DELETE internally converts to 0-indexed for Sheets `batchUpdate` `deleteDimension` (`startIndex: rowIndex - 1`).
- **Sheet selection**: All data endpoints accept `?sheet=` query param; defaults to "Job Tracking".
- **Value format**: POST/PUT bodies use `{ values: ["col1", "col2", ...] }` with `valueInputOption: "USER_ENTERED"` (supports formulas).
- **Column detection via regex**: Both backend and frontend match headers dynamically with regex patterns — `/driver/i` for driver columns, `/rate|amount|revenue|pay|charge|price|cost/i` for financial columns (hidden from Driver role), `/status/i` for status, `/load.?id|job.?id/i` for load IDs, `/origin.*lat|pickup.*lat/i` and `/dest.*lat|delivery.*lat/i` for coordinates. This makes the system flexible to different sheet column names.
- **Driver fields**: Any column matching `/driver/i` renders as a `<select>` populated from the first driver-like column in "Carrier Database".
- **Role-based routing**: Super Admin sees all, Dispatcher sees dashboard+data (no broker/financial info), Driver sees driver app (no sidebar), Investor sees financial view + truck fleet.
- **Geofence logic**: `tryGeofenceAdvance()` (from `routemateSyncTelemetry()`) uses `geolib.isPointWithinRadius()` with a **3218.69 m (2 mile) threshold** on each ELD ping — env-tunable via `GEOFENCE_RADIUS_M`, raised from 1000 m on 2026-08-06 at the client's request (of the first two automatic status changes ever recorded, one fired at 881 m against the old zone). Two consequences to know: **`load_status_history.reason` is a mixed-radius audit log** — rows before that date legitimately read `(radius 1000 m)` and are not rewritten; and a load **shorter than the radius** would strand at "At Shipper" (the truck never exits the pickup circle, so `In Transit` never fires, and `At Receiver` needs `in transit` as its predecessor) — the departure check therefore *also* accepts "moving and now closer to the delivery than to the pickup". Do not remove that second clause. Auto-advances only when current status matches the expected predecessor (Dispatched/Assigned/Heading to Shipper → At Shipper, **At Shipper/Loading → In Transit on departure**, In Transit → At Receiver); **never auto-writes a completion status**. Errors caught silently; emits `geofence-trigger` + `dispatch-notification`. Phone-GPS path (`POST /api/location`) is retired (see above).
  - **⚠️ Coordinates come from `load_coordinates`, NOT the sheet.** `checkGeofence()` prefers Job Tracking lat/lng columns, but **that sheet has no coordinate columns** (26 columns, none of them lat/lng) — so from the feature's introduction until 2026-08-05 it returned `[]` on every ping and geofencing **never fired once** (0 rows of `source='geofence'` against 197 manual status changes) while looking fully implemented. `resolveGeofencePoints()` now falls back to the `load_coordinates` table, which is where the data actually lives. Do not "simplify" this back to sheet-only.
  - **Coverage is the other half.** `load_coordinates` is filled only opportunistically — at `POST /api/loads/from-ratecon`, or by `GET /api/geocode/load/:loadId` when a human opens the map. **n8n-ingested loads get no row until someone looks at them**, so geofencing would stay dead for exactly the loads nobody is watching. `ensureLoadCoordinates()` geocodes once from the addresses already on the cached sheet row on first ping (best-effort, `geocode_cache`-backed, never throws). Row keys are inconsistent (`513987502` vs `#513987502`), so `getLoadCoordsRow()` tries both forms.
  - **Departure = time-out.** Arrival alone gives a time-IN only, which is why detention was invisible. Departure fires when the previous clean fix was inside the pickup zone, the current fix is outside, speed > `GEOFENCE_DEPART_SPEED_MPS` (2.235 m/s — the same "traveled" threshold the driver-pay active-day basis uses), and status is `at shipper|loading`. **Pickup-only by design**: leaving the receiver would mean "delivered", and completion stays manual because POD depends on it. Arrival hysteresis (previous fix also inside) is skipped for departures — a departure has already proven the previous fix was inside, so re-checking would require being in and out of the zone at once.
  - **Time in / time out needs no new storage**: `load_status_history` stamps each transition and `computeStatusPhases()` derives started/ended/`durationMs` per phase. At Shipper → In Transit *is* the shipper detention window.
  - **Every active load of a driver is evaluated, not just the first.** Queueing is supported (`POST /api/dispatch`), so a driver routinely carries two. The old `if (!loadIdByDriver[d])` first-match was **sheet row order = rate-con arrival order**, so the *oldest* load held the slot until completed and starved the load actually being driven — a row left sitting in `Dispatched` blocked automation on everything after it. Both location paths (Routemate poller **and** the Linxup webhook) now build a driver→loads list, sort by `statusProgressRank()` (most-progressed first), and `break` on the first advance so one ping writes at most one transition. Safe because `tryGeofenceAdvance` only advances from a valid predecessor, so two loads cannot both fire for one zone. **`loadIdByDriver` itself is deliberately left first-match** — the public-tracker fan-out (`publicTrack.to("load:"+activeLoadId)`) depends on that single-id shape, and changing it would alter customer-facing tracking as a side effect.
  - **⚠️ Pass `speedMps` from every location source.** The Linxup webhook path originally omitted it, which would have silently disabled departure detection (and with it the time-out half of detention) the day Linxup replaced the poller.
- **ETA calculation**: Uses `geolib.getDistance()` to destination. Default speed: 24.587 m/s (~55 mph) when GPS speed is unreliable. Compares ETA vs scheduled delivery to flag "on-time" / "delayed".
- **IFTA state matching**: Hardcoded bounding boxes for ~24 US states to classify driver GPS pings by state.
- **Sheet ID caching**: Google Sheet tab GIDs are cached in a `Map` in memory to avoid repeated API lookups. Lazy-initialized via `getSheetId()`.
- **Geocode caching**: Geocode results are cached in the `geocode_cache` SQLite table to avoid redundant Google Maps API calls.
- **No transactions**: Multi-step operations (update sheet + append log + emit socket) are not atomic. Network failures mid-operation can leave data inconsistent.
- **Onboarding documents**: driver and investor onboarding use seeded lists (`ONBOARDING_DOCS`, `INVESTOR_ONBOARDING_DOCS`) with PDF generation + e-signature capture.
- **Audit trail**: Admin actions (user creation, driver rename, etc.) are logged to the `audit_trail` table.
- **Load exclusion is centralized**: every load-revenue aggregator (`/api/dashboard`, `/api/financials`, `/api/investor`) runs sheet data through `excludeDroppedLoads(rows, headers)` before any math. It drops (a) rows whose status matches `CANCELED_STATUS_RE = /^(cancel|canceled|cancelled)$/i` and (b) rows whose `load_id` is in the `deleted_loads` table. Keep this the single place deciding "is this load live?" so dashboard/financials/investor stay consistent. `POST /api/invoices/generate` reads the sheet directly (not via this helper), so it applies its own `getDeletedLoadIds()` filter to avoid billing soft-deleted loads — keep in sync.
- **Driver "active days" = completed loads ∩ ELD travel** (driver-pay basis, shared by `/api/investor`, `/api/financials`, `POST /api/invoices/generate`): an *active day* counts only when the assigned truck **traveled** that day **and** the day is inside a **completed** load's pickup→delivery window. "Traveled" = a clean `routemate_telemetry` ping (`dropped_reason=''`) with `speed > 2.235` m/s (~5 mph). Computed by the module-scope helper `getEldTravelDaysByVehicle(vehicleIds, minMs, maxMs)` → `{ vid: { travel: Set<"YYYY-MM-DD">, coverage: Set } }`; each ping is bucketed into the **truck's local day** (zone derived per-ping from longitude via `usTzForLongitude` → continental-US IANA zone, DST-aware via `Intl`), so late trips land on the worked day, not the server's UTC day. Window days are bare wall-clock dates from the sheet (`fmtDate`/`expandDateRange`), matching the truck-local travel days. (US-centric; falls back to Central when longitude is missing.) Load truck→vehicle map: `trucks.routemate_vehicle_id` (matched on `LOWER(unit_number)`). **Coverage-aware fallback**: a window with *no* ELD pings (truck unlinked or load predates the feed) falls back to the full scheduled window so historical/un-instrumented pay is never zeroed; a covered-but-*parked* window yields 0. Daily rate = the truck's `trucks.driver_pay_daily` (falls back to `$250`; invoices used to hardcode `$250`). Only `completedStatuses` (`/^(delivered|completed|pod received)$/i`) count — the old broad `activeWorkStatuses` is gone, so deadhead, in-progress, and parked days are excluded. `parseSheetDate` (investor/financials) accepts ISO `YYYY-MM-DD` and US `M/D/Y`. Each driver-month is tagged `source: eld | mixed | estimated`; `EarningsSection.vue` renders an "ELD-verified / partly / estimated" badge. **Keep all three endpoints in lockstep** so investor portal, Financials P&L, and weekly invoice reconcile. (Invoices clip the window to the Sat–Fri billing week.)
- **Two soft-delete patterns coexist**, by design — pick the right one for new tables:
  - **Separate `deleted_loads` table** (load_id keyed): the canonical row lives in Sheets, not SQLite. Query: `LEFT JOIN deleted_loads ... WHERE deleted_loads.load_id IS NULL`. Recovery: `DELETE FROM deleted_loads WHERE load_id = ?`.
  - **`deleted_at` timestamp column** on the source table: used by `job_applications` (listings filter `WHERE deleted_at IS NULL`; `?include_deleted=true` for admin recovery). Cheaper (no join), but only works when the table lives in SQLite.
- **Notification click routing**: every `dispatch-notification` emitter stores `loadId` in the row's `metadata` JSON; admin `NotificationsView` parses it → `router.push('/dashboard?load=<loadId>')`. `DashboardView` reads `route.query.load`, switches to Active Loads, passes `focusLoadId` into `ActiveLoadsTab`, which auto-opens that load's modal then emits `focus-consumed` to clear the query.
- **SQLite timestamps on the wire**: `CURRENT_TIMESTAMP` is UTC but serializes zone-less (`"2026-04-20 14:30:00"`), which JS parses as local time. When exposing DB timestamps, wrap with `strftime('%Y-%m-%dT%H:%M:%SZ', created_at)` so the client can `new Date(ts)` correctly. `/api/dispatch-notifications` does this; follow it for new endpoints surfacing `created_at`.

### Maps key split — one key cannot be restricted, two can
`GET /api/config/maps-key` publishes a Maps key to every visitor. That is by design (the SPA needs one), so the **only** thing standing between that key and an arbitrary bill is a Google Cloud console restriction. Audited 2026-08-08: there was **none** — no application restriction and no API allowlist, verified empirically (Geocoding returned `OK` from an off-VPS IP with no `Referer`; Places New `searchNearby` returned results with a bogus `Referer`; the legacy Directions API — which this app never calls — also returned `OK`, proving no API allowlist; every denial seen was the project-level *"This API is not activated on your API project"*, never the key-level *"This API key is not authorized to use this service or API"*). Prod and staging share the identical key.
- **⚠️ The two restriction types are mutually exclusive, which is why one key can never be locked down.** A referrer-restricted key is refused outright by the legacy web services (`API keys with referer restrictions cannot be used with this API`) and, having no `Referer` to match, by Routes/Places (New) too — so it breaks **every server call**. An IP-restricted key cannot drive the Maps JavaScript API at all — so it breaks **every map**. Anyone "just adding a referrer restriction" to the shared key takes the dashboard, tracking, geocoding and rate-per-mile down at once.
- **The split**: `GOOGLE_MAPS_API_KEY` = server key (IP-restricted to the VPS; Geocoding + Distance Matrix + Routes + Places (New)). `GOOGLE_MAPS_BROWSER_KEY` = browser key (referrer-restricted; Maps JavaScript + Places). Only the browser key is ever served by the endpoint. Unset → falls back to the server key, i.e. deploying the split changes nothing until a second key exists.
- **This moves the expensive SKU off the public key.** `places:searchNearby` with `fuelOptions` (~$0.16–0.32 per fan-out) is called **only** from `lib/poi-fuel-stops.js`, server-side — so it belongs on the IP-restricted key and becomes unreachable from the published one.
- **⚠️ A referrer restriction is anti-scraper, not anti-attacker.** `Referer` is client-supplied and forgeable with one curl flag. It stops the realistic abuse (a harvested key embedded in someone else's *real website*); it does not stop a determined caller. The actual spend ceiling is the **API allowlist plus per-API quota caps and a budget alert** in the console — set those, not just the referrer.
- **⚠️⚠️ The VPS talks to Google over IPv6, so an IPv4-only allowlist breaks everything.** `76.13.22.110` is the address the box is *reached* on; it is not the address it *leaves* from. `maps.googleapis.com` resolves AAAA-first and the box prefers v6, so both curl and the Node runtime egress from **`2a02:4780:59:f4fb::1`** (proven: `curl -w '%{local_ip}'` and `socket.localAddress`/`remoteFamily` both report the v6 address against `2001:4860:…`). An IP allowlist containing only the IPv4 address would silently 403 **every** Geocoding / Distance Matrix / Routes / Places call in production. Allowlist **both** — and re-check after any VPS network change, because this is invisible until it breaks.

## Linxup GPS ingestion (webhook push)

**Linxup is the fleet GPS/telematics provider going forward, replacing the Routemate *poll* model.** (Apollo ELD — the `feat/eld-apollo-migration` provider-neutral effort — was evaluated for driver **HOS only** and dropped for GPS; Linxup won live tracking.) The defining difference from Routemate: **Linxup PUSHES** telemetry to us — there is no base URL, no poll cadence, and no `setInterval`. Linxup POSTs each message to our webhook; we validate a shared secret and ingest.

**Endpoints:**
- `POST /api/eld/linxup/webhook` — inbound push. **Token-gated** (`safeEqual` constant-time compare against `LINXUP_WEBHOOK_TOKEN`): the token is read from `Authorization: Bearer`, `X-Api-Key`, `X-Webhook-Token`, or `X-Linxup-Token` headers, or `?token=`. Returns **503** when the token is unset (not configured), **401** on mismatch, **200** `{ok, received, enabled}` on success. **ACKs fast, ingests async** (`res.json()` then `setImmediate`) so a slow sheet/geofence read never makes Linxup time out and re-deliver. Accepts a single message OR an array (`body`, `body.messages`, or `[body]`).
- `GET /api/eld/linxup/health` — **Super Admin only**. Returns `{provider:'linxup', enabled, hasToken, speedUnit, lastReceived, lastWritten, lastError, messageCounts, unlinkedPositions}`. **Never echoes the token** (`hasToken` boolean only).

**Mapping & storage:** `lib/linxup-push.js` is pure message-shape mapping. Each pushed message is classified structurally by `detectMessageType()` (the Push API carries no explicit type field) — Position, Trip, Stop, Usage, Geofence, Alert, Media, etc. **Only `Position` feeds tracking in v1**; other types are recognized + counted (`messageCounts`) so the receiver can ACK, but not written. A Position → `normalizePosition()` → the neutral telemetry shape, which server.js inserts into **`routemate_telemetry`** (the existing live table that tracking **and** the driver-pay "active days" basis already read) with `source:'linxup'` and **speed converted mph→m/s** (`speedToMps`, unit from `LINXUP_SPEED_UNIT`). It reuses the poller's quality gates (invalid-coords / speed-outlier tagged via `dropped_reason`) and the same `location-update` + `tryGeofenceAdvance()` fan-out, so tracking/pay/geofence behave identically to the Routemate path.

**Truck linkage:** a Position carries several stable ids (`tracker.trackerId`, `tracker.deviceNumber`, `tracker.deviceSerialNumber`, `asset.vin`); `vehicleIdCandidates()` returns them in that preference order and the receiver matches **any** of them against **`trucks.routemate_vehicle_id`** (the existing link column — unchanged) to resolve the truck + active driver. Unmatched positions are still stored (first candidate) so no data is lost; they just don't map to a truck until it's linked, and increment `unlinkedPositions`.

**Env vars** (in `.env.example`):
- `LINXUP_ENABLED` — master write switch. **Default off.** When false the token gate is still enforced but positions are recognized/counted only, never written → ships **dormant** (matches `ROUTEMATE_ENABLED` / `SCANKIT_ENABLED`).
- `LINXUP_WEBHOOK_TOKEN` — shared secret Linxup presents on every push. Unset → webhook 503.
- `LINXUP_SPEED_UNIT` — `mph` | `kmh` | `mps`, default `mph`.

**⚠️ LIVE-CAPTURE (confirm against the first real push):** two fields are inferred from the Push API V3 doc, not a real payload — the **speed unit** (assumed mph; a wrong guess silently mis-pays drivers via the `speed > 2.235 m/s` travel gate) and the **exact auth header** Linxup uses (we accept several defensively). Both are flagged in `lib/linxup-push.js`; lock them down once a live push is seen. **Docs:** Push API V3 PDF (`PushAPIV3.pdf`, 25-page message catalog: Position/Trip/Stop/Usage/Geofence/Alert/Media).

## House rules (`.claude/rules/`)

`.claude/rules/*.md` holds generic team coding guidelines (immutability, error handling, input validation, web security/perf, git/commit conventions, etc.). Treat them as defaults, **but this repo's reality overrides them where they conflict** — notably: the rules call for "many small files (<800 lines)" and "TDD with 80%+ coverage", whereas the backend is a deliberate ~18k-line single-file `server.js` and there is **no test framework** (only the `test-suite.js` HTTP harness). Follow the surrounding code's established patterns over the aspirational rules. Useful, accurate bits to keep: conventional-commit message format (`feat:`/`fix:`/`refactor:`/`docs:`/`test:`/`chore:`/`perf:`/`ci:`) and parameterized SQLite queries everywhere.
